    Chapter 32 — Authoring Tools & Advanced Debugging¶

    This chapter covers the tooling that makes writing and fixing tests faster: the code generator that writes a first draft for you, the Inspector for stepping through and picking locators, and a few expect refinements (with an honest note about one feature Python doesn't have). These are the day-to-day productivity tools that distinguish someone who's actually lived in Playwright from someone who's only read about it.

    32.1 playwright codegen — record actions into code¶

    You don't have to write a test from a blank file. playwright codegen opens a browser and the Playwright Inspector side by side; as you click and type in the browser, it writes the corresponding Playwright code — using good role-based locators by default:

    playwright codegen demo.playwright.dev/todomvc

    Two windows appear: the browser you interact with, and the Inspector showing generated code that you can copy into a test. Useful options:

    playwright codegen --target python-pytest playwright.dev   # emit pytest-style Python
playwright codegen --viewport-size="800,600" playwright.dev # set the viewport
playwright codegen --device="iPhone 13" playwright.dev      # emulate a device
playwright codegen --color-scheme=dark playwright.dev
playwright codegen --timezone="Europe/Rome" --geolocation="41.89,12.49" --lang="it-IT" bing.com/maps

    How to use codegen well

    Treat codegen's output as a first draft, not a finished test. It produces solid locators and correct actions, but it doesn't know your architecture — it won't put selectors into a component or extract a service. The professional workflow is: record the happy path with codegen to get correct locators quickly, then refactor that draft into your Page Object / service structure (Part IV). Codegen saves you the tedious locator-hunting; you supply the architecture.

    32.2 Capturing and reusing login with codegen¶

    Codegen can record an authenticated session and save it, so you don't have to log in by hand every time you record:

    playwright codegen github.com/microsoft/playwright --save-storage=auth.json   # log in once, save it
playwright codegen --load-storage=auth.json github.com/...                     # resume already logged in

    This is the storage-state pattern from Chapter 11, surfaced as codegen flags — handy for authoring tests on pages that sit behind a login.

    32.3 The Inspector and page.pause()¶

    For debugging (rather than recording), the Inspector lets you pause execution and step through actions one at a time. You can launch it for a whole run with an environment variable, or drop into it at a specific point in your own code with page.pause():

    PWDEBUG=1 uv run pytest tests/test_search.py      # open the Inspector for the run

    def test_something(page):
    page.goto("https://example.com")
    page.pause()                  # execution stops here; the Inspector opens with your context loaded
    page.get_by_role("button", name="Search").click()

    page.pause() is especially valuable when you've built up custom state (cookies, a logged-in session, a mid-flow page) and want the codegen/pick-locator tools available in that exact state — something a fresh codegen launch can't reproduce. While paused you can step forward, and use the Pick Locator button to hover any element and have the Inspector show you the best locator for it.

    32.4 The Trace Viewer (recap, in context)¶

    For failures you can't reproduce interactively — especially in CI — the Trace Viewer from Chapter 24 is the tool: it replays a recorded run with before/after DOM snapshots for every action. The mental split is worth stating plainly:

    • Inspector / page.pause() / --headed --slowmo — for debugging while you develop, live and interactive.
    • Trace Viewer — for debugging after the fact, especially a CI failure you can't reproduce.

    Reach for the right one based on whether you can make the failure happen again on demand.

    32.5 Tuning expect timeouts¶

    expect() assertions retry up to a default timeout (5 seconds for assertions; navigation/actions have their own 30-second default). When a specific assertion legitimately needs longer — a slow report that takes a while to generate, say — set a per-assertion timeout rather than slowing the whole suite:

    expect(slow_widget).to_be_visible(timeout=15_000)   # wait up to 15s for THIS assertion only

    You can also raise the global expectation timeout in configuration if your application is uniformly slow, but prefer per-assertion overrides — a single slow spot shouldn't make every assertion in the suite wait longer before failing.

    Honest note — Python has no built-in soft assertions

    Playwright's soft assertions (expect.soft(...), which record a failure but let the test continue so you can collect several failures in one run) are a feature of Playwright Test (the JavaScript runner), not the Python pytest-playwright integration — just like to_have_screenshot (Chapter 31). In Python, an expect failure raises immediately and stops the test. If you genuinely need to collect multiple soft-failures in one pytest run, you reach for a third-party helper such as pytest-check. Don't claim expect.soft in a Python interview — knowing it's JS-only is the precise answer.

    Interview lens

    "How do you write tests faster, and debug them?" → "I draft with playwright codegen to get correct role-based locators quickly, then refactor that into my component/service structure — I never ship raw codegen output. For debugging I use page.pause() and the Inspector's pick-locator while developing, and the Trace Viewer for CI failures I can't reproduce. And I tune timeouts per-assertion rather than globally so one slow spot doesn't slow the whole suite." That's a complete, lived-in workflow.

    Exercise 32.1 — codegen, then refactor

    Run playwright codegen --target python-pytest <some site> and record a short flow (search for something, click a result). Copy the generated test and run it. Then refactor it: move the selectors into a small Page Object with a method or two, so the test body contains no selectors. You've just done the real codegen workflow — generate, then architect.

    Key idea

    playwright codegen records a first draft with good locators (use --target python-pytest, --device, --save-storage) — then refactor it into your architecture. page.pause() + the Inspector (pick-locator) debug live; the Trace Viewer debugs after the fact. Tune expect timeouts per-assertion. And remember the honest boundaries: soft assertions and to_have_screenshot are JavaScript-runner features, not available in Python pytest-playwright.
