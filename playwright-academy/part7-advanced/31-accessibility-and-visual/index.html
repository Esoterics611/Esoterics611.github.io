    Chapter 31 — Accessibility & Visual Testing¶

    Two kinds of testing go beyond "does the button work?" to ask "is the page structured correctly?" and "does it look right?" Playwright Python supports the first natively, through aria snapshots, and the second through a mix of built-in screenshots and third-party tooling. This chapter is careful to tell you exactly what's built in versus what needs a plugin — because being honest about that distinction is itself an interview signal.

    31.1 Accessibility, and why your role locators already help¶

    Recall from Chapter 8 that the browser builds an accessibility tree — a semantic description of the page (roles and names) that assistive technology navigates. Because the whole course has you locating elements by role and name, your tests have already been exercising that tree: if get_by_role("button", name="Search") can't find the button, that's often a sign the page has an accessibility problem (a clickable <div> with no role). So good locator hygiene gives you a free, partial accessibility check.

    But you can test the accessibility structure explicitly, two ways.

    31.2 Aria snapshots — asserting the accessibility tree¶

    An aria snapshot is a YAML representation of an element's accessibility tree: its roles, names, and hierarchy. Playwright Python lets you assert that a region matches an expected structure with expect(...).to_match_aria_snapshot(...):

    from playwright.sync_api import Page, expect

def test_header_structure(page: Page):
    page.goto("https://playwright.dev")
    expect(page.get_by_role("banner")).to_match_aria_snapshot("""
        - banner:
          - link "Playwright"
          - navigation:
            - link "Docs"
            - link "API"
    """)

    This asserts that the header contains, in order, a "Playwright" link and a navigation region with "Docs" and "API" links — by their accessible roles and names, not by markup. Key features:

    • Partial matching by default: you list only the structure you care about; extra elements are allowed. (Use /children: equal or /children: deep-equal to require an exact set of children.)
    • Regex for dynamic text: write /pattern/ in place of a fixed name to match changing text.

    You can also generate the YAML programmatically to see the current tree or to capture a baseline:

    print(page.get_by_role("banner").aria_snapshot())   # prints the YAML for that region

    Aria snapshots are a powerful middle ground: more holistic than asserting one element at a time, but — unlike a pixel screenshot — stable against cosmetic restyling, because they assert meaning, not appearance.

    Interview lens

    "How would you test accessibility / page structure?" → "Two levels. First, my locators are role- and name-based, so the suite already fails if key controls aren't in the accessibility tree. Second, for structural assertions I use Playwright's aria snapshots (to_match_aria_snapshot), which assert the roles, names, and hierarchy as YAML — holistic but stable against restyling, because they check meaning, not pixels. For full WCAG rule auditing I'd add an axe-core integration (next section)." That layered answer shows real depth.

    31.3 Full accessibility auditing with axe¶

    Aria snapshots assert structure you specify. To audit a page against the actual WCAG ruleset (colour contrast, missing alt text, form labels, ARIA misuse, and dozens more), the industry standard is axe-core, integrated via a third-party library such as axe-playwright-python:

    # pip/uv add: axe-playwright-python
from axe_playwright_python.sync_playwright import Axe

def test_no_accessibility_violations(page: Page):
    page.goto("https://example.com")
    results = Axe().run(page)
    assert results.violations_count == 0, results.generate_report()

    Be honest about the boundary: axe is not part of Playwright — it's a separate, well-established library you add. Knowing that distinction (Playwright gives you aria snapshots and role locators; axe gives you rule-based auditing) is exactly the kind of accurate, non-hand-wavy answer interviewers value.

    31.4 Visual testing — and an honest caveat about Python¶

    "Visual regression testing" means capturing a screenshot and failing if it differs from an approved baseline by more than a threshold — catching unintended layout/CSS changes that functional tests miss.

    Important — to_have_screenshot is NOT in Playwright Python

    Playwright's built-in visual snapshot assertion, expect(page).to_have_screenshot(), is a feature of Playwright Test (the JavaScript/TypeScript test runner), not of the Python pytest-playwright integration. If you claim "I use to_have_screenshot in Python," an informed interviewer will know that's wrong. Be precise.

    What you can do in Python:

    # 1. Capture a screenshot (this IS built in):
page.screenshot(path="cart.png")
page.get_by_role("main").screenshot(path="cart-main.png")   # just one region

    To turn screenshots into assertions, you use a third-party pytest plugin (for example pytest-playwright-visual, or pytest-image-diff) that compares a freshly-captured image against a committed baseline and fails on a diff beyond a tolerance — or you write that comparison yourself with an image library. Either way, the capture is Playwright; the diffing is an add-on.

    A practical caution worth voicing: pixel-perfect visual tests are notoriously flaky across operating systems and browser versions (font rendering and anti-aliasing differ), so teams usually run them in a fixed container, mask dynamic regions, and allow a small pixel tolerance. Many teams deliberately prefer aria snapshots over pixel diffs precisely because structural assertions don't flake on a font-rendering difference.

    Interview lens

    "Do you do visual regression testing?" → "Playwright's built-in to_have_screenshot is a JavaScript-runner feature, not available in Python pytest-playwright. In Python I capture screenshots with page.screenshot() and compare them against baselines using a plugin like pytest-playwright-visual. But pixel diffs flake across OS/browser font rendering, so I pin them to a container, mask dynamic regions, and allow a tolerance — and where I just need structural correctness, I prefer aria snapshots, which don't flake on rendering differences." Naming the Python/JS distinction and the flakiness trade-off is a strong, precise answer.

    31.5 Attaching these to your reports¶

    Both kinds of artifact slot into the reporting you built in Chapter 25: attach screenshots to Allure steps, and attach an axe report (or the aria-snapshot YAML) on failure, so a reviewer can see what was wrong without re-running anything.

    Exercise 31.1 — assert structure, then audit

    On any page: (a) generate an aria snapshot of a region with locator.aria_snapshot(), paste the YAML into a to_match_aria_snapshot(...) assertion, then trim it to just the structure you care about and confirm partial matching still passes. (b) If you can, add axe-playwright-python and run Axe().run(page) against a deliberately-broken page (an image with no alt text) and read the violation report.

    Key idea

    Role-based locators already give partial accessibility coverage. For explicit structure, use Playwright's native aria snapshots (to_match_aria_snapshot, aria_snapshot()) — stable because they assert meaning, not pixels. For full WCAG auditing, add axe (a separate library). For visual regression, remember to_have_screenshot is JS-only; in Python you capture with page.screenshot() and diff via a plugin — and pixel diffs are flaky, so prefer structural checks where they suffice.
