    Chapter 29 — Network Interception & Mocking¶

    So far every test has driven the real application against whatever the network returned. Sometimes that's not what you want. Sometimes you need to control what the network returns — to test how the UI handles an error, an empty result, or a slow response, none of which you can reliably produce against a live backend. Playwright lets you intercept any request the page makes and decide what happens to it. This chapter teaches that capability from scratch, with the exact Python sync-API methods, and — just as importantly — when you should and shouldn't reach for it.

    29.1 Why intercept the network at all?¶

    Three motivations cover almost every real use:

    1. Test states you can't easily produce for real. How does the UI render when the search API returns zero results? When it returns a 500 error? When it's slow? Forcing the live backend into those states is hard or impossible; mocking the response makes them trivial and deterministic.
    2. Speed and determinism. A test that mocks the API doesn't depend on a real server being up, fast, or returning stable data — so it's faster and far less flaky.
    3. Block noise. You can abort requests for ads, analytics, or third-party widgets that slow tests down and add flakiness, without changing the app.

    The mechanism for all three is the same: page.route().

    29.2 page.route — intercept matching requests¶

    page.route(url_pattern, handler) registers a handler that runs for every request whose URL matches the pattern. The handler receives a Route object, and it must do exactly one of three things with it: fulfill it (provide a response), let it continue, or abort it.

    from playwright.sync_api import Page, Route, expect

def test_mock_the_fruit_api(page: Page):
    def handle(route: Route):
        mock = [{"name": "Strawberry", "id": 21}]
        route.fulfill(json=mock)              # respond with our own JSON, no real request made

    page.route("*/**/api/v1/fruits", handle)   # intercept any request to that path
    page.goto("https://demo.playwright.dev/api-mocking")
    expect(page.get_by_text("Strawberry")).to_be_visible()

    The URL pattern uses glob syntax: * matches within a path segment, ** matches across segments, so "*/**/api/v1/fruits" matches that endpoint on any host. The handler above calls route.fulfill(json=...), which makes Playwright return your JSON to the page — the real backend is never contacted. The page renders exactly as if the API had returned one strawberry, deterministically, every time.

    29.3 The three things a route handler can do¶

    route.fulfill(json=[...])               # 1. respond with a mock body (status defaults to 200)
route.fulfill(status=500, json={"error": "boom"})   # ...or a mock ERROR
route.abort()                           # 2. block the request entirely (good for ads/analytics)
route.continue_()                       # 3. let it proceed unchanged (note the trailing underscore)

    A few details that matter:

    • fulfill can set status, headers, body, or json — so you can simulate a 404, a 500, a malformed payload, anything.
    • abort simulates a failed request — useful for testing offline/error handling, or for silencing third-party noise.
    • continue_ has a trailing underscore because continue is a Python keyword (you can't name a method continue). It lets the request proceed, optionally with modified headers or post data.

    Gotcha — continue_, not continue

    continue is a reserved word in Python, so the method is spelled route.continue_(). This trips up people copying patterns from the JavaScript docs, where it's route.continue().

    29.4 Modifying a real response¶

    You can also let the real request happen, then edit the response before the page sees it. This is the route.fetch() pattern — fetch the genuine response, modify it, and fulfill with the result:

    def test_adds_a_fruit(page: Page):
    def handle(route: Route):
        response = route.fetch()              # perform the REAL request
        data = response.json()                # parse the real JSON
        data.append({"name": "Loquat", "id": 100})   # add one item
        route.fulfill(response=response, json=data)   # return the modified version

    page.route("https://demo.playwright.dev/api-mocking/api/v1/fruits", handle)
    page.goto("https://demo.playwright.dev/api-mocking")
    expect(page.get_by_text("Loquat", exact=True)).to_be_visible()

    This is the middle ground between "fully real" and "fully mocked": let the backend do its thing, but inject the one condition you want to test (an extra item, a flipped flag, a tweaked field).

    29.5 Replaying recorded traffic with HAR files¶

    For larger or more complex APIs, hand-writing mock JSON gets tedious. Playwright can record all network traffic to a HAR file (HTTP Archive) once, then replay it on later runs so the test never touches the network:

    # Replay responses from a previously-recorded HAR for matching requests:
page.route_from_har("./hars/fruit.har", url="*/**/api/v1/fruits", update=False)

    With update=True you record (or refresh) the HAR; with update=False you replay it. This gives you a deterministic, offline snapshot of a real API's behaviour — excellent for stable, fast tests against a backend you don't control, with the trade-off that the snapshot can drift from reality over time (so you re-record periodically).

    29.6 When NOT to mock¶

    Mocking is powerful, and therefore easy to overuse. The cardinal risk: a fully-mocked end-to-end test can pass while the real integration is broken. If you mock the search API and the cart API and the checkout API, your "end-to-end" test is really just testing your mocks against your UI — it would stay green even if the real backend changed its contract.

    A sound rule of thumb:

    • Mock at the edges and for hard-to-produce states — error responses, empty results, slow responses, third-party noise. These are things real backends won't reliably give you.
    • Don't mock the very thing you're trying to verify end-to-end. If the point of the test is "search really returns results from the real service," mocking that service defeats the purpose.
    • The reference project's flow is deliberately unmocked: it exercises the real eBay search and cart, because the whole point is to prove the real journey works. Mocking would be appropriate there only for a separate test like "show the empty-state message when search returns nothing."

    Interview lens

    "When do you mock the network in an end-to-end test?" → "For states the real backend can't easily produce — errors, empty results, timeouts — and to block third-party noise. I'm careful not to mock the integration the test is meant to verify, because a fully-mocked 'e2e' test can pass while the real system is broken; at that point it's a UI-against-mocks test, which is fine but should be labelled honestly. So I mock at the edges, not at the core of what I'm proving." That answer shows you understand the risk of mocking, which is more valuable than knowing the API.

    Exercise 29.1 — mock an error state

    Pick any page that calls a JSON API (the Playwright demo at https://demo.playwright.dev/api-mocking works). Write one test that uses route.fulfill to return an empty list and asserts the UI shows an empty state, and a second test that returns status=500 and asserts the UI shows an error message. Notice you just tested two states that would be very hard to trigger against a real server.

    Key idea

    page.route(pattern, handler) intercepts requests; the handler must fulfill (mock a response, including errors via status), abort (block it), or continue_ (let it pass — note the underscore). Use route.fetch() to modify a real response, and route_from_har to replay recorded traffic. Mock for hard-to-produce states and noise, never for the integration you're actually trying to verify end-to-end.
