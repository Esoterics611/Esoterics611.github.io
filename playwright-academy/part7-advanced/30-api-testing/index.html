    Chapter 30 — API Testing with Playwright¶

    Playwright is best known for driving browsers, but it ships a full HTTP client too, and it's a genuinely useful one for test engineers. This chapter covers two things: testing a REST API directly (no browser at all), and — more powerfully — combining API calls with UI tests to set up state quickly. Both come up in interviews, and the second is a technique that separates slow, fragile suites from fast, focused ones.

    30.1 Why a browser-automation tool has an HTTP client¶

    Two reasons you'll actually use it:

    1. Pure API tests. Sometimes the thing under test is the API — you want to assert that POST /issues creates an issue and returns 201, with no UI involved. Playwright's request client does this without launching a browser, so it's fast.
    2. API as a setup shortcut for UI tests. This is the high-value pattern. Suppose a UI test needs "a user with three items already in their cart." Driving the UI to create that state is slow and flaky. Instead, you call the API to set it up in milliseconds, then point the browser at the already-prepared state and test only the part you care about.

    30.2 The APIRequestContext¶

    The HTTP client is an APIRequestContext. You create a standalone one through playwright.request.new_context(...), typically in a session-scoped fixture so it's shared and configured once:

    import pytest
from playwright.sync_api import Playwright

@pytest.fixture(scope="session")
def api_request_context(playwright: Playwright):
    request_context = playwright.request.new_context(
        base_url="https://api.github.com",
        extra_http_headers={
            "Accept": "application/vnd.github.v3+json",
            "Authorization": f"token {GITHUB_API_TOKEN}",
        },
    )
    yield request_context
    request_context.dispose()        # clean up after the session (the yield/teardown pattern)

    Note the familiar shapes: a base_url so calls use short paths (Chapter 21), extra_http_headers for things like auth, the yield fixture pattern for guaranteed teardown (Chapter 13), and dispose() to release resources.

    30.3 Making requests and asserting on responses¶

    The context has a method per HTTP verb, and the response object exposes status and body:

    def test_create_issue(api_request_context):
    new_issue = api_request_context.post(
        f"/repos/{USER}/{REPO}/issues",
        data={"title": "Bug report", "body": "Something is broken"},
    )
    assert new_issue.ok                       # True for any 2xx status
    created = new_issue.json()                # parse the JSON response body
    assert created["title"] == "Bug report"

def test_list_issues(api_request_context):
    issues = api_request_context.get(f"/repos/{USER}/{REPO}/issues")
    assert issues.ok
    titles = [i["title"] for i in issues.json()]
    assert "Bug report" in titles

    The vocabulary:

    • .get(url), .post(url, data=...), .put(url, data=...), .delete(url) — one method per verb. data= sends a JSON body.
    • .ok — a boolean, True for any 2xx status. (For a specific code, there's .status.)
    • .json() — parses the response body as JSON, giving you ordinary Python dicts/lists you can assert on with plain assert (Chapter 10 — these are in-memory values, so assert, not expect).

    From TypeScript

    This is the same APIRequestContext as in TS Playwright (request.newContext, .get, .post, response.ok(), response.json()), minus the awaits. If you've used supertest or axios in JS tests, the request client fills the same role, but shares Playwright's networking and cookie handling.

    30.4 The killer pattern: API setup, UI assertion¶

    This is the technique worth internalising. Use the API to arrange state quickly, then use the browser only to assert the part you actually want to verify:

    def test_issue_appears_in_ui(api_request_context, page):
    # ARRANGE via API — fast, reliable, no clicking through forms:
    api_request_context.post(f"/repos/{USER}/{REPO}/issues",
                             data={"title": "Shows in UI", "body": "..."})

    # ASSERT via UI — only the thing under test:
    page.goto(f"https://github.com/{USER}/{REPO}/issues")
    expect(page.get_by_role("link", name="Shows in UI")).to_be_visible()

    Compare this to creating the issue through the UI (open the new-issue form, fill the title, fill the body, submit, wait for redirect) just to then check it appears in the list. That setup is slow, involves many fragile selectors, and isn't even the thing you're testing. Doing setup via the API makes the test faster, more robust, and focused — it fails only when the thing it's actually verifying breaks.

    Interview lens

    "How do you set up complex preconditions for a UI test efficiently?" → "Through the API, not the UI. Driving the UI to create state is slow and brittle and isn't what the test is verifying. I use Playwright's APIRequestContext (or any HTTP client) to arrange the state — create the user, seed the cart — in milliseconds, then point the browser at the prepared state and assert only the behaviour under test. It makes tests faster, more reliable, and more focused." This is a strong, practical answer that many candidates miss.

    30.5 Sharing authentication between the API and the browser¶

    Because both the API client and the browser context speak Playwright's networking, you can authenticate once via the API and hand the resulting session to the browser (Chapter 11's storage state):

    state = api_request_context.storage_state()       # capture cookies/tokens from the API session
context = browser.new_context(storage_state=state) # start the browser ALREADY logged in

    So a fast API login can replace a slow, captcha-prone UI login for the entire suite — log in through the API once, reuse the session everywhere.

    Exercise 30.1 — API setup, UI check

    Against any public API + UI you have access to (or a local app), write one test that creates a record via api_request_context.post(...), asserts the response .ok, then navigates the browser to a page that should display it and asserts it's visible. Time it, then imagine how much slower the same test would be if you created the record by filling out the UI form. That delta is the value of the pattern.

    Key idea

    Playwright includes a real HTTP client, the APIRequestContext (playwright.request. new_context, .get/.post/.put/.delete, .ok, .json(), .dispose()). Use it for pure API tests, and — more powerfully — to arrange state via the API and assert via the UI, which makes UI tests faster, more reliable, and focused on what they actually verify. You can even authenticate via the API once and share the session with the browser.
