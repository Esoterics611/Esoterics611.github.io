    Chapter 7 — Locators & Auto-Waiting¶

    If you internalise one chapter in this book, make it this one. Auto-waiting is the reason Playwright exists and the single biggest source of reliability in a modern suite. Understanding it deeply will eliminate the great majority of "flaky test" problems before they ever start — and "how does Playwright handle waiting?" is one of the most common interview questions there is.

    7.1 The problem: pages are asynchronous, and naive automation races them¶

    Modern web pages don't finish loading all at once. You click a button, a network request fires, and the results appear in the page some unpredictable number of milliseconds later. A naive automation tool acts the instant you tell it to — and so it often acts before the page is ready, and fails.

    The old, broken way people "fixed" this was to sleep for a fixed time and hope:

    page.click(".submit")
time.sleep(3)                 # cross your fingers that 3 seconds is enough
results = page.query_selector_all(".result")

    This is wrong in two opposite directions at once:

    • It's too slow. If the results actually appear in 200ms, you still sit there for the full 3 seconds. Multiply that waste across hundreds of tests and you've turned a two-minute suite into a twenty-minute one.
    • It's too flaky. If a busy CI machine takes 3.2 seconds one morning, the test fails — even though the application worked perfectly. The usual "fix" is to bump the sleep to 5 seconds, then 8, and now the suite is both slow and still occasionally flaky.

    There is no good fixed number, because the right amount of waiting is however long it actually takes this time, which varies. Sleeping for a constant can never be that.

    7.2 The solution: actions auto-wait for "actionability"¶

    Here is Playwright's central trick. Every action on a locator — click, fill, check, and so on — does not fire immediately. First it waits, retrying continuously, until the target element is genuinely ready to be acted upon, or until a timeout (30 seconds by default) elapses. "Ready" is defined by a precise set of actionability checks. For a click, the element must be:

    1. Attached — present in the page's DOM.
    2. Visible — it has a non-empty size and isn't hidden via display:none or visibility:hidden.
    3. Stable — not currently animating; its bounding box is the same across two consecutive animation frames.
    4. Receiving events — not covered by some overlay or other element at the point where the click would land.
    5. Enabled — not a disabled control.

    So this single line:

    page.get_by_role("button", name="Search").click()

    …actually means: "Keep checking — is the Search button attached? visible? stable? clickable at its centre? enabled? — and the moment all of those are true, click it. If 30 seconds pass and they're never all true, raise a clear timeout error explaining which check failed."

    You write the intent ("click Search") and Playwright handles the timing. For the common case, you never wait manually and you never sleep.

    Pictured, that retry loop looks like this:

    flowchart TD
    Start(["loc.click() called"]) --> A{attached?}
    A -- yes --> V{visible?}
    V -- yes --> St{stable?}
    St -- yes --> H{receives<br/>events?}
    H -- yes --> E{enabled?}
    E -- yes --> Do(["click fires"])
    A -- no --> Wait((wait briefly<br/>& retry))
    V -- no --> Wait
    St -- no --> Wait
    H -- no --> Wait
    E -- no --> Wait
    Wait --> T{timeout<br/>reached?}
    T -- no --> A
    T -- yes --> Fail(["raise: clear timeout<br/>naming which check failed"])

    Key idea

    Actions auto-wait for actionability. The instant you feel the urge to "wait here for the page to be ready," the correct response is almost never time.sleep — it's either "do nothing, the action already waits" or "assert the state you're waiting for" (next section).

    From TypeScript

    Auto-waiting is engine-level, not language-level, so it behaves identically in TS. If you ever reached for await page.waitForTimeout(3000) out of habit in TypeScript, this chapter is for you too — that's the same anti-pattern as time.sleep.

    7.3 Web-first assertions: expect() that retries¶

    Actions auto-wait. But what about checking something — that a heading appeared, that a list has five items, that the URL changed? For that, Playwright gives you expect(), whose assertions automatically retry until they pass or time out. This is how you wait for a state without sleeping:

    from playwright.sync_api import expect

expect(page.get_by_role("heading")).to_be_visible()      # waits until it's visible
expect(results).to_have_count(5)                          # retries until exactly 5 (or fails)
expect(page).to_have_url(re.compile(r".*/sch/.*"))        # waits for navigation to happen
expect(price_node).to_have_text("$25.00")                 # waits until the text matches

    Each of these polls the page repeatedly. expect(results).to_have_count(5) doesn't check "are there 5 right now?" once — it keeps checking as items stream in, and succeeds the moment there are five (or fails with a clear message after the timeout).

    Contrast this with a plain Python assert, which checks exactly once, immediately:

    assert results.count() > 0          # checks ONCE, right now — flaky if still loading
expect(results.first).to_be_visible()   # retries until visible — robust

    The rule of thumb, which we'll repeat in Chapter 10: use expect() for anything the page is still settling into, and plain assert only for values you've already finished computing in Python (a parsed Decimal, a list length you've finished building).

    Gotcha — a locator is not its matches

    This trips up nearly everyone once: 

    results = page.locator(".result-item")
assert results              # ALWAYS true! `results` is a Locator object, not a count
    A Locator is always a truthy object regardless of whether it matches anything. To actually assert presence you must act on it: expect(results.first).to_be_visible() or check results.count(). The buggy code in Chapter 26 makes exactly this mistake — it builds a locator and then asserts nothing real.

    7.4 Strict mode: ambiguity is an error, on purpose¶

    What happens if your locator matches more than one element?

    page.get_by_role("button").click()
# playwright._impl._errors.Error: strict mode violation:
#   get_by_role("button") resolved to 12 elements

    Rather than silently clicking the first match (or a random one), an action on an ambiguous locator raises a strict-mode violation. This is a deliberate, valuable feature. An ambiguous locator is a latent bug: "click the button" is meaningless if there are twelve buttons. Playwright surfaces that immediately and loudly, instead of letting it manifest later as an intermittent "it clicked the wrong thing" failure that's miserable to debug.

    When you hit a strict-mode violation, the fix is to be more specific — and the ways to do that, best to worst:

    page.get_by_role("button", name="Search")   # 1. BEST: disambiguate by accessible name
page.get_by_role("button").first            # 2. take the first — only if you're SURE
page.locator("#search-btn")                 # 3. a uniquely-identifying selector

    Interview lens

    "What is strict mode?" → "If a locator matches more than one element, Playwright throws on the action instead of guessing. It converts 'silently clicked the wrong element' — an intermittent, awful-to-debug failure — into an immediate, explicit error. I treat a strict-mode violation as a signal that my locator isn't specific enough, and I fix it by adding an accessible name, not by reflexively slapping .first on the end." That last sentence shows judgment, not just knowledge.

    7.5 Locator vs ElementHandle: use locators, always¶

    You will occasionally see an older style. It's worth knowing why to avoid it.

    Locator (use this) ElementHandle (legacy — avoid)
    Created by page.locator(...), page.get_by_*(...) page.query_selector(...)
    What it is a lazy recipe, re-resolved on each use a captured pointer to one specific DOM node
    Auto-waits? yes no
    Survives a re-render? yes (it re-finds the element) no (the pointer goes "stale")

    ElementHandle is a holdover from the Selenium/Puppeteer era. Because it grabs a specific DOM node at creation time, it becomes invalid the moment the page re-renders — the source of the dreaded StaleElementReferenceException that plagued older suites. Locators don't go stale, because they re-find the element every time you use them (§6.5). Modern Playwright is locators-only; if you see query_selector in code, that's a smell.

    7.6 Composing locators: chaining and scoping¶

    Locators combine. You take a broad locator and narrow it by chaining .locator(...) or .get_by_*(...) onto it — each step searches within the previous result:

    card = page.locator("li.s-item").first        # one result card
card.get_by_role("link").first                 # the link INSIDE that card
card.locator(".s-item__price")                 # the price INSIDE that card

    This scoping is the mechanical foundation of the component objects you'll build in Chapter 19. A component is handed a root locator and finds everything relative to it, so a ResultCardComponent scoped to one card's <li> can never accidentally grab a different card's price — even though fifty cards on the page all use the same .s-item__price class. The base component's helper is exactly this idea in one method:

    def locator(self, selector: str) -> Locator:
    return self.root.locator(selector)   # always searches within THIS component's root

    7.7 Selecting among many matches: filter and nth¶

    When a locator legitimately matches many elements and you want a specific one, prefer selecting by content over fragile position:

    rows = page.get_by_role("listitem")

rows.filter(has_text="In stock")                          # only rows containing that text
rows.filter(has=page.get_by_role("button", name="Buy"))   # only rows containing a Buy button
rows.nth(2)                                                # the third match (0-indexed)
rows.first                                                 # the first; rows.last for the last

    filter() lets you say "the row that contains X," which survives reordering and ad injection. nth(i) selects by index when you genuinely need a positional one (note: Playwright's nth is 0-indexed, unlike XPath's 1-indexing — a difference worth remembering).

    Exercise 7.1 — auto-waiting and strict mode, hands on

    On https://playwright.dev: (a) get the "Get started" link with get_by_role and click it — note you never had to wait for the page to finish loading. (b) Assert the page title contains "Playwright" using expect(page).to_have_title(...). (c) Deliberately write page.get_by_role("link").click() to trigger a strict-mode violation, read how many elements it reports, then fix it by adding a name=. You've now seen auto-waiting, web-first assertions, and strict mode.

    Exercise 7.2 — feel the difference

    Find any page with results that load after a click. Assert presence first with assert loc.is_visible() (a non-waiting snapshot) and run it ten times — note the occasional failure. Replace it with expect(loc).to_be_visible() and run ten more — note it's now rock-solid. That's the value of a retrying assertion.

    Key idea

    Actions auto-wait for actionability (attached, visible, stable, hittable, enabled), so you never time.sleep. expect() retries assertions, so you wait for state without sleeping. Ambiguity throws a strict-mode error on purpose. Use Locator (lazy, never stale), never ElementHandle. Narrow locators by chaining from a root, and select among many by content (filter) rather than position. With these habits, flakiness mostly disappears.
