    Chapter 9 — XPath, Properly Understood¶

    XPath is a tool many automation engineers have used for years without ever really understanding it. By the end of this chapter you will understand it well enough to write it, read it, and explain why you usually shouldn't reach for it. That last part is what interviewers most want to hear.

    9.1 What XPath actually is¶

    XPath (XML Path Language) is a query language for navigating a tree of nodes. HTML, once parsed, is a tree (the DOM), so XPath can address any element by describing a path through that tree — much like a filesystem path addresses a file through directories.

    /html/body/div/ul/li/a        ← an absolute path, like /home/user/file.txt

    CSS selectors can also find elements, and for most jobs they're shorter and faster. XPath's distinguishing powers are:

    1. It can match on an element's text content (contains(text(), "Add")).
    2. It can walk upward and sideways (to a parent, ancestor, or sibling), not just downward.

    Those two abilities are the only reasons to choose XPath over CSS. If you need neither, use CSS.

    9.2 The anatomy of an XPath expression¶

    //ul[contains(@class, 'srp-results')]/li[contains(@class, 's-item')]//a
└┬┘└┬┘└──────────┬───────────────┘└┬┘└─┬─┘└────────┬──────────┘└┬┘└┬┘
 │  │            │                 │  │            │            │  │
 │ node         predicate         sep node     predicate       sep node
 axis          (a filter)              (a filter)

    Piece by piece:

    Axis / separators: / and //¶

    • / — direct child. ul/li = an li that is an immediate child of ul. (Same as CSS >.)
    • // — any descendant, at any depth. //a = any <a> anywhere below. (Same as CSS descendant — a space.)
    • A leading / means absolute from the document root; a leading // means relative — match anywhere. You almost always want // (relative); absolute paths from <html> are the most brittle locators in existence.

    Node test¶

    The element name: ul, li, a, div. Use * to match any element: //*[@id='main'] = any element with that id.

    Predicate: [ ... ]¶

    A filter in square brackets, applied to the node before it. This is where XPath's power lives:

    //li[@class='s-item']                  element whose class attribute EQUALS 's-item'
//li[contains(@class, 's-item')]       class attribute CONTAINS 's-item' (substring)
//button[text()='Add to cart']         element whose text EQUALS 'Add to cart'
//button[contains(text(), 'Add')]      text CONTAINS 'Add'
//a[@href]                             any <a> that HAS an href attribute
//li[3]                                the THIRD <li> (XPath is 1-indexed!)
//div[@id='cart'][@data-open='true']   two predicates = AND
    • @name reads an attribute (@class, @href, @id, @data-testid).
    • = is exact match; contains(haystack, needle) is substring match.
    • text() is the element's text node.
    • [n] selects by position, 1-indexed (XPath counts from 1, unlike almost everything else in programming).
    • Stacking [..][..] means logical AND.

    Gotcha — 1-indexed and = vs contains

    Two traps for newcomers: (1) //li[1] is the first item, not the second — XPath counts from 1. (2) [@class='s-item'] requires the class attribute to be exactly s-item; if the real markup is class="s-item s-item--large", that exact match fails. Use contains(@class, 's-item') for elements that carry multiple classes — which is most of them.

    Useful functions¶

    contains(@class, 'x')          substring match on an attribute
starts-with(@id, 'item-')      prefix match
normalize-space(text())        text with leading/trailing/collapsed whitespace removed
text()                         the text node
last()                         the last positional index: //li[last()]
not(@disabled)                 negation: //option[not(@disabled)]

    normalize-space() is the professional touch — raw text() includes stray whitespace and newlines from HTML formatting, so text()='Add to cart' can fail where normalize-space(text())='Add to cart' succeeds.

    9.3 Axes — XPath's superpower (walking up and sideways)¶

    CSS can only go down the tree (with limited recent exceptions). XPath can go anywhere via axes:

    //span[text()='$25.00']/parent::div            the element's direct parent
//span[@class='price']/ancestor::li            the nearest <li> ancestor
//label[text()='Size']/following-sibling::select   the <select> after that <label>
//td[text()='Total']/following::td[1]          the next <td> in document order

    The killer use case: "find the price that lives in the same card as this title." You locate the title by its text, then walk up to the shared <li> ancestor, then back down to the price. CSS cannot express "go up to my container" — this is the one job XPath is uniquely good at.

    //a[contains(text(), 'Nike Air')]/ancestor::li[contains(@class,'s-item')]//span[@class='s-item__price']
└─────────── find the title ──────────┘└──── walk up to its card ────┘└──── then down to price ────┘

    9.4 Using XPath in Playwright¶

    Prefix the selector with xpath=:

    page.locator("xpath=//ul[contains(@class,'srp-results')]//a[contains(@class,'s-item__link')]")

# A leading // is auto-detected as XPath, so this also works:
page.locator("//button[text()='Add to cart']")

    Auto-waiting and strict mode (Chapter 7) apply to XPath locators exactly as they do to any other — XPath only changes how you describe the element, not how Playwright acts on it.

    9.5 CSS ⇄ XPath translation table¶

    Goal CSS XPath
    Element by tag li //li
    Direct child ul > li //ul/li
    Any descendant ul li //ul//li
    By id #main //*[@id='main']
    By class (exact) .s-item //*[@class='s-item']
    By class (contains) [class~='s-item'] //*[contains(@class,'s-item')]
    By attribute [href] //*[@href]
    nth match li:nth-of-type(3) //li[3]
    By text (not possible) //button[text()='Buy']
    Parent (not possible) //span/parent::div
    Ancestor (not possible) //span/ancestor::li

    The bottom three rows are XPath's reason to exist. Everything above them, prefer CSS.

    9.6 Why we avoid XPath by default¶

    Given XPath is more powerful, why is it last in the priority order?

    • Brittleness. XPath tempts you into long positional chains (/div[2]/div/ul/li[3]/a) that break on any DOM edit. CSS discourages this (it has no clean ancestor axis, so you don't write 8-level paths).
    • Readability. get_by_role("button", name="Add to cart") states intent; //div[3]//button[1] states structure. The next maintainer can read the first and must reverse-engineer the second.
    • Performance. XPath evaluation is generally slower than CSS, and noticeably so on large pages with // (full-tree) scans.
    • No accessibility signal. A role locator doubles as an a11y check; an XPath positional chain tells you nothing about whether the page is usable.

    Key idea

    Use XPath only for its two unique powers — matching by text and walking to a parent/ancestor/sibling. For everything else CSS is shorter, faster, and less brittle, and role/label locators beat both. Never write positional XPath chains.

    9.7 A worked case: when a spec demands XPath¶

    Sometimes a specification (or an interviewer) explicitly requires XPath — for example, "retrieve the items using XPath." That creates a tension with the priority order you just learned. The reference project resolves it the senior way: role/CSS is the default everywhere, and there is one documented XPath method that satisfies the requirement:

    _SEL_CARD_LINKS_XPATH = (
    "//ul[contains(@class, 'srp-results')]"      # the results list (descendant)
    "/li[contains(@class, 's-item')]"            # each card (direct child)
    "//a[contains(@class, 's-item__link')]"      # the link within (descendant)
)

def card_links_via_xpath(self) -> list[str]:
    links = self.page.locator(f"xpath={self._SEL_CARD_LINKS_XPATH}")
    return [
        href
        for i in range(links.count())
        if (href := links.nth(i).get_attribute("href"))
    ]

    Notice the deliberate choices that make this good XPath rather than typical bad XPath:

    • // and / mixed intentionally, not a blind //a.
    • contains(@class, …), not @class='…', because eBay cards carry several classes.
    • No positional [n] anywhere — eBay shuffles result order per visitor, so position-based XPath would be flaky. We match by what the element is.
    • The walrus := keeps only links that actually have an href (Chapter 2.5).

    Interview lens — a model answer

    "My default is role/CSS locators because they survive restyling and read as intent. When a spec asks specifically for XPath, I add one documented XPath retrieval path — and I write it carefully: relative //, contains(@class,…) rather than exact match because the cards have multiple classes, and crucially no positional indices, since eBay reorders results per visitor. So it demonstrates I can write XPath and that I know its failure modes." This answer turns the one apparent rule-break in the repo into evidence of judgment.

    Exercise 9

    On any e-commerce page, open DevTools → Console and test XPath live with $x("//a[contains(@class,'product')]") (Chrome's $x() helper runs XPath). Then: (a) select an element by its visible text, (b) from that element, walk up to its containing card with ancestor::, (c) deliberately write a positional path and then a class-based one, and observe which survives if you delete a sibling node in the Elements panel.
