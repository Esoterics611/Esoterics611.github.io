    Chapter 6 — How Playwright Is Built¶

    Playwright has a small, clean object model. Once it clicks, the rest of the library follows naturally, and you can answer the common interview opener "walk me through Playwright's architecture" with confidence. We'll build the model from the outside in, explaining each layer and why it exists, then cover the one decision that's specific to Python (sync vs async) and the single most important idea in the whole library (lazy locators).

    6.1 The four objects: Playwright, Browser, Context, Page¶

    Everything you do flows through a hierarchy of four objects:

    Playwright (the runtime)
└── Browser              one launched browser process (Chromium, Firefox, or WebKit)
    └── BrowserContext   an isolated, incognito-like session
        └── Page         a single tab
            └── Frame    (an <iframe> embedded within a page)

    The same picture, drawn to highlight why one browser hosts many isolated contexts (the isolation/parallelism boundary), each holding its own tabs:

    flowchart TD
    PW["Playwright runtime"]
    B["Browser — ONE process, expensive"]
    C1["Context A — isolated session<br/>(own cookies, storage)"]
    C2["Context B — isolated session<br/>(own cookies, storage)"]
    P1["Page (tab)"]
    P2["Page (tab)"]
    P3["Page (tab)"]
    PW --> B
    B --> C1
    B --> C2
    C1 --> P1
    C1 --> P2
    C2 --> P3

    Let's understand each, because the differences between them are what matter.

    The Playwright runtime is the engine. You rarely interact with it directly beyond starting and stopping it — and even that is usually handled for you (§6.3).

    A Browser is an actual launched browser process. Launching one is expensive — it takes a few hundred milliseconds and consumes real memory — so the rule is: launch a browser once and reuse it across many tests.

    A BrowserContext is the key concept. Think of it as a fresh incognito window: it has its own cookies, its own localStorage, its own cache, its own permissions, all completely isolated from every other context. Two contexts in the same browser cannot see each other's data. And creating a context is cheap — near-instant. This combination (one expensive browser, many cheap isolated contexts) is the foundation of two things you care about deeply: test isolation and parallelism.

    A Page is a single tab inside a context. One context can hold several pages — which is exactly what happens when the cart flow opens each product in its own tab while keeping the search-results tab around.

    A Frame is the document inside an <iframe>. Most pages have just the one main frame; you only think about frames when content is embedded (payment widgets, some consent banners) — covered in Chapter 11.

    Key idea — the isolation boundary is the CONTEXT, not the browser

    Each test gets its own fresh context: a clean cookie jar and clean storage, while sharing the already-launched (expensive) browser. This is why one test's login or cart state never leaks into the next, and why tests can run in parallel safely. If you remember one thing from this chapter, remember that the context is the unit of isolation.

    From TypeScript

    The model is identical across languages: chromium.launch() → browser.newContext() → context.newPage(). The only surface differences in Python are snake_case (new_page() not newPage()) and the absence of await (next section).

    6.2 Two APIs: sync and async (and why this course uses sync)¶

    Playwright for Python ships two versions of its API. They do the same things; they differ in how you call them.

    from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto("https://playwright.dev")
    print(page.title())          # this line BLOCKS until the title is ready
    browser.close()

    import asyncio
from playwright.async_api import async_playwright

async def main():
    async with async_playwright() as p:
        browser = await p.chromium.launch()
        page = await browser.new_page()
        await page.goto("https://playwright.dev")
        print(await page.title())     # note the `await` on every call
        await browser.close()

asyncio.run(main())

    In the synchronous API, each call runs to completion and returns its result directly — no await, no async def, no event loop to manage. This is the right choice for test suites, for three reasons: tests are inherently step-by-step ("do this, then assert that"); pytest is built around ordinary synchronous functions; and the code reads straight down the page. The asynchronous API only earns its extra ceremony when you need genuine concurrency — driving many pages at once within a single process — which test suites almost never do. (When suites want speed, they parallelise across processes with pytest-xdist, covered in Chapter 15, not across async tasks.)

    From TypeScript

    JavaScript has only the async API — every Playwright call is awaited, because JS is single-threaded and built on an event loop. Python's sync API is a real convenience JS can't offer: the same calls, no await. Mentally, take any TS Playwright snippet and delete every await. (Under the hood, the sync API runs the async engine on a background thread and blocks for you — but you never see that.)

    Gotcha — don't mix the two APIs

    Importing from both playwright.sync_api and playwright.async_api in one flow, or putting await in front of a sync call, produces confusing errors. Choose the sync API for a pytest suite and stay entirely within it.

    6.3 Who creates these objects?¶

    In a quick standalone script, you create them — that's the with sync_playwright() as p: block in §6.2, where you call launch(), new_page(), and close() yourself.

    In a pytest suite, you almost never do. The pytest-playwright plugin provides ready-made browser, context, and page objects and manages their entire lifecycle — launching the browser once, giving each test a fresh context, and tearing everything down afterwards. You simply request a page by naming it as a function argument:

    def test_home(page):                 # the plugin creates and injects a fresh page
    page.goto("https://www.ebay.com")

    That "request it by naming it" mechanism is a fixture ( Chapter 13). For now the rule to hold onto is: manual lifecycle management is for scripts; fixtures are for suites. Mixing them up — manually launching Playwright inside a pytest test — throws away everything the plugin gives you and is one of the bugs you'll dissect in Chapter 26.

    6.4 Headless vs headed, and slow-motion¶

    When you launch a browser you can choose whether it's visible and how fast it moves:

    browser = p.chromium.launch(
    headless=False,    # show a real browser window
    slow_mo=100,       # pause 100ms before each action so a human can follow along
)
    • Headless (no visible window) is the default and the right choice for CI: it's faster and needs no display attached to the machine.
    • Headed (headless=False) is for development — you watch the browser drive itself, which is invaluable when something isn't working.
    • slow_mo inserts a small delay before each action. It is purely a human-watching aid. It is not a synchronisation tool — you never use slow_mo to "wait for the page," because Playwright already waits automatically (the entire next chapter). Reaching for slow_mo to fix a timing problem is the same mistake as time.sleep.

    These two settings map directly onto the reference project's environment profiles (Chapter 21): the dev profile runs headed with slow_mo=100 for watchability; the ci profile runs headless with slow_mo=0 for speed. Same code, different configuration.

    6.5 The single most important concept: locators are lazy¶

    This idea is the hinge the whole library turns on, so we'll be deliberate about it.

    When you write this:

    search_box = page.locator("#search")   # creates a LOCATOR — finds nothing yet

    …you have not found an element. Nothing has been queried in the page. A Locator is not an element — it is a recipe for finding an element, a stored description that gets re-evaluated every time you act on it:

    search_box.fill("shoes")    # NOW Playwright runs the recipe, finds the element, and types

    Why does this laziness matter so much? Because web pages are dynamic — elements appear, disappear, and get re-rendered as JavaScript runs. If a locator captured a specific element the moment you created it, that reference would go stale the instant the page re-rendered (the classic "stale element" error from older tools). Because a Playwright locator re-runs its recipe at the moment of each action, it always finds the current element. This laziness is exactly what makes the auto-waiting in the next chapter possible — and it's why the same locator can be created early and used safely much later.

    Interview lens

    A model answer to "walk me through Playwright's object model": "One expensive browser, reused across tests; many cheap, isolated contexts — the context is the unit of test isolation and what makes parallelism safe; and pages (tabs) within a context. In a suite, the pytest-playwright fixtures own that whole lifecycle and hand each test a fresh context. And a locator is a lazy recipe, re-evaluated on every action, not a captured element — which is why it never goes stale and why auto-waiting works." That's complete, accurate, and senior.

    Exercise 6.1 — see laziness in action

    In a script, write box = page.locator("#search") before calling page.goto(...). Then page.goto(...) and only afterwards box.fill("hi"). It works — even though the locator was created before the page existed — because the locator didn't look for anything until .fill() ran. Now try the same with an old-style page.query_selector("#search") before navigation and watch it fail or return nothing: that's the difference between a lazy locator and an eager element handle.

    Key idea

    Browser (expensive, shared) → Context (cheap, isolated — the test/parallelism boundary) → Page (tab). Use the sync API in suites and let fixtures own the lifecycle. And a Locator is a lazy, re-evaluated recipe, never a captured element — the foundation everything else rests on.
