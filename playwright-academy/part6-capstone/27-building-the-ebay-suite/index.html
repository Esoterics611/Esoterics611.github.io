    Chapter 27 — Capstone: The Reference Suite End to End¶

    This chapter assembles everything into the full architecture. Read it as a guided tour from the test at the top down to the browser at the bottom and back up again, naming the chapter behind each decision. If you can narrate this walkthrough out loud, you genuinely understand the system — which is also the surest way to be able to defend a suite like it under questioning.

    27.1 The reference project, restated¶

    The worked example implements an end-to-end flow on eBay with clean architecture (POM, OOP, data-driven). It provides four functions:

    1. guest auth — establish a session;
    2. searchItemsByNameUnderPrice(query, maxPrice, limit) → URLs — search, filter by price, and collect up to limit qualifying item URLs;
    3. addItemsToCart(urls) — open each item, pick variants if required, add it to the cart;
    4. assertCartTotalNotExceeds(budgetPerItem, itemsCount) — verify the cart subtotal.

    Plus a static review of buggy AI-generated code, a README, and a run report.

    27.2 The layer map (with the chapter behind each layer)¶

    flowchart TD
    T["tests/  — assertions only  (Ch 18, 20)"]
    CF["conftest.py  — DI: db, env, services  (Ch 13, 21)"]
    SV["services/  — auth · search · cart · variants  (Ch 17, 20, 23)"]
    CO["components/  — home · header · results · card · filter · item · cart  (Ch 18, 19)"]
    PW["Playwright sync API  — browser · context · page  (Ch 6, 7)"]
    UT["utils/  — price_parser · paginator · screenshot · logger  (Ch 5, 16, 23)"]
    DB["db/  — data.yaml + typed loaders  (Ch 14, 21)"]
    T --> CF --> SV --> CO --> PW
    SV -.uses.-> UT
    T -.parametrized by.-> DB

    Every arrow points downward: tests depend on services, services on components, components on Playwright. Nothing points back up. That acyclic, downward dependency flow is the architecture — and each boundary is drawn where it is for the SOLID reasons from Chapter 17.

    27.3 Tracing one test from top to bottom¶

    Here is the canonical end-to-end test:

    @pytest.mark.regression
def test_full_e2e_search_add_assert(auth_service, search_service, cart_service, screenshots):
    with allure.step("SETUP_GUEST"):
        auth_service.start_guest_session()

    with allure.step("SEARCH"):
        urls = search_service.search_items_by_name_under_price("shoes", Decimal("220"), 5)
        assert len(urls) > 0

    with allure.step("ADD_TO_CART"):
        cart_service.add_items_to_cart(urls)

    with allure.step("ASSERT_TOTAL"):
        cart_service.assert_cart_total_not_exceeds(Decimal("220"), len(urls))

    Now walk through what happens, layer by layer, naming the chapter that explains each piece:

    1. Fixtures resolve (Chapter 13). Requesting search_service pulls in page → env → (db, profile). The test receives fully-wired services with no new in sight. The money values are Decimal literals — never floats (Chapter 5).
    2. start_guest_session() (auth service): seeds region/currency cookies on the context (Chapter 11), loads the home page, and dismisses the cookie banner idempotently (Chapter 22). No login — a guest can reach every flow under test, and the real login is captcha-gated and out of scope.
    3. search_items_by_name_under_price("shoes", 220, 5) (search service): orchestrates home.load() → header.search() → apply_price_filter() → apply_buy_it_now() → sort_by_price_plus_shipping_lowest(), then calls the generic collect_until paginator (Chapter 23) with an injected collector. The collector qualifies each card — skip sponsored, skip auctions, drop price > max, with parse_price raising on garbage (Chapters 5 and 20). It returns up to five URLs.
    4. assert len(urls) > 0 — a plain assert on an in-memory value (Chapter 10).
    5. add_items_to_cart(urls) (cart service): each URL opens in a new tab sharing the context session (Chapter 11); auctions are logged and skipped (Chapter 22); variants are chosen by the injected variant service (Chapter 23); add-to-cart fires; a screenshot is taken; the tab is closed in finally.
    6. assert_cart_total_not_exceeds(220, len(urls)) (cart service): opens the cart, parses the subtotal as a Decimal (Chapter 5), compares it against budget_per_item * items_count, and raises a structured message on failure (Chapter 20).
    7. Throughout, allure.step labels each phase and screenshots attach to the report (Chapter 25); on failure, the trace is retained (Chapter 24).

    27.4 How the data-driven variant reuses all of it¶

    @pytest.mark.regression
def test_scenario(scenario, auth_service, search_service, cart_service, screenshots):
    auth_service.start_guest_session()
    urls = search_service.search_items_by_name_under_price(
        scenario.query, scenario.max_price, scenario.limit
    )
    if len(urls) < scenario.limit and not scenario.allow_partial:
        raise AssertionError(...)
    assert len(urls) >= scenario.min_results
    if not urls:
        return
    cart_service.add_items_to_cart(urls)
    cart_service.assert_cart_total_not_exceeds(scenario.max_price, len(urls))

    It's the identical flow, but query/max_price/limit come from a Scenario dataclass that pytest_generate_tests parametrized from data.yaml (Chapter 14). Adding a scenario is a YAML edit. The allow_partial / min_results fields encode each scenario's tolerance (Chapter 22). Same services, different data — that's DRY across the smoke, regression, and data-driven suites (Chapter 17).

    27.5 The same services power a non-test demo¶

    A standalone simulate_usage.py script drives the exact same services outside pytest, headed, over a demos table — proving the framework is library-quality, not test-only glue. This is the real test of clean layering: if your services needed pytest fixtures to function, they'd be too coupled to the test harness. That they don't is the proof the boundaries are real.

    Interview lens — the whole-architecture narration

    Practise saying this in about sixty seconds: "Tests assert and are data-driven from YAML. They request services via fixture dependency injection. Services own the cross-page flows and policy — search composes home/header/results/filter plus a generic paginator; cart opens tabs, handles variants and auctions, and asserts the subtotal in Decimal. Components own one markup region each, scoped by a root locator so repeated cards don't collide. Pure utilities — the price parser, the paginator — are unit-tested in milliseconds. Config is typed, profile-switched by one env var, with no hardcoded URLs. And the same services run a headed demo outside pytest, which proves the layering holds." That narration touches every major area of evaluation.

    27.6 If you rebuilt it from scratch — a sensible order¶

    A bottom-up sequence, where each layer is testable before the next is built:

    1. Config + models (db/) — load YAML into typed dataclasses; unit-testable immediately.
    2. Pure utils (price_parser, paginator) — write them with their unit tests.
    3. BaseComponent — the scoped-locator plumbing.
    4. Components — one region at a time, against the live pages.
    5. Services — compose components into the four flows.
    6. conftest fixtures — wire the services together via DI.
    7. Tests — smoke first ("does search work?"), then the full e2e, then data-driven.
    8. Reporting + CI — Allure steps, the workflow, artifact upload.

    Exercise 27.1 — narrate it

    Without looking, narrate the path of test_full_e2e_search_add_assert out loud, from fixture resolution down to the browser and back to the assertion, naming the responsibility of each layer. Time yourself; aim for under ninety seconds. If you get stuck at a layer, that's the chapter to revisit.

    Key idea

    The whole suite is one downward dependency flow: tests → services → components → Playwright, with pure utilities and typed config on the side. Each layer has one job and one reason to change. The data-driven test and the demo script reuse the same services, proving the boundaries are real. Being able to narrate this tour is the same skill as being able to defend the design.
