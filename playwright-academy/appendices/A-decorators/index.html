    Appendix A — Decorators, In Depth¶

    Decorators are the Python feature most likely to be asked about in a "do you really know Python?" moment, and they're everywhere in this stack (@property, @dataclass, @pytest.fixture, @pytest.mark.*). This appendix takes you from "I use them" to "I can explain and write them."

    A.1 The prerequisite: functions are objects¶

    In Python a function is a first-class value — you can assign it to a variable, pass it as an argument, return it, and store it in a list:

    def shout(text):
    return text.upper()

f = shout              # assign the function itself (no parentheses!)
f("hi")                # "HI" — call it through the new name

def apply(fn, value):  # pass a function as an argument
    return fn(value)
apply(shout, "hi")     # "HI"

    Gotcha

    f = shout stores the function; f = shout("hi") calls it and stores the result ("HI"). The presence or absence of () is the entire difference. Decorators rely on passing the function itself, so this distinction matters.

    From TypeScript

    Identical to JS/TS — functions are values you can pass around. If you've written arr.map(fn) or passed a callback, you already have the prerequisite.

    A.2 A decorator is a function that takes a function and returns a function¶

    That's the whole definition. Here's the simplest useful one — a logger that wraps any function to announce its calls:

    import functools

def logged(fn):                              # (1) takes the original function
    @functools.wraps(fn)                     # (4) preserve fn's name/docstring
    def wrapper(*args, **kwargs):            # (2) a replacement function
        print(f"calling {fn.__name__}")
        result = fn(*args, **kwargs)         # (3) call the original
        print(f"{fn.__name__} returned {result!r}")
        return result
    return wrapper                           # (5) hand back the replacement

def add(a, b):
    return a + b

add = logged(add)        # wrap it manually
add(2, 3)
# calling add
# add returned 5
    1. logged receives the function to decorate.
    2. It defines wrapper, which has the same calling convention via *args, **kwargs (so it works for any signature).
    3. wrapper does its extra work, then calls the original fn.
    4. functools.wraps(fn) copies fn's name and docstring onto wrapper (without it, add.__name__ would become "wrapper" — confusing in tracebacks).
    5. logged returns wrapper, which now stands in for add.

    A.3 The @ syntax is just sugar¶

    add = logged(add) is exactly what the @ does. These two are identical:

    def add(a, b):
    return a + b
add = logged(add)        # explicit form

    @logged                  # sugar — runs `add = logged(add)` for you
def add(a, b):
    return a + b

    Key idea

    @decorator above a definition means name = decorator(name). Read every @ you see as "replace this function with whatever decorator returns when given it." That single sentence demystifies all of them.

    A.4 Decorators that take arguments (one more layer)¶

    @pytest.fixture(scope="session") and @dataclass(frozen=True) take arguments. That needs a third layer: a function that takes the arguments and returns a decorator. Reading outward-in:

    import functools

def retry(times):                            # (1) takes the ARGUMENT, returns a decorator
    def decorator(fn):                       # (2) the actual decorator
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):        # (3) the replacement function
            last = None
            for _ in range(times):
                try:
                    return fn(*args, **kwargs)
                except Exception as e:
                    last = e
            raise last
        return wrapper
    return decorator

@retry(times=3)                              # retry(3) returns `decorator`, applied to flaky
def flaky():
    ...

    So @retry(times=3) first calls retry(3) (returning decorator), then applies that to flaky. Three nested functions: configure → decorate → wrap. This is the shape behind every parameterized decorator you use.

    Interview lens

    "How does a decorator with arguments work?" → "Three layers: the outer function takes the arguments and returns a decorator; the decorator takes the function and returns a wrapper; the wrapper takes the call's args and adds behavior. @retry(3) calls the outer to get a decorator, then applies it. That's why @pytest.fixture(scope='session') has parentheses but @pytest.fixture doesn't — one is called to produce a decorator, the other is the decorator."

    A.5 The decorators you use in this course — decoded¶

    Decorator What it does Chapter
    @property turns a method into a read-only getter (access without ()) 3
    @staticmethod a method with no self — a plain function namespaced in the class C
    @classmethod a method receiving the class (cls) instead of an instance C
    @dataclass(frozen=True) generates __init__/__eq__/__repr__; frozen makes it immutable 3
    @pytest.fixture marks a function as a dependency provider for tests 13
    @pytest.fixture(scope="session") same, built once per run 13
    @pytest.mark.smoke / .regression tags a test for selection with -m 15
    @pytest.mark.parametrize(...) generates one test per data row 14
    @pytest.hookimpl(hookwrapper=True) wraps a pytest hook (used to capture test reports) 13

    Notice @property, @staticmethod, and @classmethod are built-in decorators; @dataclass is from the stdlib; the @pytest.* ones come from pytest. They're all just functions following the rule in A.3.

    A.6 Class decorators¶

    A decorator can also wrap a class (it receives the class and returns one). @dataclass is the canonical example: it takes your class with its field annotations and returns the same class with an auto-generated __init__, __eq__, and __repr__:

    @dataclass(frozen=True)
class Environment:
    id: str
    headless: bool
# dataclass added __init__(self, id, headless), __eq__, __repr__, and froze it

    You almost never write class decorators, but knowing @dataclass is "a class decorator that generates boilerplate from annotations" is a strong, precise answer.

    A.7 Why decorators matter for clean test code¶

    Decorators let a framework add cross-cutting behavior without you changing your functions: pytest discovers and parametrizes your plain test function because @parametrize wrapped it; @property lets results.cards read as a noun; @dataclass removes a dozen lines of self.x = x. They're how Python keeps your code declarative — you say what (this is a fixture, this is parametrized) and the decorator supplies the how.

    Exercise A

    1. Write a @timed decorator that prints how long the wrapped function took (use time.perf_counter()), with functools.wraps.
    2. Apply it to a function and confirm fn.__name__ is preserved.
    3. Extend it to @timed(label="search") (the three-layer form) so the printout includes a custom label.
    4. Explain out loud why @timed has no parentheses but @timed(label="x") does.

    Key idea

    A decorator is a function that takes a function (or class) and returns a replacement; @d means name = d(name). Parameterized decorators add a third nesting layer (@d(arg) calls d(arg) to get the decorator). Every @property, @dataclass, and @pytest.fixture you use is just that rule in action — and you can now write your own.
