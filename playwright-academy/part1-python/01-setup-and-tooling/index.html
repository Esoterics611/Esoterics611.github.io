    Chapter 1 — Setup & Tooling¶

    Before we write a single test, we need to understand the machinery a Python project sits on: the interpreter, virtual environments, the package manager, and the project manifest. This is not busywork. Two of the most common ways a newcomer gets stuck — "it works on my machine but not in CI" and "I installed the package but Python can't find it" — are tooling problems, not code problems. Spend twenty minutes here and you will save hours later, and you will be able to answer the very first question many interviewers ask: "How do you manage your project's dependencies?"

    We will build up the picture one layer at a time, and nothing below assumes you have used Python's tooling before.

    1.1 What "running Python" actually means¶

    When you run a Python program, a piece of software called the interpreter reads your .py file and executes it line by line. The interpreter is itself a program installed on your computer, usually reachable as python or python3:

    python3 --version
# Python 3.12.3

    So far so simple. The complication is packages. Almost no real program is written from scratch — you install libraries other people wrote (Playwright, pytest, and so on). When you install a package, it gets copied into a special folder that the interpreter searches when your code says import playwright. That folder is called site-packages.

    Here is the problem. If every project on your computer shares one site-packages folder (the one belonging to the system's Python), then every project shares one version of every library. Picture two projects:

    • Project A was written last year and depends on Playwright 1.40.
    • Project B is brand new and needs Playwright 1.50, which changed how a function behaves.

    You cannot have both 1.40 and 1.50 installed in the same site-packages at once. Fix one project and you break the other. This is the famous "dependency hell," and beginners hit it constantly because the obvious move — pip install straight into the system Python — is exactly the thing that causes it.

    Key idea

    Installing packages into the single, shared system Python couples every project to one set of library versions. We need a way to give each project its own private set of packages. That mechanism is the virtual environment.

    1.2 Virtual environments: a private sandbox per project¶

    A virtual environment ("venv") is, quite literally, a folder. Inside it lives a private copy (or link) of the Python interpreter and a private, empty-to-start site-packages. When a venv is "active," the names python and pip point at that folder's interpreter and that folder's packages instead of the system ones.

    You can see this with your own eyes. Without a venv:

    which python3
# /usr/bin/python3          ← the system interpreter, shared by everything

    Create and activate a venv, and the same command points somewhere else:

    python3 -m venv .venv          # create a venv in a folder called .venv
source .venv/bin/activate      # "activate" it (Windows: .venv\Scripts\activate)
which python
# /home/you/project/.venv/bin/python   ← now it's the PRIVATE one

    Anything you pip install now lands in .venv/, visible only to this project. Delete the .venv folder and the project's packages vanish with it, the system untouched. Project A and Project B each get their own .venv, each with the Playwright version they need, and they never collide.

    From TypeScript

    A venv is conceptually like node_modules plus a pinned copy of Node itself, bundled in one folder you "step into." Node resolves node_modules implicitly from the nearest parent folder; a venv instead changes what python means once you activate it. The payoff is identical: per-project isolation.

    This works, but managing venvs by hand (python -m venv, source activate, pip install, remembering to activate every time, keeping versions in sync across a team) is fiddly. That is the gap the next tool fills.

    1.3 uv: one tool that manages all of it¶

    uv is a modern, extremely fast project manager for Python (written in Rust). It rolls the jobs of several older tools — venv, pip, virtualenv, pip-tools — into one. Crucially, it creates and manages the venv for you, so you rarely activate anything by hand.

    Install it once:

    curl -LsSf https://astral.sh/uv/install.sh | sh    # macOS / Linux

    The single command you will use most is uv run. It means: "make sure this project's venv exists and has exactly the right packages installed, then run the following command inside it."

    uv run pytest          # runs pytest inside the project's managed venv
uv run python script.py
uv run playwright install chromium

    Notice you never typed source activate. uv run handles the venv transparently. That is why every command in this course is prefixed uv run — it guarantees the command executes against the correct, isolated set of packages.

    If you come from the Node world, this table is the Rosetta Stone:

    Task npm / Node uv
    Install everything the project declares npm install uv sync
    Add a runtime dependency npm install playwright uv add playwright
    Add a development-only dependency npm install -D pytest uv add --dev pytest
    Run a tool inside the project npx tool uv run tool
    Run a tool you don't want to install npx tool uvx tool
    The lockfile (see §1.5) package-lock.json uv.lock

    Interview lens

    A common opener is "How do you set up and manage a Python project?" A confident answer: "I use uv — it manages the virtual environment and dependencies and runs everything with uv run, so the environment is reproducible and I never pollute the system Python. Dependencies and tool config live in pyproject.toml, pinned by a uv.lock lockfile." You have just signalled that you understand isolation, reproducibility, and modern tooling — in two sentences.

    1.4 pyproject.toml: the project's single manifest¶

    Modern Python projects describe themselves in one file: pyproject.toml. (TOML is a simple, readable configuration format — think of it as a tidier .ini file. Values are grouped under headings in [square brackets] called tables.) This file is the Python equivalent of package.json.

    Here is a representative manifest, annotated. Read the numbered notes below it:

    [project]                       # (1)
name = "ebay-automation"
version = "0.1.0"
requires-python = ">=3.11"      # (2)
dependencies = [                # (3)
    "playwright>=1.44.0",
    "pyyaml>=6.0",
]

[dependency-groups]             # (4)
dev = [
    "pytest>=8.2.0",
    "pytest-playwright>=0.5.0",
    "ruff>=0.4.7",
    "black>=24.4.2",
]

[tool.pytest.ini_options]       # (5)
addopts = "--tracing=retain-on-failure"
testpaths = ["tests"]
markers = [
    "smoke: fast critical-path tests",
    "regression: full regression suite",
]
    1. [project] holds the project's identity — its name, version, and metadata.
    2. requires-python declares which Python versions are acceptable. >=3.11 means "3.11 or newer." Tools refuse to install the project on an older interpreter, catching a whole class of "works on my machine" surprises early.
    3. dependencies are the libraries the shipped code needs to run. The >=1.44.0 is a version constraint: "at least 1.44.0." Without these, your import statements would fail.
    4. [dependency-groups] → dev are libraries needed only while developing — the test runner, the linter, the formatter. A person who merely uses your package doesn't need pytest; a person working on it does. Separating the two keeps the shipped artifact lean.
    5. [tool.*] tables configure your tools, all in this one file. Instead of a scattered .pytest.ini, .ruffrc, and .flake8, everything lives under [tool.pytest...], [tool.ruff], and so on. One file, one place to look.

    Interview lens

    "Why pyproject.toml instead of a requirements.txt?" → "pyproject.toml is the modern, standardized (PEP 621) manifest. It captures project metadata, separates runtime from dev dependencies, and centralizes tool configuration — and it pairs with a lockfile for reproducible installs. A requirements.txt is just a flat list of packages with none of that." Mentioning PEP 621 by name signals you keep up with the ecosystem.

    1.5 The lockfile: making installs reproducible¶

    dependencies lists constraints (playwright>=1.44.0), not exact versions. That flexibility is good when adding packages, but dangerous for reproducibility: if you install today and a teammate installs next month, you might silently get different versions, and "works on my machine" creeps back in.

    The lockfile (uv.lock) solves this. When you run uv sync or uv add, uv resolves your constraints into one exact set of versions — including the versions of your dependencies' dependencies — and records every one in uv.lock. Commit that file, and everyone (and CI) installs the byte-for-byte same versions.

    uv sync     # reads pyproject.toml + uv.lock, installs the EXACT locked versions

    From TypeScript

    uv.lock is exactly package-lock.json / yarn.lock: the manifest says "roughly these versions," the lockfile says "precisely these versions." Commit the lockfile for applications; the reasoning is identical in both ecosystems.

    1.6 Installing the browsers (a separate step)¶

    Here is a subtlety unique to Playwright that trips up almost everyone on their first run. Installing the playwright package (via uv add/uv sync) gives you the Python API — the code you call. It does not download the actual browser programs. Those are large binaries fetched separately:

    uv run playwright install chromium               # download Chromium
uv run playwright install --with-deps chromium   # ...plus required OS libraries

    --with-deps additionally installs the operating-system-level shared libraries that headless Chromium needs (fonts, graphics libraries, etc.). On your laptop you usually already have them; on a fresh, bare Linux machine — like a CI runner — you do not, which is why CI scripts always add --with-deps.

    Gotcha — the most common first-run error

    If you install the package but forget playwright install, your first test fails with a confusing message like "Executable doesn't exist at .../chrome-linux/chrome. Looks like Playwright was just installed... run playwright install." It is not a code bug. It means the browser binaries were never downloaded. Run the install command and it disappears.

    1.7 A professional project layout¶

    Here is the directory shape this course uses, and that you should reach for in real work:

    ebay-automation/
├── pyproject.toml            # manifest + tool config (§1.4)
├── uv.lock                   # pinned, reproducible versions (§1.5)
├── .env.example              # documents which secrets are needed (committed)
├── .env                      # the actual secret VALUES (gitignored — never committed)
├── src/
│   └── ebay_automation/      # the importable package — your framework code
│       ├── components/       # Page Object Model layer
│       ├── services/         # business-flow layer
│       ├── db/               # config / test-data loading
│       └── utils/            # small helpers (logging, price parsing, screenshots)
└── tests/
    ├── conftest.py           # shared pytest fixtures
    ├── unit/                 # fast tests with no browser
    └── test_*.py             # end-to-end tests

    Two conventions here are worth understanding rather than just copying.

    The src/ layout. Notice the package lives under src/, not at the repo root. Why the extra folder? Because of a sneaky bug it prevents. If your package sat at the root, Python could import ebay_automation directly from your working directory even when the package was never properly installed. Everything would seem fine on your machine — and then break for a teammate or in CI, because the "it just happened to be importable from the current folder" trick doesn't hold there. Putting the code under src/ makes that shortcut impossible, which forces you to install the package properly (uv sync does this automatically, in "editable" mode — see the note). Your tests then import the package the exact same way a real user would, so a packaging mistake fails immediately and locally, not later and remotely.

    tests/ is a sibling of src/, not inside it. Test code is not part of the shipped product, so keeping it out of the package keeps the published artifact clean.

    From TypeScript

    The src/ layout is like keeping src/ and test/ as siblings with a build step that only emits src/. "Editable install" is like npm link-ing your own package into itself: your code edits are picked up live, with no rebuild between change and test run.

    1.8 Secrets versus structural configuration¶

    There are two kinds of "configuration," and conflating them is a classic, sometimes serious, mistake.

    • Secrets — passwords, API keys, tokens. These differ per person or machine, must never be committed to git, and live in a file called .env that is listed in .gitignore. To document which secrets a project needs without revealing their values, you commit a .env.example template with the keys but blank/placeholder values.
    • Structural configuration — base URLs, timeouts, which region or currency to test, how many pages to paginate. These are not secret, are shared by the whole team, and should be committed — ideally in a typed, queryable form (we build exactly this in Chapter 21).
    # .env.example  (committed — a template, no real values)
EBAY_USERNAME=
EBAY_PASSWORD=

# .env          (gitignored — the real values, only on your machine)
EBAY_USERNAME=alice@example.com
EBAY_PASSWORD=hunter2

    Gotcha

    Two failure modes, mirror images of each other: putting a base URL in .env (now every teammate must invent their own, and there is no shared source of truth), and putting a password in committed config (now your secret is in git history forever — a genuine security incident). The rule is simple: secrets in .env, everything else in committed config.

    Interview lens

    "Where do you keep configuration?" Always split the answer in two: "Secrets in a gitignored .env, documented by a committed .env.example. Structural, non-secret config — base URLs, profiles, timeouts — in a committed, typed file." This shows security awareness and maintainability instinct in one breath.

    1.9 Putting it together: a first run from scratch¶

    Let's assemble everything above into a real, working setup you can type out now.

    # 1. Create and enter a project folder
mkdir hello-playwright && cd hello-playwright

# 2. Initialise a uv project (writes a starter pyproject.toml)
uv init

# 3. Add the dependencies we need
uv add playwright
uv add --dev pytest pytest-playwright

# 4. Download the browser binaries
uv run playwright install chromium

# 5. Write the smallest possible test
mkdir tests
cat > tests/test_first.py <<'PY'
def test_title(page):
    page.goto("https://playwright.dev/")
    assert "Playwright" in page.title()
PY

# 6. Run it
uv run pytest

    You should see one passing test. Pause on something subtle: your test function took an argument called page, yet you never created a page anywhere. Where did it come from? It was supplied by the pytest-playwright plugin through a mechanism called a fixture — pytest saw the parameter named page, found a provider for it, created a fresh browser page, and handed it in. That is dependency injection, and it is one of the most important ideas in the whole course. We unpack it thoroughly in Chapter 13; for now, just notice that something gave you a working browser tab for free.

    1.10 Exercises¶

    Exercise 1.1 — see the isolation

    In an empty folder, run which python3. Then python3 -m venv .venv and source .venv/bin/activate (or .venv\Scripts\activate on Windows), and run which python again. Confirm the path changed from a system location to one inside .venv/. Run deactivate and confirm it changes back. You have now seen what a virtual environment does.

    Exercise 1.2 — a project from nothing

    Follow §1.9 end to end on your own machine. Then deliberately skip step 4 (playwright install) in a fresh project and run the test — read the error message carefully so you'll recognise it instantly the next time it appears in a colleague's screen-share.

    Exercise 1.3 — read a manifest

    Open the pyproject.toml uv init generated and add a dev dependency with uv add --dev ruff. Watch how both pyproject.toml and uv.lock change. Explain to yourself, in one sentence each, what each file now records.

    Key idea

    The interpreter runs your code; a virtual environment gives each project its own private packages; uv creates that environment and runs everything with uv run; pyproject.toml is the single manifest and the uv.lock lockfile pins exact versions for reproducibility; browsers install separately from the Playwright package; the src/ layout forces correct installs; and secrets and structural config live in different places for different reasons.
