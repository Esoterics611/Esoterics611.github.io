    Chapter 5 — Decimal, Money & Context Managers¶

    Two compact topics that punch far above their weight — in real bugs and in interviews. The first is why money must never be a floating-point number, and how to handle it correctly. The second is the with statement, the mechanism Playwright and the reporting tools lean on to manage resources safely. Both are explained from scratch.

    5.1 Why floating-point numbers corrupt money¶

    Computers store ordinary decimals like 0.1 using a format called floating point (IEEE 754), which represents numbers in binary (base 2). The trouble is that many perfectly ordinary base-10 fractions have no exact representation in base 2 — just as 1/3 has no exact representation in base 10 (0.3333… forever). So the computer stores the closest binary approximation, and the tiny error leaks out:

    >>> 0.1 + 0.2
0.30000000000000004
>>> 0.1 + 0.2 == 0.3
False

    Read that again: in Python (and JavaScript, and most languages), 0.1 + 0.2 is not equal to 0.3. It's 0.30000000000000004. The error is microscopic, but it is real, and it is exactly the kind of thing that wrecks a test that compares money.

    Picture the reference project's core assertion: "the cart subtotal must not exceed the budget." If budgets and prices are floats, you can get:

    • a subtotal of $0.30 that compares as greater than a budget computed as 0.1 + 0.2, failing a test that should pass; or
    • a $220.01 total that rounds its way to comparing as ≤ 220.0 and passes a test that should fail.

    Money bugs are the bugs that destroy trust, because the numbers are almost right.

    5.2 Decimal: exact base-10 arithmetic¶

    Python's standard library provides Decimal, which stores numbers in base 10, exactly as written — no binary approximation:

    from decimal import Decimal

Decimal("0.1") + Decimal("0.2")              # Decimal('0.3')  — exact
Decimal("0.1") + Decimal("0.2") == Decimal("0.3")   # True

    Decimal supports all the arithmetic and comparisons you'd expect, and it never silently turns back into a float, so an entire money pipeline — parse, multiply, compare — stays exact end to end.

    But there is one rule you must never break:

    Decimal("25.00")     # CORRECT — construct from a STRING
Decimal(25.00)       # WRONG — the float 25.00 may already be imprecise
Decimal(0.1)         # Decimal('0.1000000000000000055511151231257827021181583404541015625')

    Look at that last line. Decimal(0.1) is a disaster, because 0.1 was already a lossy binary float before Decimal ever saw it — and Decimal faithfully preserves the error. Decimal("0.1"), built from the string "0.1", is exactly one-tenth.

    The cardinal rule of money in Python

    Always build a Decimal from a string, never from a float. The instant a value passes through float, the damage is done and Decimal can only preserve it. This is precisely why prices are stored as quoted strings in YAML (max_price: "220.00") and parsed with Decimal(str(value)) — the value goes string → Decimal and never touches float.

    Multiplication and comparison stay exact, which is all the budget check needs:

    budget = budget_per_item * items_count    # Decimal * int → Decimal, still exact
if subtotal > budget:                      # exact comparison
    raise AssertionError("over budget")

    From TypeScript

    JavaScript has only IEEE floats (the number type), which is why serious JS money code reaches for integer cents, BigInt, or libraries like decimal.js/dinero.js. Python's Decimal is the batteries-included equivalent of decimal.js. The trap Decimal(0.1) vs Decimal("0.1") is identical to new Decimal(0.1) vs new Decimal("0.1") in those libraries.

    Interview lens

    "Why use Decimal instead of float for prices?" is a classic question that sorts juniors from seniors. A full answer: "Floats are binary and can't represent most decimal fractions exactly, so 0.1 + 0.2 != 0.3. For budget comparisons that causes false passes and false failures. Decimal is exact base-10 — but only if you construct it from a string, never a float, which is why I store prices as quoted strings." Explaining the binary representation root cause is what makes the answer complete.

    5.3 Parsing a messy price string safely¶

    Real prices on a page arrive as messy text: "$25.00", "US $1,234.56", "$25.00 to $30.00", even "Subtotal (3 items) $50.00". We need to extract the number reliably. A robust parser anchors on the $ sign and refuses to guess when there's no price:

    import re
from decimal import Decimal

_DOLLAR_AMOUNT = re.compile(r"\$\s*(-?\d{1,3}(?:,\d{3})*(?:\.\d+)?)")

def parse_price(text: str) -> Decimal:
    match = _DOLLAR_AMOUNT.search(text)
    if match is None:
        raise ValueError(f"no numeric value found in price text: {text!r}")
    return Decimal(match.group(1).replace(",", ""))

    Don't worry about mastering the regular expression itself yet — that's the subject of Appendix B. What matters here are the two design decisions baked into this tiny function, because both are reusable principles:

    1. Anchor on intent ($), not on position. The pattern requires a literal $, so in "Subtotal (3 items) $50.00" the 3 from "(3 items)" can never be mistaken for the price — the parser locks onto $50.00. A naive "grab the first number" parser would return 3, and every budget comparison downstream would silently use the item count as the price. Anchoring on the meaningful symbol prevents an entire category of subtle bug.

    2. Fail loudly on ambiguity. When there's no $-anchored number at all ("Auction ended", "Time left: 3d 4h"), the function raises ValueError rather than returning 0 or None. Why? Because a parser that invents 0 for garbage spreads a wrong number into your assertions, where it's almost impossible to trace. Raising puts the decision back where the context lives — the caller decides whether to skip that listing or fail the test. (This is the "separate mechanism from policy" idea from Chapter 2, made concrete.)

    Here's the parser working across the formats it must survive:

    parse_price("$25.00")                     # Decimal('25.00')
parse_price("US $1,234.56")               # Decimal('1234.56')   (strips the comma)
parse_price("$25.00 to $30.00")           # Decimal('25.00')     (lower bound of a range)
parse_price("Subtotal (3 items) $50.00")  # Decimal('50.00')     ($ wins over the "3")
parse_price("Time left: 3d 4h")           # raises ValueError     (refuses to guess)

    Interview lens

    Reviewers love this function because it is pure — input text in, Decimal out, no browser, no I/O. "I extracted price parsing into a pure function so I could unit-test 20+ formats in milliseconds without launching a browser" is a strong thing to say. It's also why Chapter 16 on unit testing exists — pure functions are the part of a suite you can test exhaustively and instantly.

    5.4 Context managers: the with statement¶

    The second topic. A context manager is an object that guarantees some setup happens before a block of code and some cleanup happens after it — even if the block raises an exception. You use one with the with keyword, and you'll encounter it in three places in this stack:

    with sync_playwright() as p:        # SETUP: starts the Playwright runtime...
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto("https://example.com")
# ...CLEANUP: stops the runtime here, automatically — even if something above failed

with allure.step("SEARCH"):         # SETUP: opens a labelled report step...
    urls = search.search_items_by_name_under_price(...)
# ...CLEANUP: closes the step here

with open("file.txt") as f:         # SETUP: opens the file...
    data = f.read()
# ...CLEANUP: closes the file handle here, guaranteed

    How it works under the hood: the object after with defines two special methods — __enter__ (run on entry; its return value is what as name captures) and __exit__ (run on the way out, guaranteed, whether the block finished normally or threw). Python calls them for you. (Those are dunder methods again; see Appendix C.)

    Why prefer with over manually cleaning up? Compare:

    # Manual — you must remember the cleanup, and get it right even on exceptions:
f = open("file.txt")
try:
    data = f.read()
finally:
    f.close()        # easy to forget; must be in `finally` to survive exceptions

# Context manager — the resource owns its own cleanup; you cannot forget it:
with open("file.txt") as f:
    data = f.read()

    The with version is shorter, and — more importantly — the cleanup is defined once by the resource itself, not re-typed correctly at every call site. You literally cannot forget it.

    From TypeScript

    with has no long-standing JavaScript equivalent (the newer using declaration is the emerging analogue). Today's JS pattern is try { ... } finally { resource.close(); }. with sync_playwright() as p: is that try/finally, but with the cleanup defined by the resource rather than rewritten at each use.

    Gotcha — a real bug this prevents

    A common mistake (you'll dissect it in Chapter 26) is calling sync_playwright().start() and then never calling .stop(), which leaks a background process. Repeated in CI, the runner eventually exhausts its handles and starts failing mysteriously. Wrapping the runtime in with sync_playwright() as p: fixes the leak by construction — the __exit__ calls .stop() for you, every time, even on error. This is a concrete reason context managers matter for test stability, not just tidiness.

    Exercise 5.1 — feel the float bug, then fix it

    In a Python REPL, evaluate 0.1 + 0.2 == 0.3 (it's False). Now evaluate Decimal("0.1") + Decimal("0.2") == Decimal("0.3") (it's True). Finally, evaluate Decimal(0.1) and read the long imprecise result — that's the float error preserved. Internalise: strings into Decimal, never floats.

    Exercise 5.2 — write a context manager user

    Use with open("notes.txt", "w") as f: to write a line to a file, then read it back with another with open(...). Confirm you never called f.close() yet the file was properly written and closed both times.

    Key idea

    Money is Decimal, and a Decimal is always built from a string, never a float (binary floats can't represent most decimal fractions exactly). Parse prices by anchoring on the meaningful symbol ($) and raising on ambiguity so the caller sets policy. And with (context managers) guarantees setup and cleanup around a block even on exceptions — use it for the Playwright runtime, files, and report steps so cleanup can never be forgotten.
