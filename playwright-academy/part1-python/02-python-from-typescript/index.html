    Chapter 2 — Python Essentials for the Working Programmer¶

    This chapter teaches the Python you need for everything that follows. It assumes you can already program — you know what a variable, a loop, and a function are — but it assumes nothing about Python specifically. Every idiom is explained from the ground up, with several examples, because the small syntactic and semantic differences between Python and other languages are exactly where bugs hide.

    If you happen to know TypeScript or JavaScript, the From TypeScript notes connect each idea to something you already know. If you don't, skip them — the main text stands on its own.

    2.1 The shape of Python code¶

    Let's start with a complete, ordinary function and dissect every part of it:

    def greet(name: str, loud: bool = False) -> str:
    message = f"Hello, {name}"
    if loud:
        message = message.upper()
    return message

    Walking through the unfamiliar pieces, one at a time:

    Blocks are defined by indentation, not braces. There are no { } around the function body or the if body. Instead, the indentation itself — four spaces by convention — tells Python what belongs to what. The colon : at the end of def …: and if …: opens a new indented block. This is not a style preference you can ignore; mis-indenting is a syntax error that stops the program from running.

    if loud:
    message = message.upper()   # indented → inside the if
print(message)                  # not indented → runs always

    Variables are not declared. There is no let, const, or var, and no type keyword in front. You simply assign: message = "Hello". The variable springs into existence on first assignment.

    Type hints are written name: type. In the signature, name: str says "name is expected to be a string," and -> str says "this function returns a string." Hold on to a crucial fact we'll expand in §2.7: Python does not enforce these at run time. They are documentation for humans and tools.

    f"...{expr}..." is an f-string — a string with embedded expressions. Anything in { } is evaluated and inserted: f"Hello, {name}" with name = "Sam" produces "Hello, Sam". You can put any expression inside: f"{2 + 2}" → "4".

    Naming conventions are cultural but near-universal. Functions and variables use snake_case (lowercase with underscores). Classes use PascalCase. Constants use UPPER_SNAKE_CASE. Linters will nag you if you deviate, and other Python programmers will read snake_case as "this is a function or variable" automatically.

    From TypeScript

    No braces (indentation instead); no let/const (just assign); types written after a colon and — unlike TS — not checked at compile time (§2.7). f"{x}" is a template literal `${x}`. snake_case where you'd write camelCase.

    Gotcha — tabs vs spaces

    Mixing tabs and spaces for indentation is a syntax error in Python 3. Configure your editor to insert 4 spaces when you press Tab. Almost every Python editor does this by default, but if you ever see a baffling TabError, this is why.

    2.2 None, truthiness, and the two kinds of equality¶

    Python has a single value representing "nothing here": None. There is no separate null and undefined — just None.

    result = None

    Testing for None: use is¶

    Python has two comparison operators that look similar but mean different things:

    • == asks "are these two values equal?"
    • is asks "are these two the exact same object in memory?" (identity)

    For almost everything, you want ==. The one place you use is is comparing against None, True, and False, because there is only ever one None object in a running program, so identity is the precise, idiomatic check:

    if result is None:        # idiomatic
    ...
if result is not None:    # the negation
    ...

    Truthiness: what counts as "empty"¶

    In a boolean context (if x:, while x:), Python treats certain values as falsy: None, False, 0, 0.0, "" (empty string), [] (empty list), {} (empty dict), and set() (empty set). Everything else is truthy. This enables a very common, readable idiom:

    urls = []
if not urls:              # reads as "if urls is empty"
    print("no results")

if urls:                  # reads as "if urls has anything in it"
    process(urls)

    You will see if not items: continue and return value or default throughout test code, and now you can read them at a glance.

    Gotcha — if x: is NOT if x is not None:

    These two checks are not the same, and confusing them causes real bugs. If x could legitimately be 0 or "", then if x: is False for those values, but if x is not None: is True. Concretely: a price of 0 is a valid price, but if price: would treat it as "missing" and skip it. When zero or empty is a legitimate value, always test is None explicitly. This single distinction separates code that handles edge cases from code that quietly mishandles them.

    From TypeScript

    None ≈ null and undefined merged into one. Python == does not do JavaScript-style type coercion, so it behaves like JS === for primitives. is has no everyday JS equivalent — it's reference identity, closest to Object.is.

    2.3 The four collection types¶

    Python has four built-in containers. You will use all of them.

    List — an ordered, growable sequence¶

    nums = [10, 20, 30]
nums.append(40)        # → [10, 20, 30, 40]
len(nums)              # 4
nums[0]                # 10  (first; zero-indexed)
nums[-1]               # 40  (last; negative counts from the end)
nums[1:3]              # [20, 30]  (a "slice": from index 1 up to, not including, 3)

    The two things most likely to surprise you: negative indices count from the end (nums[-1] is the last element, nums[-2] the second-to-last), and slicing nums[start:stop] returns a new list from start up to but not including stop.

    Dict — key/value pairs¶

    config = {"region": "US", "headless": True}
config["region"]            # "US"
config["currency"] = "USD"  # add or overwrite a key
config.get("missing")       # None  (instead of raising)
config.get("missing", "?")  # "?"   (a default if the key is absent)
"region" in config          # True  (membership test on keys)

    The important nicety: indexing a missing key (config["nope"]) raises an error, whereas config.get("nope") returns None (or a default you supply). Reach for .get() when a key might legitimately be absent.

    Tuple — a fixed, unchangeable sequence¶

    point = (40.7, -74.0)       # parentheses; cannot be modified after creation
point[0]                    # 40.7

    Tuples are used for fixed-size records and for returning several values from a function at once: return ("ok", 200).

    Set — unique members, fast membership¶

    tags = {"smoke", "regression"}   # curly braces, but no key:value → it's a set
"smoke" in tags                  # True  (very fast)
tags.add("smoke")                # no effect; sets ignore duplicates

    Sets shine for "does this collection contain X?" and for de-duplicating.

    Unpacking (destructuring)¶

    Any sequence can be "unpacked" into variables in one line:

    lat, lon = point                 # lat = 40.7, lon = -74.0
first, *rest = [1, 2, 3, 4]      # first = 1, rest = [2, 3, 4]

    From TypeScript

    list ≈ Array; dict ≈ Object/Map (with explicit keys); tuple ≈ a fixed-length readonly tuple; set ≈ Set. nums[-1] and nums[1:3] have no JS syntax equivalent (arr.at(-1) and arr.slice(1,3) are the closest). lat, lon = point is array destructuring [lat, lon] = point.

    2.4 Loops and the all-important comprehension¶

    Python's for loop iterates directly over the items of a collection — there is no C-style for (i = 0; i < n; i++):

    for url in urls:           # `url` takes each value in turn
    print(url)

for i in range(3):         # range(3) yields 0, 1, 2
    print(i)

for i, url in enumerate(urls):    # index AND value together
    print(i, url)

    range(n) produces the numbers 0 to n-1. enumerate(seq) pairs each item with its index — use it instead of manually maintaining a counter.

    The comprehension¶

    This is the single most important Python idiom to be able to read, because well-written Python uses it constantly. A list comprehension builds a new list from an existing iterable, optionally filtering, in one expression:

    labels = ["small", "", "large", ""]
result = [label.upper() for label in labels if label]
# result == ["SMALL", "LARGE"]

    Read it left to right as an English sentence:

    [  label.upper()    for label in labels    if label  ]
   ▲ what to keep    ▲ the loop              ▲ the filter (optional)

    "Take label.upper(), for each label in labels, but only where label is truthy (non-empty)." Let's build one up in stages so the structure is unmistakable:

    [x for x in nums]                 # every element, unchanged → a copy
[x * 2 for x in nums]             # every element, doubled
[x for x in nums if x > 10]       # only elements greater than 10
[x * 2 for x in nums if x > 10]   # doubled, but only the ones over 10

    There are dict and set comprehensions too, with the same structure:

    {s.id: s for s in scenarios}      # dict comprehension: {id → object}
{card.url() for card in cards}    # set comprehension: unique URLs (dedupes)

    Why does Python prefer this over a for loop with .append()? Because it is one self-contained expression, it is faster, and — once you can read it — it states the intent ("a list of the upper-cased non-empty labels") more directly than three lines of loop-and-append.

    From TypeScript

    A comprehension is a fused .filter().map(): [x*2 for x in nums if x>10] ≈ nums.filter(x => x > 10).map(x => x * 2). Python folds both into one expression and considers it the idiomatic default.

    Exercise 2.1 — read and write comprehensions

    First, predict the output of [n for n in range(6) if n % 2 == 0]. Then rewrite this loop as a single comprehension: 

    out = []
for c in cards:
    if not c.is_sponsored():
        out.append(c.url())
    Answers First: [0, 2, 4] (the even numbers under 6). Second: out = [c.url() for c in cards if not c.is_sponsored()].

    2.5 The walrus operator :=¶

    You will meet := ("the walrus," for its eyes-and-tusks shape) in resilient list-building code. Normal assignment with = is a statement and produces no value. The walrus := is an expression: it assigns and hands back the assigned value, so you can both store something and test it in the same breath.

    The motivating example: collect each link's href, but keep only the ones that actually have an href, without fetching it twice:

    return [
    href
    for i in range(links.count())
    if (href := links.nth(i).get_attribute("href"))
]

    Trace what happens for each i: links.nth(i).get_attribute("href") is called once; its result is stored in href; the if then tests whether href is truthy; and if so, that same href is what the comprehension keeps. Without the walrus you would have to call get_attribute once in the if and again in the output expression — slower and easy to get subtly wrong.

    From TypeScript

    No clean equivalent. The closest feel is assigning inside a condition — if ((href = el.getAttribute("href"))) { ... } — which JS allows but lint rules usually forbid. Python deliberately introduced := to make exactly the comprehension pattern above both possible and readable.

    2.6 Functions: defaults, keyword arguments, and variadics¶

    def search(query: str, max_price, limit: int = 5) -> list[str]:
    ...

    Default values. limit: int = 5 gives limit a default, so callers may omit it. Keyword arguments. Any parameter can be passed by name at the call site, which makes calls self-documenting:

    search("shoes", 220)               # limit defaults to 5
search("shoes", 220, 3)            # positional: 3 is `limit` (you must know the order)
search("shoes", 220, limit=3)      # keyword: unmistakable
apply_price_range(max_value=price) # the name tells the reader what `price` is for

    Keyword-only arguments. A bare * in the signature forces everything after it to be passed by name. This prevents a caller from accidentally passing a flag positionally:

    def capture(self, step: str, *, full_page: bool = True):
    ...
capture("cart", full_page=False)   # OK
capture("cart", False)             # TypeError — `full_page` must be named

    Variadic parameters. *args collects extra positional arguments into a tuple, and **kwargs collects extra keyword arguments into a dict. You'll see these most in wrapper functions and decorators (Appendix A):

    def f(*args, **kwargs):
    print(args)      # a tuple of positionals
    print(kwargs)    # a dict of named arguments
f(1, 2, x=3)         # args == (1, 2);  kwargs == {"x": 3}

    Gotcha — never use a mutable default argument

    This is one of Python's most infamous traps: 

    def add(item, items=[]):     # BUG: the default [] is created ONCE, ever
    items.append(item)
    return items
add(1)   # [1]
add(2)   # [1, 2]  ← the SAME list persisted between calls!
    The default list is created a single time when the function is defined, then shared across every call, so it silently accumulates state. The fix is the standard idiom: 
    def add(item, items=None):
    items = items if items is not None else []
    items.append(item)
    return items

    From TypeScript

    limit=5 ≈ a default parameter limit = 5. Keyword arguments are like passing an options object but built into the language. *args/**kwargs ≈ rest parameters (...args) plus an options bag. The mutable-default trap has no TS equivalent — it's a genuinely Python-specific thing to memorize.

    2.7 Type hints are advisory, not enforced¶

    This is the single biggest mental adjustment for programmers arriving from a compiled, statically-typed language, so we'll be explicit about it.

    def price_text(self) -> str:
    return 42        # annotated to return str, actually returns int

    Python will run this happily. The -> str is never checked at run time. The annotations exist for three audiences: human readers, your editor (autocomplete and inline warnings), and optional external type-checkers. To actually verify the hints, you run a separate tool — mypy or pyright — typically as a CI step:

    uv run mypy src/      # reports type mismatches WITHOUT running the program

    So type hints are not worthless — far from it. They make code self-documenting, power your editor, and catch real bugs when you run the checker. But by default they are advice, not law.

    From TypeScript

    In TypeScript, tsc refuses to compile mismatched types and the types vanish at run time. In Python, the types also vanish at run time and are never checked at all unless you opt in with mypy/pyright. So treat hints like JSDoc types that a separate tool can verify if you ask it to — valuable, but advisory by default.

    2.8 Modules, packages, and imports¶

    A single .py file is a module. A folder of modules is a package. You bring names from one module into another with import:

    from ebay_automation.components.home import HomePage   # one specific name
from decimal import Decimal                             # one name from a stdlib module
import re                                               # the whole module; use re.compile(...)
    • from X import Y brings the single name Y into scope.
    • import X brings the whole module; you then access its contents as X.thing.
    • Imports are resolved by package path (dotted names like ebay_automation.db.client), not by relative file path like ../db/client.

    A folder becomes an importable package when it contains an __init__.py file (which may be empty). That file is what lets components/ be imported as ebay_automation.components.

    Finally, you will see this guard at the bottom of runnable scripts:

    if __name__ == "__main__":
    main()

    It means "only run main() when this file is executed directly, not when it is imported by something else." Library modules omit it; scripts you run from the command line include it.

    From TypeScript

    from x import y ≈ import { y } from "x"; import x ≈ import * as x from "x". There is no default export — every import is named. if __name__ == "__main__": is the rough analogue of checking whether a module is the entry point.

    2.9 Exceptions and error handling¶

    Python signals errors by raising exceptions, which you catch with try/except:

    try:
    price = parse_price(text)
except ValueError:
    log.debug("unparseable price; skipping this card")
    return None
finally:
    tab.close()        # runs no matter what — success OR exception
    • raise ValueError("message") throws an exception.
    • except SomeError: catches a specific type. Catch the narrowest type you can — except ValueError: catches only value errors; the catch-all except Exception: hides bugs you didn't anticipate and should be rare.
    • finally: always executes, whether the try body succeeded, raised, or returned. It's the classic place for cleanup like closing a browser tab. (Often a with block, covered in Chapter 5, expresses this even more cleanly.)

    A small but important design point lives in that example: parse_price raises when it can't make sense of the text, and the caller decides what to do about it (here: skip this one card and move on). The function that detects the problem doesn't decide the policy; the caller does. We'll return to this "separate the mechanism from the policy" idea repeatedly.

    Interview lens

    "How would you handle a listing whose price can't be parsed?" → "The parser raises a ValueError rather than guessing a number; the caller catches it, logs at debug level, and skips that single listing instead of failing the whole run. That keeps how to parse and what to do when parsing fails in separate places." This answer quietly demonstrates that you think about error policy, not just error handling.

    Exercise 2.2 — exceptions

    Write a function safe_divide(a, b) that returns a / b, but returns None (and logs a message) if b is 0, using try/except ZeroDivisionError. Then call it with safe_divide(10, 0) and confirm it returns None rather than crashing.

    Key idea

    Indentation defines blocks; None with is; truthiness powers if not items; the comprehension ([expr for x in xs if cond]) is the core idiom to master; := assigns-and-returns inside an expression; keyword arguments make calls self-documenting (and never use a mutable default); type hints are advisory unless you run mypy; imports are by package path; and exceptions separate detecting a problem from deciding what to do about it.
