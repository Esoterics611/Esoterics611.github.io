    Chapter 3 — Object-Oriented Python¶

    The Page Object Model — the architecture at the heart of this course — is applied object-oriented programming. If classes feel shaky, POM will feel like magic incantations. So this chapter builds classes up slowly and concretely, with enough examples that by the end the later architecture chapters read as common sense rather than mystery. We assume you've seen the idea of objects before, but not how Python specifically expresses them.

    3.1 What a class is, and why we want one¶

    A class is a template that bundles together some data (called attributes or fields) and the functions that operate on that data (called methods). An object (or instance) is one concrete thing built from that template.

    Why bundle data and behavior? Because it keeps related things together. Imagine automating a search box. Without a class you'd have a loose selector string here, a "fill the box" function there, a "click submit" function somewhere else — all referring to the same UI element but scattered. A class gathers them into one named unit:

    class HeaderComponent:
    _SEL_SEARCH_NAME = "Search for anything"   # (1) class attribute (shared)

    def __init__(self, page):                  # (2) the constructor
        self.page = page                       # (3) instance attribute (per-object)

    def search(self, query):                   # (4) a method
        self.page.fill(self._SEL_SEARCH_NAME, query)

    Let's name each part, because these four ideas recur on every component you'll write:

    1. A class attribute is defined directly under the class line and is shared by every instance of the class. We use these to hold selector strings — the constant that identifies the search box is the same for every HeaderComponent. (Think of it as a static field.)
    2. __init__ is the constructor: a special method Python runs automatically when you create an instance. ("Dunder" is shorthand for "double underscore"; names like __init__ are special hooks Python calls for you — more in Appendix C.)
    3. self.page = page stores the value passed in as an instance attribute — data that belongs to this particular object. Until you assign something to self.something, it's just a local variable that disappears when __init__ ends.
    4. A method is a function defined inside the class. Its first parameter is always self (explained in §3.2).

    You create and use an instance like this — note there is no new keyword:

    header = HeaderComponent(page)   # this CALLS __init__(self=header, page=page)
header.search("shoes")           # this CALLS search(self=header, query="shoes")

    So HeaderComponent(page) builds an object, runs __init__ to set it up, and hands you back the ready-to-use instance stored in header.

    From TypeScript

    __init__ ≈ constructor. A class attribute ≈ a static readonly field. An instance attribute (self.page) ≈ this.page. The biggest surface difference: Python has no new — you "call the class" directly, HeaderComponent(page).

    3.2 self: the explicit "this"¶

    Every method's first parameter is, by strong convention, named self, and it refers to the specific instance the method was called on. Here is the part that surprises newcomers: you write self in the definition, but you never pass it at the call site — Python supplies it automatically.

    class HeaderComponent:
    def search(self, query):          # you DECLARE self...
        self.page.fill("...", query)

header = HeaderComponent(page)
header.search("shoes")                # ...but you pass only "shoes"; Python sends `header` as self

    When you write header.search("shoes"), Python rewrites it internally as HeaderComponent.search(header, "shoes") — the object before the dot becomes self. That's the whole rule. Inside the method, self.page means "the page belonging to whichever instance this was called on."

    From TypeScript

    self ≈ this, with three improvements: (a) you always declare it explicitly as the first parameter, so there's no ambiguity about where it comes from; (b) you never pass it manually; and (c) it can never be silently rebound the way JavaScript this can when you detach a method — so the entire family of "lost this" bugs simply doesn't exist in Python.

    Gotcha — forgetting self

    If you write def search(query): (no self) and then call header.search("x"), Python raises TypeError: search() takes 1 positional argument but 2 were given. The "2" is confusing until you realise Python passed the instance as a hidden first argument and your signature had no slot for it. Whenever you see that exact error, you forgot self.

    3.3 "Private" by convention: the leading underscore¶

    Python has no private or public keywords. Instead it uses a convention: a name beginning with a single underscore is understood to be internal — "this is an implementation detail; please don't depend on it from outside."

    class HeaderComponent:
    _SEL_SEARCH_NAME = "Search for anything"   # internal: a selector detail
    def search(self, query): ...               # public: part of the API
    def _build_query(self, raw): ...           # internal helper
    • name — public API, safe for others to use.
    • _name — internal; may change without warning; don't rely on it from outside.
    • __name (two underscores) — name-mangled to avoid clashes in subclasses; rarely needed in practice.

    Nothing enforces this — Python won't stop you touching a _name from outside — but every Python programmer and every linter reads the underscore as "hands off." It's a social contract that works remarkably well.

    From TypeScript

    _name ≈ private name, but advisory rather than compiler-enforced. Python's guiding philosophy here is "we're all consenting adults": the underscore signals intent; if you reach past it anyway, you accept the consequences.

    3.4 Inheritance: building on a base class¶

    Inheritance lets one class build on another, reusing its attributes and methods. The classic use in this course is a thin shared base that every UI component extends:

    class BaseComponent:
    def __init__(self, page, root=None):
        self.page = page
        self.root = root if root is not None else page.locator("body")
        self.log = get_logger(self.__class__.__name__)

class ResultCardComponent(BaseComponent):       # (1) inherit from BaseComponent
    def __init__(self, page, root):
        super().__init__(page, root)             # (2) run the base constructor
        # ...any extra setup specific to a result card...
    1. class ResultCardComponent(BaseComponent): declares that a ResultCardComponent is a BaseComponent. It automatically gains everything the base defines — self.page, self.root, self.log — without re-declaring them.
    2. super().__init__(page, root) calls the parent's constructor so the base's setup actually runs. This is easy to forget and important: if you override __init__ in the child and don't call super().__init__(...), then self.page, self.root, and self.log are never set, and the object is half-built. A frequent beginner bug.

    That self.__class__.__name__ line is a small, professional flourish: self.__class__ is the actual runtime class of the object, and .__name__ is its name as a string. So when a ResultCardComponent is running, the base creates a logger labelled "ResultCardComponent" — log lines automatically say which component produced them, with no per-class boilerplate.

    From TypeScript

    class Child(Parent): ≈ class Child extends Parent. super().__init__() ≈ calling super(...) in a constructor. Methods are "virtual" by default — a child method with the same name simply replaces the parent's, with no override keyword needed.

    3.5 Composition: building with parts (usually the better default)¶

    Inheritance models an is-a relationship ("a result card is a component"). Composition models a has-a relationship ("a home page has a header") and is usually the better tool for assembling behaviour. Real pages use both, deliberately:

    class HomePage(BaseComponent):                      # IS-A component (inheritance)
    def __init__(self, page):
        super().__init__(page)
        self.header = HeaderComponent(page)         # HAS-A header (composition)
        self.cookie_banner = CookieBannerComponent(page)  # HAS-A cookie banner

    HomePage is a BaseComponent, so it gets logging and the scoped-locator helper for free. And it has a HeaderComponent and a CookieBannerComponent, so you can write:

    home = HomePage(page)
home.header.search("shoes")        # reach into the composed header
home.cookie_banner.accept()        # reach into the composed banner

    This mirrors how a real page is actually built: a page is made of regions. Composition lets the same HeaderComponent be reused on the home page, the search-results page, the item page — written once, plugged in everywhere.

    Interview lens

    "Inheritance or composition for page objects?" → "Inherit from a thin base for shared plumbing — logging, a scoped-locator helper — and compose sub-components for the page's regions. Deep inheritance between pages is a smell, because pages don't have a clean is-a relationship with each other, but they clearly have regions. So: inherit the plumbing, compose the parts." Knowing when to prefer composition is a senior-level signal; reciting "inheritance good" is not.

    3.6 @property: a method that reads like an attribute¶

    Sometimes you want a value that is computed on demand but reads like a plain field. The @property decorator turns a method into exactly that — a read-only, computed attribute accessed without parentheses:

    class SearchResultsPage(BaseComponent):
    @property
    def cards(self):
        return self.page.locator("ul.srp-results > li.s-item")

results = SearchResultsPage(page)
results.cards          # NO () — looks like a field, but runs the method each time
results.cards.first    # chain straight onto the result

    Without @property you'd write results.cards() with parentheses; with it, the access reads as a noun — results.cards, header.search_input — which is how we think about these things. The method still runs fresh on every access, so the locator is always current.

    (@property is a decorator. We give decorators their own thorough treatment in §3.7 and Appendix A; for now, just read @property as "make this method behave like a getter.")

    From TypeScript

    @property ≈ a get cards() getter: accessed without (), computed behind the scenes.

    3.7 Decorators — the short version¶

    A decorator is a function that wraps another function or class to add behaviour, written with @name on the line directly above a def or class:

    @property                 # turns a method into a getter
def cards(self): ...

@dataclass(frozen=True)   # auto-generates a constructor, equality, immutability
class Scenario: ...

@pytest.fixture           # marks a function as a test-dependency provider
def db(): ...

    The mental shortcut: @thing above a definition means "pass this definition through thing and use whatever comes back." You will use decorators long before you ever write one, and that's perfectly fine. Because they come up so often — and because "explain a decorator" is a classic interview question — they get a full, build-it-from- scratch treatment in Appendix A — Decorators, which you should read after Part I.

    From TypeScript

    Python decorators resemble TS decorators (@Component, @Injectable), and the @pytest.fixture dependency-injection pattern will feel a lot like Angular/NestJS providers — though Python decorators are just plain functions, simpler than TS's.

    3.8 @dataclass: typed records without the boilerplate¶

    Storing a few fields on an object normally means writing a repetitive __init__ (self.id = id, self.query = query, …). A dataclass writes that constructor for you — plus equality and a readable string form — from nothing more than typed field declarations:

    from dataclasses import dataclass, field
from decimal import Decimal

@dataclass(frozen=True)            # (1)
class Scenario:
    id: str
    query: str
    max_price: Decimal
    limit: int
    allow_partial: bool
    min_results: int = 1                            # (2) field with a default
    tags: list[str] = field(default_factory=list)   # (3) mutable default — special!
    1. frozen=True makes instances immutable: after construction, scenario.limit = 9 raises an error. This is perfect for configuration and test data that should never change mid-run — it turns "someone accidentally mutated the config" into an immediate, loud failure.
    2. Fields with defaults must come after fields without them (the same rule as function parameters).
    3. For a mutable default like a list or dict, you must use field(default_factory=list) rather than a bare = []. This is the exact same trap as the mutable-default-argument gotcha from Chapter 2: a bare [] would be created once and silently shared across every instance. default_factory=list instead creates a fresh empty list per instance.

    What you get for those few lines:

    s = Scenario(id="x", query="shoes", max_price=Decimal("220"),
             limit=5, allow_partial=True)
s.query                    # "shoes"
s.tags                     # []  (its own fresh list)
print(s)                   # Scenario(id='x', query='shoes', ...)  ← readable repr
s == Scenario(id="x", ...) # value equality, generated for you

    The auto-generated __repr__ (the readable form) is a real gift in test output: when an assertion fails, the failure log prints the whole object legibly instead of <Scenario object at 0x7f…>.

    From TypeScript

    @dataclass(frozen=True) ≈ a readonly interface plus an auto-generated constructor and structural equality. It's what you reach for instead of hand-writing a class with five this.x = x lines — "a class that behaves like a typed record."

    Interview lens

    "How do you model test data or configuration?" → "Frozen dataclasses. They give me typed fields, immutability so config can't be mutated mid-run, value equality, and a readable repr in failure logs — all without boilerplate. And I parse fields like money into Decimal at load time (Chapter 21) so the rest of the code is type-safe."

    Exercise 3.1 — write a small class

    Write a class Cart whose __init__ stores an empty list self.items. Give it an add(self, name, price) method that appends a (name, price) tuple, and a total(self) method that returns the sum of the prices. Create one, add two items, and print the total. (You've now written instance state and behaviour.)

    Exercise 3.2 — inheritance and super()

    Make a BaseThing with __init__(self, name) that sets self.name. Make a Widget(BaseThing) whose __init__(self, name, size) calls super().__init__(name) and then sets self.size. Create a Widget and print both attributes. Then delete the super().__init__(name) line and observe the AttributeError when you access self.name — that's the "forgot to call super" bug, made visible.

    Key idea

    A class bundles state (self.x, set in __init__) with behaviour (methods, whose first parameter is the explicit self). Inherit a thin base for shared plumbing; compose sub-objects for a page's regions. A leading underscore marks "internal." @property makes a computed getter; @dataclass(frozen=True) makes an immutable typed record. These are the entire structural vocabulary of the Page Object Model.
