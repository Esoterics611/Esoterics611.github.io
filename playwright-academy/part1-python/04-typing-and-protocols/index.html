    Chapter 4 — Typing, Generics & Protocols¶

    Chapter 2 established that type hints in Python are advisory — documentation that a separate tool can check, not rules the interpreter enforces. This chapter goes deeper: how to write hints for the situations that actually come up in test code, and one idea — Protocol — that is genuinely powerful, that underpins a beautifully decoupled piece of the reference project, and that comes up in senior interviews. We build everything from the notation up; no prior typing experience is assumed.

    4.1 The notation, reviewed and extended¶

    A type hint is written after a colon for variables and parameters, and after an arrow for return values:

    name: str = "shoes"               # a variable, hinted as a string
prices: list[Decimal] = []        # a list of Decimals
config: dict[str, int] = {}       # a dict mapping strings to ints

def search(query: str, max_price: Decimal, limit: int = 5) -> list[str]:
    ...                           # takes those types; returns a list of strings

    The bracket syntax describes containers and what's inside them:

    Hint Meaning
    list[str] a list whose elements are strings
    dict[str, int] a dict with string keys and int values
    tuple[str, int] a 2-tuple of a string then an int
    set[str] a set of strings
    list[Decimal] a list of Decimal values

    On Python 3.11+ you use the lowercase built-in names (list, dict, tuple, set) directly. Older code imports capitalised versions (List, Dict) from a module called typing; you may see those, but prefer the lowercase forms in new code.

    4.2 Optional values: X | None¶

    Constantly in test code, a lookup might find nothing — an element with no href, a config key that's absent. The type for "an X, or nothing" is written X | None:

    def url(self) -> str | None:        # might find an href, might not
    href = self.root.get_by_role("link").first.get_attribute("href")
    return href or None             # return the href, or None if it was empty/missing

    The | reads as "or," so str | None is "a string or None." This shows up most often in two places:

    # 1. Return types of lookups that can come up empty:
def find_price(self) -> Decimal | None: ...

# 2. Optional parameters that default to "nothing":
def __init__(self, page: Page, root: Locator | None = None) -> None:
    ...

    That second line is the signature of every component in the reference project: "you may hand me a root locator to scope me, or omit it (in which case root is None and I fall back to a default)." We'll see exactly how that's used in Chapter 19.

    From TypeScript

    str | None is identical to TS string | null. Locator | None = None ≈ root: Locator | null = null. Older Python wrote Optional[str] (imported from typing); str | None is the modern, equivalent spelling — prefer it.

    4.3 Generics: code that works for any type while remembering which¶

    Sometimes a function should work for any element type but still report the right type back. Consider a "give me the first element" helper. It should work on a list of ints (returning an int) or a list of strings (returning a string). A generic expresses "whatever type goes in, that same type comes out."

    In Python you introduce a type variable with TypeVar, then use it as a stand-in type:

    from typing import TypeVar

T = TypeVar("T")                  # T is a placeholder for "some type"

def first(items: list[T]) -> T:   # takes a list of T, returns one T
    return items[0]

first([1, 2, 3])        # T is inferred as int  → returns an int
first(["a", "b"])       # T is inferred as str  → returns a str

    The single T ties the input and output together: whatever element type the list has, that's what first returns. A type-checker now knows first([1,2,3]) is an int, catching mistakes like first([1,2,3]).upper() (you can't .upper() an int).

    The reference project's paginator is generic over the type of thing it collects:

    def collect_until(..., collect_fn: Callable[[_Pageable], list[T]], ...) -> list[T]:

    It accumulates a list[T] and returns a list[T], where T is whatever the collector function produces — here, str URLs, but it could be anything. So one paginator works for collecting URLs, or product objects, or rows of a table, with no changes. (Callable and _Pageable are explained next.)

    From TypeScript

    T = TypeVar("T") then using T ≈ declaring a generic <T> on a function. Python spells the type parameter as a module-level variable instead of inline angle brackets, but the meaning is the same: "preserve whatever type the caller used."

    4.4 Callable: typing a function you pass around¶

    In Python, functions are values you can pass as arguments (we saw this in Chapter 2 and it's the basis of decorators). When a function accepts another function, you type that parameter with Callable:

    from typing import Callable

# "a function that takes a SearchResultsPage and returns a list of strings":
collect_fn: Callable[[SearchResultsPage], list[str]]

    The shape is Callable[[ArgType1, ArgType2, ...], ReturnType] — a list of the argument types, then the return type. Passing functions as values is what lets the paginator stay ignorant of what it's collecting: the caller hands it a small function describing how to gather one page's worth of items.

    Those small inline functions are often written as a lambda — an anonymous, single-expression function:

    collect_fn=lambda r: self._collect_card_urls(r, max_price)
#          ▲ parameter  ▲ the single expression it returns

    lambda r: <expr> is a function taking r and returning <expr>. It's used for short, throwaway functions where a full def would be overkill.

    From TypeScript

    Callable[[Arg], Ret] ≈ a function type (arg: Arg) => Ret. A lambda r: expr ≈ an arrow function (r) => expr. Same concepts, different spelling.

    4.5 Protocol: the star of the chapter (structural typing)¶

    This is the idea worth real attention. It's what makes the paginator elegant, and being able to explain it cleanly is a strong interview signal.

    Two ways a type can "match"¶

    There are two philosophies for deciding whether some object satisfies a type:

    • Nominal typing (Python's classic default): an object matches a type only if its class explicitly says it does — e.g. by inheriting from it. The name of the relationship is what counts.
    • Structural typing: an object matches a type if it has the right shape — the right methods and attributes — regardless of what it inherits from. "If it walks like a duck and quacks like a duck, it's a duck."

    Protocol brings structural typing to Python. You declare a Protocol describing the shape you need, and any object with that shape satisfies it — no inheritance required.

    A worked example¶

    The paginator needs to "advance through pages." It doesn't care what it's paging — a search-results page, an orders list, anything — only that the thing can tell it whether there's a next page and can go to it. So we describe exactly that capability:

    from typing import Protocol

class _Pageable(Protocol):
    def has_next_page(self) -> bool: ...      # "...": no body needed; this is just a shape
    def go_to_next_page(self) -> None: ...

def collect_until(component: _Pageable, ...):
    ...
    if not component.has_next_page():
        break
    component.go_to_next_page()

    Now look at SearchResultsPage. It happens to have both methods:

    class SearchResultsPage(BaseComponent):
    def has_next_page(self) -> bool: ...
    def go_to_next_page(self) -> None: ...

    Crucially, SearchResultsPage does not inherit from _Pageable and never mentions it. But because it has the right shape — both required methods, with matching signatures — a type-checker accepts it anywhere a _Pageable is expected. That's structural typing in action.

    Pictured, the relationship looks like this — note the dashed arrow, signalling that SearchResultsPage matches _Pageable by shape, not by inheritance:

    flowchart LR
    P["_Pageable (Protocol)<br/>• has_next_page()<br/>• go_to_next_page()"]
    S["SearchResultsPage<br/>• has_next_page() ✓<br/>• go_to_next_page() ✓<br/>(does NOT inherit from _Pageable)"]
    C["collect_until()<br/>(the paginator)"]
    S -. matches by shape .-> P
    C -- depends on --> P

    Why this is good design, not just clever¶

    • The paginator depends on a capability, not a class. It knows nothing about SearchResultsPage, eBay, or search results — only "something I can ask for a next page and tell to advance." That's a tiny, honest dependency.
    • Future pages satisfy it for free. A reviews list, an order-history page — any class that grows those two methods works with the paginator instantly, with zero changes to the paginator.
    • It is the Dependency Inversion Principle (the "D" of SOLID, Chapter 17) captured in one small construct: the high-level paginator and the low-level page both depend on an abstraction (_Pageable), not on each other.

    From TypeScript

    Protocol ≈ a TypeScript interface used structurally. In TS, an object satisfies an interface just by having the right members — you don't write implements. SearchResultsPage "implements" _Pageable exactly that way: by shape, not by declaration. If you've ever passed a plain object to a function expecting an interface in TS, you already understand Protocol.

    Interview lens

    Being able to say "the paginator accepts a Protocol, so it's decoupled from any concrete page — that's dependency inversion" demonstrates three things at once: you understand Python's typing, you know SOLID, and you design for reuse. It's a genuinely senior sentence — understand it well enough to say it in your own words.

    4.6 Making the hints real: running a type-checker¶

    Because hints do nothing at run time, they only catch bugs if you run a checker. The two common ones are mypy and pyright:

    uv run mypy src/      # analyses types statically, reports mismatches, runs nothing

    Wire this into CI and a whole class of bugs — passing the wrong type, forgetting a None check, returning the wrong shape — is caught before code merges. A common, pragmatic policy is to type-check src/ strictly and be more relaxed in tests.

    Exercise 4.1 — write a Protocol

    Define a Protocol named Closable with a single method close(self) -> None. Write a function close_all(items: list[Closable]) -> None that calls .close() on each. Then create two unrelated classes — File and Connection — each with a close method, put instances of both in one list, and pass it to close_all. Note that neither class inherits from Closable, yet both satisfy it by shape. You've just used structural typing.

    Key idea

    Use X | None for "maybe nothing"; TypeVar + list[T] for generics that preserve the caller's type; Callable[[A], R] for function parameters (often supplied as a lambda); and — the centrepiece — Protocol for structural typing, which lets a utility like the paginator depend on a shape rather than a concrete class. That decoupling is the Dependency Inversion Principle you can point to in real code.
