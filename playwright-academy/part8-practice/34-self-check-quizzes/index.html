    Chapter 34 — Self-Check Quizzes¶

    Use these to test recall and to rehearse interview answers out loud. Try to answer before expanding each solution. If an answer doesn't come quickly, that's the chapter to revisit — each answer links back to it. Aim to answer in your own words, not verbatim.

    Part I — Python¶

    1. Why must money be a Decimal, and what's the one rule when constructing one?

    Floats are binary and can't represent most decimal fractions exactly, so 0.1 + 0.2 != 0.3, which causes false pass/fail on budget comparisons. Decimal is exact base-10 — but only if you build it from a string (Decimal("0.1")), never a float (Decimal(0.1) preserves the float error). (Chapter 5)

    2. What is a Protocol, and why does the paginator use one?

    A Protocol is structural typing: a class satisfies it by having the right shape (methods), not by inheriting from it. The paginator depends on _Pageable (just has_next_page and go_to_next_page), so it's decoupled from any concrete page — that's dependency inversion, and it makes the paginator reusable for any paginated list. (Chapter 4)

    3. is vs ==, and when does if x: differ from if x is not None:?

    is checks identity (same object); == checks value equality. Use is only for None/True/False. They differ when x could be 0 or "": if x: is False for those, but if x is not None: is True. So when zero/empty is a valid value, test is None explicitly. (Chapter 2)

    4. Explain a decorator in one sentence, and what @d desugars to.

    A decorator is a function that takes a function (or class) and returns a replacement; @d above a definition means name = d(name). (Appendix A)

    Part II — Playwright core¶

    5. Why is time.sleep an anti-pattern, and what replaces it?

    It's simultaneously too slow (always burns the full duration) and too flaky (fails when a slow runner needs longer). Actions auto-wait for actionability; expect() retries assertions; bounded wait_for(state=...) handles genuine probes. (Chapter 7)

    6. What's the difference between a browser, a context, and a page — and which is the isolation boundary?

    A browser is one expensive launched process (reused). A context is a cheap, isolated session (own cookies/storage) — the isolation and parallelism boundary. A page is a tab within a context. (Chapter 6)

    7. What is strict mode, and how should you resolve a violation?

    If a locator matches more than one element, an action throws instead of guessing — turning a silent wrong-click into an immediate error. Resolve it by making the locator more specific (add an accessible name), not by reflexively appending .first. (Chapter 7)

    8. State the locator priority order and the principle behind it.

    Role/label → text/placeholder → test-id → CSS (with comma fallbacks) → XPath last. The principle: locate the way a user perceives the page (roles, labels, text), not the way a developer built it (classes, positions), because the former is stable and the latter is implementation detail. (Chapter 8)

    9. Name the two things XPath can do that CSS can't, and one thing to never put in an XPath.

    XPath can match by text and walk to a parent/ancestor/sibling. Never put positional indices (li[3]) in it, because sites reorder elements per visitor. (Chapter 9)

    Part III — pytest¶

    10. What is a fixture, and what does 'scope' control?

    A fixture is a function that provides a dependency, requested by naming it as a parameter (dependency injection); fixtures compose into a graph pytest resolves. Scope controls how often it's built — function (default, per test) up to session (once per run) — trading isolation for speed. (Chapter 13)

    11. How would you make a suite data-driven from an external file?

    Store rows in YAML, load them into typed (frozen) dataclasses at the boundary (money → Decimal), and use pytest_generate_tests to parametrize the test from those rows filtered by tag — so adding a case is a YAML edit with no code change. (Chapter 14)

    12. Why have unit tests if you already have end-to-end tests?

    Unit tests are fast (milliseconds), precise (name the exact failing input), and not flaky. They catch logic regressions an e2e test would either miss or report vaguely after 30 seconds. They're possible because logic is extracted into pure functions. Many fast unit tests, few slow e2e — the pyramid. (Chapter 16)

    13. Why organise tests by marker rather than by folder, and how does parallelism stay safe?

    A marker makes a test's role/speed a property of the test itself (and a test can carry several), selectable with -m. Parallelism (xdist) is safe because each test gets its own isolated context, so there's no shared mutable state to corrupt. (Chapter 15)

    Part IV — Architecture¶

    14. THE big one: why have a service layer on top of page objects?

    Flows span multiple pages and own business logic (pagination, filtering, money math). In a test that logic duplicates across suites; in a page object it gives the object a second reason to change (SRP violation). A service is the single home for cross-page flow and policy, so components stay markup-only and tests stay assertion-only. (Chapter 20)

    15. Why is 'skip sponsored listings' in the service, not the component?

    It's policy (what to do), which changes for different reasons than the markup the component owns. The component only reports (is_sponsored()); the service decides to skip. Mechanism in the component, policy in the service. (Chapter 17)

    16. How do you stop fifty identical result cards from colliding in locators?

    Each card is its own component scoped to a root locator (cards.nth(i)), and all its queries go through self.locator(), which resolves relative to that root — so each component only ever sees its own subtree. (Chapter 19)

    17. Should a page object contain assertions? Where do hardcoded URLs live?

    No — page objects return domain values; tests assert. There are no hardcoded URLs: base_url lives in the profile and is set on the context, so tests navigate by path, and PROFILE switches environments. (Chapter 18, Chapter 21)

    Part V — Robustness, reporting, review¶

    18. Give three techniques for making locators resilient on a volatile site.

    Locate by identity not position; use CSS comma-fallbacks ([data-testid=x], .x) for markup variants; use anchored regex names for labels with dynamic parts (re.compile(r"^Cart")). (Also: idempotent probes for conditional UI, defensive parsing, logged skip-and-continue.) (Chapter 22)

    19. How do you debug a flaky CI failure you can't reproduce locally?

    Capture a trace on failure (--tracing=retain-on-failure), download the trace.zip artifact, and open it with playwright show-trace — it gives before/after DOM snapshots, network, and console for every action, so you see the exact state when the locator failed. (Chapter 24)

    20. Why upload CI artifacts even on failed runs, and how?

    A failed run is when you most need the evidence. Let the test step continue-on-error: true and gate the artifact upload on if: always(), so the report, traces, and screenshots are produced for red builds too. (Chapter 25)

    21. The buggy AI snippet 'passes' — what's its single worst problem?

    It has no assertions — it builds a locator and verifies nothing, so it can't fail on a real bug. (Then: brittle locators, time.sleep, a stray Selenium import + leaked runtime, and manual Playwright in a pytest function.) Lead with impact: no assertions first. (Chapter 26)

    Part VII — Beyond the basics¶

    22. When should you mock the network, and when should you NOT?

    Mock for states the real backend can't easily produce (errors, empty results, slow responses) and to block third-party noise. Don't mock the integration the test is meant to verify — a fully-mocked 'e2e' test can pass while the real system is broken. (Chapter 29)

    23. What's the high-value pattern for setting up complex UI-test preconditions?

    Arrange state via the API (APIRequestContext), not by driving the UI — it's faster, more reliable, and keeps the test focused on what it's actually verifying. Then assert via the UI. You can even authenticate via API once and share the session with the browser. (Chapter 30)

    24. Which 'visual/structural' assertions exist in Python, and which is JS-only?

    Python has aria snapshots (to_match_aria_snapshot) for asserting the accessibility tree, and role-based locators give partial a11y coverage; full WCAG auditing needs axe (a separate library). Pixel to_have_screenshot is JavaScript-runner-only — in Python you capture with page.screenshot() and diff via a plugin. (Soft assertions are likewise JS-only.) (Chapter 31, Chapter 32)

    25. What's the right way to use playwright codegen?

    As a first draft generator: record a flow to get correct role-based locators quickly, then refactor that into your component/service architecture. Never ship raw codegen output as your test. (Chapter 32)

    Key idea

    If you can answer all 25 of these in your own words, you can hold your own in a senior Playwright/Python interview. The ones to over-prepare: #14 (why a service layer), #9/the XPath defence, #19 (trace viewer), and #22 (when not to mock) — these are where judgment shows. Anything you stumbled on points straight at the chapter to re-read.
