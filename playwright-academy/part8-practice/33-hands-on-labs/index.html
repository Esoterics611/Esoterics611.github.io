    Chapter 33 — Hands-On Labs¶

    Reading teaches recognition; building teaches understanding. These labs take you from a single passing test to a small, properly-layered framework, using free public practice sites. Do them in order — each builds on the last. Every lab states a goal, gives staged hints, and hides a solution sketch you should only open after attempting it.

    Practice sites used here

    • https://playwright.dev — stable docs site, good for locators and assertions.
    • https://www.saucedemo.com — a demo shop with login, products, and a cart (great for POM).
    • https://demo.playwright.dev/api-mocking — a tiny app that calls a JSON API (for mocking).
    • https://the-internet.herokuapp.com — many isolated UI challenge pages.

    Set up a fresh project first (uv init, uv add playwright, uv add --dev pytest pytest-playwright, uv run playwright install chromium) as in Chapter 1.

    Lab 1 — Your first robust test (Chapters 7, 8, 10)¶

    Goal. Write a test that searches playwright.dev and verifies results appear, using only role/text locators and web-first assertions — no time.sleep, no CSS classes.

    Steps. 1. Navigate to https://playwright.dev. 2. Open the search (press the search button/icon), type "locator". 3. Assert that a results listbox becomes visible and that the first result contains "locator".

    Hints
    • The search trigger is a button; the input is a searchbox/textbox. Use get_by_role.
    • For the results, assert with expect(...).to_be_visible() — never assert is_visible().
    Solution sketch 

    from playwright.sync_api import Page, expect

def test_search_docs(page: Page):
    page.goto("https://playwright.dev")
    page.get_by_role("button", name="Search").click()
    page.get_by_role("searchbox").fill("locator")
    results = page.get_by_role("listbox")
    expect(results).to_be_visible()
    expect(results.get_by_role("option").first).to_contain_text("locator", ignore_case=True)
    What you practised: role locators, auto-waiting, web-first assertions. If a site's exact roles differ, use playwright codegen (Chapter 32) to discover them — then keep the role-based result.

    Lab 2 — A pure function and its unit tests (Chapters 5, 16)¶

    Goal. Write and exhaustively unit-test a pure parse_price function — no browser at all.

    Steps. 1. Write parse_price(text: str) -> Decimal that anchors on $, handles thousands commas, takes the lower bound of a range, and raises ValueError on garbage. 2. Write parametrized tests covering: plain, US-prefixed, thousands, a range, the "(3 items) $50" trap, and several unparseable inputs.

    Hints
    • Reuse the regex from Chapter 5: re.compile(r"\$\s*(-?\d{1,3}(?:,\d{3})*(?:\.\d+)?)").
    • Build the Decimal from a string (match.group(1).replace(",", "")), never a float.
    • Use @pytest.mark.parametrize for the valid cases and pytest.raises for the garbage.
    Solution sketch

    See Chapter 16 §16.3 for the parser and the full parametrized test. What you practised: purity, Decimal correctness, parametrization, and the test-pyramid principle — these ~20 tests run in well under a tenth of a second with no browser.

    Lab 3 — Refactor into a Page Object (Chapters 18, 19)¶

    Goal. Log in to saucedemo.com and assert you reach the products page — first as a scrappy test, then refactored into a LoginPage component owning the selectors.

    Steps. 1. Write a working but "ugly" test: raw page.fill/page.click with selectors inline. 2. Create a LoginPage(BaseComponent) with _SEL_ constants and a login(username, password) method; add an is_logged_in() query returning a bool. 3. Rewrite the test to use it. Confirm the test body now contains zero selectors.

    Hints
    • Standard saucedemo creds are shown on its login page (e.g. standard_user / secret_sauce).
    • login() should do (fill + click); a separate method should report state (return a bool) — keep doing and reporting separate.
    Solution sketch 

    class LoginPage(BaseComponent):
    _SEL_USER = "Username"
    _SEL_PASS = "Password"
    _SEL_SUBMIT = "Login"
    def login(self, username: str, password: str) -> None:
        self.page.get_by_placeholder(self._SEL_USER).fill(username)
        self.page.get_by_placeholder(self._SEL_PASS).fill(password)
        self.page.get_by_role("button", name=self._SEL_SUBMIT).click()
    def is_on_products(self) -> bool:
        return self.page.get_by_text("Products").is_visible()
    What you practised: hiding selectors behind intent, _SEL_ constants, separating action (login) from query (is_on_products). Note the page object has no assertions — the test asserts on is_on_products().

    Lab 4 — Add a service layer (Chapters 17, 20)¶

    Goal. On saucedemo, build a flow that spans pages — log in, add the two cheapest products to the cart, and return the cart count — and put that flow in a service, not a page object.

    Steps. 1. Add a ProductsPage component that can list product (name, price) pairs and add a product to the cart by name. 2. Write a ShoppingService whose constructor takes the page, composes LoginPage and ProductsPage, and has add_cheapest(n) returning the names added. 3. Write a test that logs in, calls add_cheapest(2), and asserts the cart badge shows 2.

    Hints
    • "The two cheapest" is a policy decision (sort by price, take the first two) — that belongs in the service, not in ProductsPage. The page object only reports prices.
    • Parse prices into Decimal (Lab 2's function) before sorting.
    Solution sketch

    The service sorts the page's reported (name, Decimal) pairs, slices the cheapest n, and calls products.add_to_cart(name) for each. What you practised: the mechanism/policy split — the component reports prices (mechanism), the service decides which to add (policy) — and a service composing multiple components. This is the Chapter 20 pattern in miniature.

    Lab 5 — Data-drive it (Chapters 13, 14)¶

    Goal. Turn Lab 4's test into a data-driven one, with login credentials and the expected outcome loaded from a YAML file via fixtures.

    Steps. 1. Create users.yaml with a few users (standard_user should succeed; locked_out_user should be blocked). 2. Load it in conftest.py and use pytest_generate_tests to parametrize a test_login(scenario). 3. Each case asserts success or the expected error, per its expect_ok field.

    Hints
    • Model each row as a frozen dataclass; parse it at load (Chapter 21 pattern).
    • pytest_generate_tests(metafunc) should check if "scenario" in metafunc.fixturenames.
    Solution sketch

    See Chapter 14 §14.4 for the pytest_generate_tests shape. What you practised: external data, typed loading, and generating one test per row — adding a user becomes a YAML edit, not a code change.

    Lab 6 — Mock an error state (Chapter 29)¶

    Goal. On demo.playwright.dev/api-mocking, force the fruit API to return an empty list and an error, and assert the UI handles each.

    Steps. 1. Use page.route("*/**/api/v1/fruits", handler) to route.fulfill(json=[]) and assert the UI shows no fruit. 2. In a second test, route.fulfill(status=500, json={"error": "boom"}) and assert the UI's error handling (or simply that the known fruit does not appear).

    Solution sketch

    See Chapter 29 §29.2. What you practised: controlling the network to test states a real backend won't reliably produce — and doing so deterministically.

    Lab 7 — Mock three states of a real API (Chapter 29)¶

    Goal. Against https://demo.playwright.dev/api-mocking, write three tests that force the fruit API into three different states and assert how the UI handles each: empty, server error, and a slow response.

    Steps. 1. Test A — fulfil with an empty JSON array; assert no fruit names appear. 2. Test B — fulfil with status=500; assert an error region/message becomes visible. 3. Test C — use a real route.fetch() then call time.sleep(0.0) inside the handler (or use page.route with a delayed response via a separate technique) — at minimum, log how long the page took to render with the slow mock. (For a true delay you can implement it in the handler.)

    Hints
    • Use route.fulfill(json=[]) for the empty case and route.fulfill(status=500, json={"error": "boom"}) for the error case.
    • For "slow," your handler can import time; time.sleep(2) inside the handler — Playwright will simply not respond to the page until the handler returns. (Beware: this slows the test by ~2s too; that's the point of exercising the slow case in isolation.)
    Solution sketch

    Each test installs a page.route("*/**/api/v1/fruits", handler) before page.goto(...), then asserts the UI state with expect(). Same locators, three different controlled backends. What you practised: deterministic testing of states the live backend won't reliably produce.

    Lab 8 — Use the API client (Chapter 30)¶

    Goal. Use playwright.request.new_context to exercise a public REST API directly — no browser.

    Steps. 1. Build an APIRequestContext for https://jsonplaceholder.typicode.com in a session-scoped fixture, with extra_http_headers={"Content-Type": "application/json"}. 2. Write a test that POSTs {"title": "lab", "body": "hi", "userId": 1} to /posts and asserts response.ok and that the parsed json() echoes back the title. 3. Write a second test that GETs /posts/1 and asserts the JSON has a non-empty title.

    Hints
    • JSONPlaceholder is a sandbox — it doesn't really persist anything, but it responds correctly, which is what you need to practise the API client.
    • request_context.dispose() after the yield in your fixture.
    Solution sketch 

    @pytest.fixture(scope="session")
def api(playwright):
    ctx = playwright.request.new_context(base_url="https://jsonplaceholder.typicode.com")
    yield ctx
    ctx.dispose()

def test_create_post(api):
    r = api.post("/posts", data={"title": "lab", "body": "hi", "userId": 1})
    assert r.ok
    assert r.json()["title"] == "lab"
    What you practised: the standalone API client. The next step in real work — covered in Chapter 30 — is to combine an API setup with a UI assertion on an app you own, where the API actually persists.

    Lab 9 — Assert structure with an aria snapshot (Chapter 31)¶

    Goal. On playwright.dev, capture an aria snapshot of the page header and use it as an assertion.

    Steps. 1. Navigate to https://playwright.dev. 2. Print page.get_by_role("banner").aria_snapshot() to see the YAML structure. 3. Trim that YAML to just the structural elements you care about (a couple of nav links) and feed it into expect(...).to_match_aria_snapshot(...). Confirm the test passes (partial matching is the default). 4. Add a deliberately wrong line (a link that doesn't exist) and watch the assertion fail.

    Solution sketch 

    expect(page.get_by_role("banner")).to_match_aria_snapshot("""
  - banner:
    - link "Playwright"
    - navigation:
      - link "Docs"
""")
    What you practised: asserting page structure (meaning) rather than appearance — far more stable than pixel-diffing.

    Lab 10 — Codegen, then refactor (Chapter 32)¶

    Goal. Use the recorder to draft a test quickly, then refactor it into a Page Object — the correct codegen workflow.

    Steps. 1. Run playwright codegen --target python-pytest https://www.saucedemo.com. In the browser, log in (e.g. standard_user / secret_sauce) and click a product. 2. Copy the generated Python into a new test file and run it; confirm it passes. 3. Refactor: move every selector into LoginPage/ProductsPage components with _SEL_ constants; keep the test body free of selectors. Re-run; still passes.

    Solution sketch

    The point isn't the specific selectors codegen produced — they'll vary — it's the refactor. Your final test should look like LoginPage(page).login("standard_user", "secret_sauce"); ProductsPage(page).click("Sauce Labs Backpack"); expect(...).to_be_visible(). What you practised: using codegen as a first draft, then applying architecture. Never ship raw codegen output.

    Lab 11 — Drive the Trace Viewer (Chapter 24)¶

    Goal. Capture and replay a trace, so the tool isn't unfamiliar the first time a CI failure hands you one.

    Steps. 1. Write any small test that navigates and clicks. Force a failure by changing one locator to something that doesn't exist (e.g. page.get_by_role("button", name="Does Not Exist").click()). 2. Run it with uv run pytest --tracing=on. Locate the produced trace.zip under test-results/. 3. Open it: uv run playwright show-trace test-results/.../trace.zip. Step through the timeline, hover an action, and inspect the before/after DOM snapshot. Read the network and console panels.

    What to notice

    The before/after snapshots are the magic — they let you see the DOM state at the exact moment the locator failed, so you can tell whether it was a timing problem, a markup change, or just-wrong text. That capability is why "capture a trace on failure in CI" is the senior debugging answer.

    Lab 12 — Review the AI snippet cold (Chapter 26)¶

    Goal. Practise the static-review skill before an interview asks you to.

    Steps. 1. Without re-reading Chapter 26, copy this snippet onto paper: 

    from playwright.sync_api import sync_playwright
from selenium import webdriver
import time
def test_search_functionality():
    browser = sync_playwright().start().chromium.launch()
    page = browser.new_page()
    page.goto("https://example.com")
    time.sleep(2)
    page.locator("#search").fill("playwright testing")
    page.locator(".button").click()
    time.sleep(3)
    results = page.locator(".result-item")
    browser.close()
    2. In five minutes, list every problem you can find and why each matters (not just what it is). 3. Check yourself against Chapter 26 §26.7. Lead your answer with the highest-impact issue (the one that makes the test unable to fail).

    What you practised

    The reviewer's instinct — for every line, ask "does this do the thing its shape implies?" AI-generated tests fail by looking right and behaving wrong; spotting that gap is the entire point of being a senior reviewer.

    Capstone lab — your own miniature suite¶

    Goal. Combine Labs 3–6 into a small, properly-layered project: components/ (LoginPage, ProductsPage, CartPage), services/ (ShoppingService), db/data.yaml (users + scenarios), tests/ (a unit test for price parsing, a smoke test, a data-driven e2e), and a GitHub Actions workflow (Chapter 25). Add an Allure report with allure.step phases.

    When it builds green and you can narrate the path of one test from fixture to browser and back (Chapter 27), you have built — and can defend — a real framework.

    Key idea

    You learn this craft by building it. These labs walk the same arc as the whole book: a robust single test → a unit-tested pure function → a Page Object → a service → data-driven → mocking → a complete layered suite. Do them in order, attempt before peeking, and refactor as you go — that refactoring is the learning.
