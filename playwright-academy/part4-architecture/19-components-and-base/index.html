    Chapter 19 — Component Objects & the Base Class¶

    Classic POM has one object per page. But real pages are built from repeating, reusable regions — a header, a result card, a filter panel — that show up across many pages. The component object pattern (the grown-up form of POM) models those regions as their own small classes. This chapter explains the pattern, and the one mechanic — scoped locators — that makes it work without elements colliding.

    19.1 Pages are composed of components¶

    A page object doesn't have to be one giant class. It can be assembled from smaller component objects, each owning one region:

    class HomePage(BaseComponent):
    def __init__(self, page: Page) -> None:
        super().__init__(page)
        self.header = HeaderComponent(page)          # reused on every page
        self.cookie_banner = CookieBannerComponent(page)

    Now home.header.search("shoes") reads exactly the way the page is structured: a home page has a header, and the header can search. And because HeaderComponent is its own class, the same header object is reused on the search-results page, the item page, and the cart — written once, composed everywhere. This is composition (Chapter 3) applied to UI structure:

    flowchart TD
    HP["HomePage"] --> HD["HeaderComponent"]
    HP --> CB["CookieBannerComponent"]
    SR["SearchResultsPage"] --> HD
    SR --> FP["FilterPanelComponent"]
    SR --> RC["ResultCardComponent (one per result)"]
    IP["ItemPage"] --> HD
    CP["CartPage"] --> HD

    Notice HeaderComponent is shared by every page — that reuse is the payoff of modelling regions as components rather than duplicating header selectors in each page class.

    19.2 The root locator and scoped queries — the key mechanic¶

    The defining feature of a component is that it can be scoped to a sub-tree of the page, so that its locators only ever match elements within its own region. This is what the BaseComponent provides:

    class BaseComponent:
    def __init__(self, page: Page, root: Locator | None = None) -> None:
        self.page = page
        self.root = root if root is not None else page.locator("body")   # default: whole page
        self.log = get_logger(self.__class__.__name__)
        self.screenshots = ScreenshotManager(page)

    def locator(self, selector: str) -> Locator:
        return self.root.locator(selector)      # ALWAYS resolves *within* this component's root
    • A component created without a root defaults to the whole body — appropriate for page-level objects like HomePage.
    • A component created with a root (say, scoped to one result card's <li>) finds elements only inside that subtree.

    Why does this matter so much? Consider a search-results page showing fifty result cards, each containing a .s-item__price. If a component used self.page.locator(".s-item__price"), it would match all fifty prices — a strict-mode disaster (Chapter 7). But because each ResultCardComponent is handed its own <li> as root, calling self.locator(".s-item__price") resolves to that card's price and no other:

    class ResultCardComponent(BaseComponent):
    _SEL_PRICE_CSS = ".s-item__price"

    def __init__(self, page: Page, root: Locator) -> None:
        super().__init__(page, root)             # root is MANDATORY for a card

    def price_text(self) -> str:
        return self.locator(self._SEL_PRICE_CSS).first.inner_text().strip()

    Key idea

    The root locator is what makes a component reusable and unambiguous. Scoped self.locator(...) queries are resolved relative to the component's own subtree, so N instances of the same component on one page never collide. This is the single most important implementation detail in component-style POM.

    From TypeScript

    root.locator(...) is identical to chaining locators in TS Playwright (card.locator(".price")). The component simply stores that root, so every method is automatically scoped — much like a React component receiving a ref to its own DOM subtree and querying only within it.

    19.3 The child-factory pattern¶

    A page often needs to hand back a list of components — one per repeated element. That's a child factory:

    class SearchResultsPage(BaseComponent):
    _SEL_CARDS_CSS = "ul.srp-results > li.s-item"

    @property
    def cards(self) -> Locator:
        return self.page.locator(self._SEL_CARDS_CSS)

    def get_visible_result_cards(self) -> list[ResultCardComponent]:
        cards = self.cards
        return [ResultCardComponent(self.page, cards.nth(i)) for i in range(cards.count())]

    get_visible_result_cards() walks the matched <li> elements and wraps each one as its own typed ResultCardComponent, scoped to its nth(i) locator. The caller can then ask each card domain questions (card.is_sponsored(), card.price_text()) without ever touching a selector.

    Gotcha — is the comprehension 'business logic in a component'?

    A reviewer might object that the list comprehension is logic inside a component. It isn't business logic — it's a structural child factory: it produces typed wrappers and makes no decisions about which cards matter (that's the service's job). Be ready to name that distinction. Selecting or filtering cards by price or sponsorship would be business logic, and it lives in the service (Chapter 20), not here.

    19.4 What belongs in the base class — and what doesn't¶

    A BaseComponent should hold only cross-cutting plumbing that every component genuinely needs:

    • the page and root references,
    • the scoped locator() factory,
    • a logger automatically labelled with the subclass name (via self.__class__.__name__, Chapter 3),
    • a screenshot helper.

    Resist the temptation to put page-specific methods on the base — that's a "god object" creeping in by the back door, and it violates Single Responsibility. The base stays thin; everything specific lives in the subclasses.

    19.5 The component catalogue, at a glance¶

    Component Root Single responsibility
    HomePage body the entry point; composes header + cookie banner
    HeaderComponent the banner role search box + submit, cart link
    CookieBannerComponent body detect and dismiss the consent banner (idempotently)
    SearchResultsPage body the card factory, pagination, composes the filter panel
    FilterPanelComponent the results region price range, Buy-It-Now filter, sort
    ResultCardComponent one <li> report one card's title, price, type, sponsored-ness
    ItemPage body title, price, variants, add-to-cart
    CartPage body subtotal, line items

    Every row has a crisp single responsibility (Chapter 17), and the one that's repeated on the page (ResultCardComponent) is precisely the one that takes a mandatory root.

    Interview lens

    "How do you stop selector collisions when a page has many identical cards?" → "Each card is its own component scoped to a root locator (cards.nth(i)), and all queries go through a self.locator() factory that resolves relative to that root. So fifty cards' fifty price nodes never collide — each component only ever sees its own subtree. The base class provides that scoped factory plus logging and screenshots, and holds no page-specific behaviour." That answer demonstrates you've actually built component POM, not just read about it.

    Exercise 19.1 — scope a repeated component

    On any page with a repeated card/row (a search result list, a table), write a tiny RowComponent(BaseComponent) that takes a root and exposes one method returning some text from within that row. Then write a factory method that returns a list of them, one per row, each scoped with .nth(i). Confirm that calling the method on row 3 returns row 3's text, not row 1's — that's scoping working.

    Key idea

    Components model reusable regions; pages compose them. The root locator plus the scoped locator() factory make many instances of the same component unambiguous. A child factory wraps repeated elements as typed components (structural, not business logic). The base class holds only thin cross-cutting plumbing — never page-specific behaviour.
