    Chapter 21 — Configuration & Environments¶

    Configuration — data-driven config, environment variables, profiles — is its own area of evaluation, because it is what separates a one-off script from a maintainable suite. The goals of this chapter: zero hardcoded URLs or magic values anywhere in the code, switching between environments with a single variable, and one typed source of truth for everything structural. We build it from the two-axis distinction up to a small typed loader.

    21.1 Two independent axes of "configuration"¶

    People lump "configuration" into one bucket, but there are really two independent questions, and conflating them causes real problems:

    1. Is it secret, or structural? A password is secret — it differs per person, must never be committed to git. A base URL is structural — it's shared by the whole team and should be committed. (We covered this in Chapter 1; secrets go in a gitignored .env, structural config in a committed file.)
    2. Does it vary by environment, or stay constant? headless differs between your laptop and CI; the result-card CSS selector is the same everywhere.

    A clean design answers both: secrets in .env, structural config in a committed typed file, and an environment profile that bundles the structural values that vary by environment.

    21.2 Profiles: a named bundle of environment settings¶

    A profile is a named set of environment-specific settings. The reference project defines two — dev (your laptop) and ci:

    # db/data.yaml
environments:
  dev:
    base_url: https://www.ebay.com
    region: US
    currency: USD
    headless: false        # show the browser locally
    slow_mo_ms: 100        # slow it down so you can watch
    max_pages_to_paginate: 5
  ci:
    base_url: https://www.ebay.com
    region: US
    currency: USD
    headless: true         # no display in CI; run fast
    slow_mo_ms: 0
    max_pages_to_paginate: 3

    You choose the active profile with a single environment variable, read once in a fixture:

    @pytest.fixture(scope="session")
def profile() -> str:
    return os.getenv("PROFILE", "dev")     # default to "dev" if PROFILE isn't set

@pytest.fixture(scope="session")
def env(db, profile) -> Environment:
    return db.environments.get(profile)

    uv run pytest -m smoke                          # PROFILE unset → "dev" (headed, slow-mo)
PROFILE=ci uv run pytest -m regression -n 4     # "ci" (headless, tighter pagination cap)

    The same code runs differently in the two environments, and the difference is driven entirely by which profile is selected — not by if running_in_ci: checks scattered through the code. The profile is the switch.

    From TypeScript

    os.getenv("PROFILE", "dev") ≈ process.env.PROFILE ?? "dev". Profiles are like Playwright Test projects, or a config.{env}.ts chosen by an env var — the same "one knob picks a whole bundle of settings" idea.

    21.3 Why YAML, and not .env, for structural config¶

    .env files are flat KEY=value strings. That's fine for a handful of secrets, but wrong for structured, typed, queryable data:

    • Scenarios have nested fields, lists (tags: [regression]), and real types (Decimal, bool, int).
    • The same data feeds the regression suite, the data-driven runner, and a standalone demo script.
    • You want to query it — "give me all the regression-tagged scenarios."

    A flat .env can't express any of that without ugly conventions like SCENARIO_1_QUERY=.... YAML gives you nesting, lists, comments, and types, and it parses cleanly into structured objects.

    Interview lens

    "Why a YAML 'database' instead of .env or a Python config module?" → "Secrets go in .env because they're per-person and gitignored. But structural test data is nested, typed, and shared across suites and a demo script, so it lives in one committed YAML file loaded into typed dataclasses, queryable by tag. .env is a flat string map — the wrong shape for scenarios. And money fields are stored as quoted strings so they parse to Decimal, never float." That single answer covers configuration, secrets, data-driven design, and the Decimal rule.

    21.4 Parse into typed objects at the boundary¶

    Raw YAML loads as nested dictionaries of strings, ints, and lists. The professional move is to convert it once, right at the edge, into typed frozen dataclasses, so the rest of the code works with real types:

    @dataclass(frozen=True)
class Environment:
    id: str
    base_url: str
    region: str
    currency: str
    headless: bool
    slow_mo_ms: int
    max_pages_to_paginate: int

@dataclass(frozen=True)
class Scenario:
    id: str
    query: str
    max_price: Decimal      # parsed from a quoted string, at load time
    limit: int
    allow_partial: bool
    min_results: int = 1
    tags: list[str] = field(default_factory=list)

    The loader does the conversion, including the critical money step:

    _DECIMAL_FIELDS = frozenset({"max_price"})

def _load_model(model, id_, payload):
    kwargs = {"id": id_}
    for f in fields(model):
        if f.name == "id" or f.name not in payload:
            continue
        value = payload[f.name]
        if f.name in _DECIMAL_FIELDS:
            value = Decimal(str(value))     # str → Decimal: exact, never via float
        kwargs[f.name] = value
    return model(**kwargs)

    After this boundary, every scenario.max_price is a Decimal and every env.headless is a real bool — no string-to-type juggling anywhere downstream.

    Key idea — convert at the boundary

    Parse and type external data once, at the point it enters the system, into immutable typed objects. The rest of the codebase then trusts those types. This is the same principle as validating untrusted input at a system's edge — and it's where the "string → Decimal, never float" money rule (Chapter 5) gets enforced exactly once.

    21.5 Accessor objects: a small query API¶

    Rather than passing raw dictionaries around, wrap each table in an accessor with a small, intention-revealing API:

    class ScenarioAccessor:
    def __init__(self, items: dict[str, Scenario]) -> None:
        self._items = items
    def get(self, id: str) -> Scenario:
        if id not in self._items:
            raise KeyError(f"scenario '{id}' not found. Available: {sorted(self._items)}")
        return self._items[id]
    def all(self) -> list[Scenario]:
        return list(self._items.values())
    def where(self, tag: str) -> list[Scenario]:
        return [s for s in self._items.values() if tag in s.tags]

    Now db.scenarios.where(tag="regression") reads like a query and hides the underlying dict. Notice that get lists the available keys in its error message — a small touch that turns a cryptic KeyError into a helpful "here's what you could have meant." This is the difference between data that merely sits in a file and data that's a first-class part of your system.

    21.6 Validate at load, fail clearly¶

    The loader rejects malformed config loudly and immediately, rather than letting it cause a confusing failure three layers deep later:

    unknown = set(raw) - set(_EXPECTED_TABLES)
if unknown:
    raise ValueError(
        f"unknown top-level keys: {sorted(unknown)}. Expected: {sorted(_EXPECTED_TABLES)}"
    )

    Mistype a top-level key as scenrios: and you get an immediate, clear error at load time — not a baffling empty result far away from the cause. Fail fast, fail clearly is a quiet hallmark of well-built infrastructure.

    Interview lens

    "How do you keep environment URLs out of the code?" → "There are none in the code. The base_url lives in the profile and is set on the browser context, so tests navigate with paths (/sch/i.html). Switching environments is one PROFILE env var. All structural config loads into typed, frozen dataclasses with validation at the boundary, exposed through accessor objects with a small query API." Zero hardcoded URLs is an explicit evaluation point — this is how you satisfy it.

    Exercise 21.1 — a tiny typed loader

    Create a settings.yaml with two profiles (local, ci) each having a base_url and a timeout (int). Write a frozen @dataclass Settings, a loader that reads the YAML and returns the right Settings for a profile chosen by os.getenv("PROFILE", "local"), and a line that prints settings.base_url. Then mistype a field in the YAML and confirm you get a clear error rather than a silent wrong value.

    Key idea

    Keep secrets in .env and structural config in one committed YAML file, loaded into frozen typed dataclasses (with money parsed to Decimal at the boundary). Profiles bundle the environment-varying settings, switched by a single PROFILE variable. Accessor objects give a clean query API, and validation at load makes mistakes fail fast and clearly. The result: no hardcoded URLs, one source of truth, one knob to switch environments.
