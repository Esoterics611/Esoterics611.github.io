    Chapter 17 — SOLID & SRP for Test Frameworks¶

    Architecture and clean code are, in almost any serious evaluation, the most heavily weighted area of all — and they're what an interviewer is probing when they say "walk me through your design" or "why is this in a service and not a component?" This chapter gives you the principles, in plain language and applied directly to test code. The next four chapters put them into practice. Don't skip this even if "SOLID" sounds like buzzword bingo — the one principle that actually earns the marks (Single Responsibility) is taught here on concrete cases you'll be asked about.

    17.1 Why a test suite needs architecture at all¶

    A twenty-line throwaway script needs no architecture. A suite of two hundred tests against a user interface that changes every week needs it desperately. The reason has a name: change amplification. A small change in one place should not force edits in fifty files.

    Picture the worst case. The site renames a CSS class. If that class string appears in eighty test files, you now have eighty edits to make, you'll miss three, and the suite goes red for a week. Good architecture localises the blast radius of change: a class rename touches one line, in one place. Every principle in this chapter is, ultimately, a different angle on that single goal — keeping changes small and contained.

    17.2 The layered design, as a picture¶

    The reference project (and most well-built suites) is organised into layers, each depending only on the one below it:

    flowchart TD
    T["tests/ — what to verify (assertions only)"]
    S["services/ — business flows & policy (the 'how')"]
    C["components/ — one UI region each (the markup)"]
    P["Playwright — browser / context / page"]
    U["utils/ — pure helpers (price parser, paginator)"]
    D["db/ — typed config & scenario data"]
    T --> S --> C --> P
    S -.uses.-> U
    T -.parametrized by.-> D

    The arrows point only downward — tests depend on services, services on components, components on Playwright. Nothing points back up. That one-directional, acyclic flow is the architecture, and the SOLID principles below explain why each boundary is drawn where it is.

    17.3 SOLID, translated into test-code terms¶

    SOLID is five principles. Here's each, stated plainly and shown in this domain:

    S — Single Responsibility: a class should have exactly one reason to change. : A ResultCardComponent changes only when the result-card markup changes. A SearchService changes only when the search flow changes. (Expanded in §17.4 — this is the one that matters most.)

    O — Open/Closed: open for extension, closed for modification. : Adding a new test scenario is a new row in the YAML data file (extension), not an edit to the test body (modification). Adding a new flow is a new method on a service, not surgery on existing methods.

    L — Liskov Substitution: any subtype must work wherever its base type is expected. : Every component extends BaseComponent and honours its contract, so anything written to work with a BaseComponent works with any specific component.

    I — Interface Segregation: don't force a client to depend on methods it doesn't use. : The paginator depends on _Pageable — just has_next_page() and go_to_next_page() — not on the whole SearchResultsPage. It needs two methods, so it asks for exactly two.

    D — Dependency Inversion: depend on abstractions, not concrete implementations. : The paginator depends on the _Pageable Protocol (Chapter 4), not on SearchResultsPage. The high-level paginator and the low-level page both depend on an abstraction, not on each other.

    From TypeScript

    These are the same SOLID principles you'd apply in a NestJS service or an Angular app. The translation to test code is direct: components are your "view" layer (markup), services are your "business" layer (flows), tests are the "callers" (assertions). If you've kept HTTP concerns out of business logic in application code, you already have the instinct.

    17.4 Single Responsibility is the one that earns the marks¶

    Of the five, Single Responsibility is the principle interviewers probe hardest, because violating it is the most common real-world failure. The test to apply is one question: "What is the one reason this class would change?"

    • ResultCardComponent → "the result-card markup changed." ✔ one reason.
    • SearchService → "the search flow changed — different filters, a different sort, a new pagination policy." ✔ one reason.
    • A hypothetical CartPage that also knew how to walk search results → it would change when the cart markup changes and when search pagination changes. ✘ two unrelated reasons → split it.

    The layered design from §17.2 enforces SRP physically, by giving each layer one category of reason-to-change:

    Layer Changes when…
    tests/ what we want to assert changes
    services/ a business flow changes
    components/ a page's markup changes
    utils/ a pure algorithm changes (price format, pagination rule)

    That clean separation of "reasons to change" is the architecture.

    Interview lens — the question you WILL be asked

    "Why is the price filtering in the service and not the component?" → "Because 'skip sponsored, skip auctions, drop anything over the max price' is a business decision — it changes when our selection policy changes, not when eBay's card markup changes. The component's job is only to report what's on a card — price_text(), is_sponsored(); deciding what to do with that is the service's job. Putting the policy in the component would give the component two reasons to change and couple business rules to markup." That is SRP, articulated on a concrete case, and it's the answer that scores the architecture marks.

    17.5 Mechanism versus policy¶

    A theme that threads through the whole codebase, worth naming explicitly because it makes the SRP boundary obvious in practice:

    • Mechanism = how to do a low-level thing. parse_price knows how to turn text into a Decimal. card.is_sponsored() knows how to detect the sponsored badge.
    • Policy = what to do about it. The service decides that sponsored cards are skipped and that an unparseable price means drop this listing.

    Keep them apart and each stays simple and reusable. The parser refuses to guess and raises; the caller decides whether to skip the listing or fail the test. The very same parser then serves a strict test and a lenient demo, because it has no policy baked into it. When you're unsure which layer something belongs in, ask: "is this how to do something (mechanism → lower layer) or what to do about it (policy → higher layer)?"

    17.6 DRY, and its limits¶

    "Don't Repeat Yourself" is why the three end-to-end suites (smoke, regression, data-driven) all call the same search → add → assert flow living once in the services, instead of copy-pasting it three times where the copies would drift apart.

    But beware premature DRY. Two pieces of code that merely look alike today, but would change for different reasons tomorrow, should not be merged — coupling them means a change for one forces a change on the other. The skill is to merge things that share a reason to change, not things that are superficially similar. (That's the SRP test again, viewed from the other side.)

    Gotcha — over-abstraction is as harmful as under-abstraction

    A five-level-deep page-object inheritance tree, or a "BaseTest" that everything extends, usually signals DRY applied to things that don't actually share a reason to change. Prefer composition and shallow hierarchies. A reliable smell test: if an abstraction makes a test harder to read, it's the wrong abstraction. Clever indirection that obscures what a test does costs more than the duplication it removed.

    Exercise 17.1 — apply the SRP question

    Take a method you've written (or imagine a LoginPage that both fills the login form and decides which user role to log in as based on the test environment). Ask "what are the reasons this would change?" If you find two unrelated reasons (the login markup changing vs. the policy of which role to use), describe how you'd split it into a component (markup) and a service or fixture (policy).

    Key idea

    Architecture exists to localise change. Of the SOLID five, Single Responsibility — one reason to change per class — is the one that earns the marks; be ready to articulate it on the concrete "why service, not component?" question. Separate mechanism (how to do something) from policy (what to do about it). Apply DRY to shared reasons to change, never to superficial resemblance — and never let an abstraction make a test harder to read.
