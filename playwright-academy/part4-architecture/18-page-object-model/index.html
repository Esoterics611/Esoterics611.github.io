    Chapter 18 — The Page Object Model¶

    Most engineers who adopt the Page Object Model quickly sense that it is cleaner than scattering raw Playwright calls through their tests. This chapter explains precisely why, and — just as importantly — what separates a good page object from a bad one, because POM done badly can be worse than no POM at all. We build from the problem it solves up to a catalogue of the mistakes to avoid.

    18.1 The problem POM solves¶

    Without POM, selectors get scattered through every test that touches a given screen:

    def test_a(page):
    page.fill("#gh-ac", "shoes")              # eBay's search input id
    page.click("#gh-btn")                      # eBay's search button id
    assert page.locator("ul.srp-results > li.s-item").count() > 0

def test_b(page):
    page.fill("#gh-ac", "books")              # the SAME selectors, copy-pasted
    page.click("#gh-btn")
    ...

    Now eBay renames #gh-ac. You must find and fix it in every test that searches. Across two hundred tests that's a day's work and a guaranteed missed occurrence — and the suite goes red until you find it. The deeper problem is conceptual: selectors are implementation detail, and they've leaked into the expression of test intent. A test should say "search for shoes," not "type into the element with id gh-ac."

    18.2 The core idea: hide selectors behind intent¶

    A Page Object is a class that wraps a page (or a region of one) and exposes intent-revealing methods, keeping the selectors hidden inside:

    class HeaderComponent(BaseComponent):
    _SEL_SEARCH_INPUT_NAME = "Search for anything"
    _SEL_SEARCH_SUBMIT_NAME = "Search"

    def search(self, query: str) -> None:
        self.root.get_by_role("combobox", name=self._SEL_SEARCH_INPUT_NAME).fill(query)
        self.root.get_by_role("button", name=self._SEL_SEARCH_SUBMIT_NAME).click()

    Now the tests speak the domain language and own zero selectors:

    def test_a(page):
    HomePage(page).header.search("shoes")     # WHAT to do, not HOW it's wired

def test_b(page):
    HomePage(page).header.search("books")

    When eBay renames its search input, you fix it in one method, and every test that searches keeps working untouched.

    Key idea

    A page object converts how the page is built (selectors, clicks, waits) into what you can do with it (search, add_to_cart, subtotal). Tests express intent; the page object owns the markup. That single inversion of responsibility is the entire point of POM.

    18.3 What a good page object SHOULD do¶

    • Expose intent-revealing methods: header.search("shoes"), item.add_to_cart(), cart.subtotal(). The method name describes a user-meaningful action or query.
    • Own its selectors, as _SEL_ constants (Chapter 8).
    • Return domain values, not Playwright objects: subtotal() returns a Decimal, price_text() returns a str, is_sponsored() returns a bool. (More on this in §18.5.)
    • Encapsulate one region's markup, and nothing else.

    18.4 What a good page object should NOT do¶

    This list is where most POM implementations go wrong. Each item is a real, common mistake:

    • It should not return raw Locators to the test. If cart.subtotal_locator() hands a locator back, the test will call .inner_text() on it and parse the result — and now selector-and-parsing knowledge has leaked back into the test, defeating the point. Return the parsed value instead.
    • It should not contain assertions. A page object reports state (subtotal() -> Decimal); the test asserts on it. Putting assert statements inside page objects scatters your verification logic across many classes and makes the page object unusable in non-test contexts (like a demo script or a monitoring tool).
    • It should not contain business logic or cross-page flow. "Search, paginate, filter by price, add the first five" is a flow across pages — it belongs in a service (Chapter 20), not on any single page object.
    • It should not know about test data or environments. Those are injected from above; a page object just drives whatever page it was handed.

    Interview lens — the most-tested boundary

    "Should a page object contain assertions?" → "No. Page objects report state as domain values; tests assert on those values. Keeping assertions out means the same page object works in a test, in a demo script, and in a monitoring tool — and all verification stays in one place (the test) instead of scattered across page classes." Many candidates get this wrong; getting it right is a strong signal.

    18.5 Returning domain values — a concrete before/after¶

    This is worth seeing side by side, because it's the most common subtle leak:

    # BAD — leaks a Locator; the test ends up knowing about markup AND parsing:
class CartPage:
    def subtotal_element(self) -> Locator:
        return self.page.get_by_text(re.compile(r"^Subtotal"))

# in the test:
text = cart.subtotal_element().inner_text()      # the test does the reading...
amount = Decimal(text.replace("$", ""))           # ...and the parsing. The leak is here.

    # GOOD — returns a parsed Decimal; the test knows nothing about markup or parsing:
class CartPage:
    def subtotal(self) -> Decimal:
        text = self.page.get_by_text(re.compile(r"^Subtotal")).first.inner_text()
        return parse_price(text)

# in the test:
assert cart.subtotal() <= budget                  # pure intent

    In the "good" version, all of the markup-and-parsing knowledge is sealed inside CartPage. The test reads like a requirement: "the subtotal must not exceed the budget."

    18.6 A catalogue of POM anti-patterns¶

    Anti-pattern Why it's bad The fix
    Selectors in test files change amplification move them to _SEL_ constants in a page object
    Page object with asserts scatters verification; can't reuse outside tests return values; assert in the test
    One "god" page object for the whole site a thousand reasons to change one class per region
    Returning Locators to tests selector knowledge leaks back into tests return parsed domain values
    Deep page-object inheritance rigid, hard to follow a shallow base + composition
    Business logic in page objects couples flow to markup extract a service

    18.7 When POM is not worth it¶

    Maturity means knowing when a pattern is overkill. Modern Playwright (especially in TypeScript) sometimes favours small fixtures over full page-object classes for simple apps. The trade-off: POM shines when the UI is large, shared across many tests, and volatile — an e-commerce site is the textbook case. For a tiny, stable app with a handful of tests, heavy POM is just indirection that costs more than it saves.

    Interview lens

    "When is POM not worth it?" → "For a small, stable surface with few tests, the indirection can cost more than it saves — a couple of role locators inline are fine. POM earns its keep when the UI is large, volatile, and shared across many tests, so the one-place-to-fix-a-selector payoff dominates. It's a judgment call, not dogma." Showing you know when not to apply a pattern is more senior than reciting that the pattern is good.

    Exercise 18.1 — refactor toward POM

    Take the scattered-selector test_a/test_b from §18.1. Write a small SearchPage class with _SEL_ constants and a search(query) method, plus a result_count() method that returns an int. Rewrite both tests to use it. Notice that the tests no longer contain a single selector, and that a class rename would now be a one-line fix.

    Key idea

    A page object hides selectors behind intent-revealing methods and returns domain values — never raw locators, never assertions, never business logic. One class per region; no test-data knowledge. POM's payoff scales with the size, churn, and reuse of the UI — apply it where that payoff is real, not reflexively.
