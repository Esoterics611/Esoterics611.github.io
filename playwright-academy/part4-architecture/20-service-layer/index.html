    Chapter 20 — The Service Layer¶

    This is the chapter that lifts a suite from "fine" to "architected," and it contains the single most valuable thing you can articulate in an interview: why there is a layer above the page objects at all. Many candidates build page objects and stop there; being able to explain the service layer — what it's for, what goes in it, and what stays out — is what marks senior design judgment. We'll build the motivation carefully, then state the rules.

    20.1 The gap that page objects alone leave¶

    Page objects model regions of the UI. But a real test goal isn't about one region — it spans several. Consider the headline flow:

    "Search for shoes under $220, add the first five Buy-It-Now items to the cart, then assert the cart total."

    That single sentence touches the home page, the search-results page, multiple item pages, and the cart — and it carries real logic: pagination bounds, filtering out sponsored and auction listings, picking random variants, and money arithmetic. Where does all of that go?

    Two tempting-but-wrong answers:

    • Put it in the test. Then it gets duplicated across the smoke, regression, and data-driven suites — three copies that drift apart over time.
    • Put it in a page object. Then a CartPage ends up knowing how to walk search results, which gives it two unrelated reasons to change — a Single Responsibility violation (Chapter 17).

    Neither fits. The flow needs a home of its own. That home is a service.

    flowchart LR
    Test["test (asserts)"] --> Svc["SearchService.search_items_by_name_under_price()"]
    Svc --> Home["HomePage"]
    Svc --> Results["SearchResultsPage"]
    Svc --> Filter["FilterPanelComponent"]
    Svc --> Pag["collect_until() paginator"]

    20.2 What a service is¶

    A service owns the flows and policy of one business domain. It composes calls to several components into a meaningful, multi-step action, holding the what to do (policy) while the components hold the how (mechanism):

    class SearchService(BaseService):
    def __init__(self, page: Page, env: Environment) -> None:
        super().__init__(page)
        self.env = env
        self._home = HomePage(page)
        self._results = SearchResultsPage(page)

    def search_items_by_name_under_price(
        self, query: str, max_price: Decimal, limit: int = 5
    ) -> list[str]:
        self._home.load()
        self._home.header.search(query)
        self._results.apply_price_filter(max_price)
        self._results.filter_panel.apply_buy_it_now()
        self._results.filter_panel.sort_by_price_plus_shipping_lowest()
        return collect_until(
            component=self._results,
            collect_fn=lambda r: self._collect_card_urls(r, max_price),
            target_count=limit,
            env=self.env,
        )

    Read that method top to bottom: it's a recipe — load, search, filter, sort, paginate-and-collect. Each step delegates to a component; the service decides the sequence and the rules. The components execute the clicks; the service decides what the clicks add up to.

    20.3 Policy lives in the service; mechanism lives in the component¶

    The filtering rules are private service methods, and that placement is deliberate:

        def _qualify_card(self, card: ResultCardComponent, max_price: Decimal) -> str | None:
        if card.is_sponsored():            # the component REPORTS; the service DECIDES
            return None
        if card.item_type() != "buy_it_now":
            return None
        try:
            price = parse_price(card.price_text())
        except ValueError:
            return None                    # unparseable price → skip (a policy decision)
        if price > max_price:
            return None
        return card.url() or None

    card.is_sponsored() is mechanism — it knows how to detect the sponsored badge. "Skip sponsored cards" is policy — and policy is the service's job. If the selection rules change tomorrow (say, "allow auctions after all"), you edit the service; the component is untouched, because the markup didn't change. That's Single Responsibility paying off in practice.

    Interview lens — THE architecture question

    "Why have a service layer on top of your page objects?" → "The flows I'm testing span multiple pages and own business logic — pagination bounds, price filtering, variant selection, money math. Put that in a test and it's duplicated across suites; put it in a page object and the object grows a second reason to change. A service is the single home for cross-page flow and policy, so components stay markup-only and tests stay assertion-only. Each tier ends up with exactly one job." This is the highest-value answer in the whole interview — internalise its shape and say it in your own words.

    20.4 The rules services follow¶

    The reference services follow a tight contract worth stating as explicit rules:

    1. One service per domain. auth, search, cart, variants — not one giant EbayService doing everything.
    2. Receive page / context / env at construction (injected by a fixture). A service never reaches for globals.
    3. Never import another service. Services compose components, not each other — importing one service into another creates coupling and risks circular imports. (The cart service uses a variant service, but it's injected as a dependency, not imported and constructed internally — see §20.5.)
    4. Return domain values, not Locators. search_items_by_name_under_price returns list[str] (URLs); a subtotal getter returns Decimal. The test asserts on plain values.
    5. No assertions scattered through flows (with one deliberate, named exception — §20.6). Services do the flow and return results; tests assert.

    20.5 Dependency injection between services¶

    The cart service needs the variant service. Rather than constructing one internally (which would hard-couple them), it receives one:

    class CartService(BaseService):
    def __init__(self, page, context, variant_service: VariantService) -> None:
        super().__init__(page)
        self.context = context
        self.variant_service = variant_service     # INJECTED, not newed up internally

    And the fixture wires the two together:

    @pytest.fixture
def cart_service(page, context, variant_service):   # variant_service is itself a fixture
    return CartService(page, context, variant_service)

    This keeps the cart service decoupled from how variants get chosen — you could inject a different variant-selection strategy without touching the cart service at all. It's the same dependency injection you saw with fixtures (Chapter 13) and with the Protocol (Chapter 4), now applied between services.

    20.6 The one nuance: where the budget assertion lives¶

    There is one place a service does raise: assert_cart_total_not_exceeds.

        def assert_cart_total_not_exceeds(self, budget_per_item: Decimal, items_count: int) -> None:
        self._cart.open()
        subtotal = self._cart.subtotal()
        budget = budget_per_item * items_count
        if subtotal > budget:
            raise AssertionError(f"cart subtotal exceeds budget ... over_by {subtotal - budget}")

    Doesn't that violate rule #5 ("no assertions in services")? This is a named spec function — the reference project's spec defines assertCartTotalNotExceeds as a reusable assertion primitive, so encapsulating the comparison (with a rich, structured failure message) and reusing it across all the suites is exactly right. The general rule still holds — services don't litter ad-hoc asserts through their flow logic — but a deliberately named, reusable assertion method is a reasonable, defensible exception. The point is to be able to explain the distinction, not to follow the rule blindly.

    Interview lens

    If an interviewer says "you told me no assertions in services, but here's one" — don't get flustered. "General flows return values and let tests assert. But the spec defined assertCartTotalNotExceeds as a named, reusable assertion primitive, so I encapsulated it with a structured failure message and reuse it across suites. It's a deliberate, named exception — not assertions sprinkled through business logic." Being able to defend a considered deviation is more impressive than rigidly insisting a rule has no exceptions.

    Exercise 20.1 — find the seam

    Take a flow you know (e.g. "log in, open settings, change the theme, confirm it saved"). List which steps are component mechanics (fill, click, read text) and which are policy / sequencing (which order, what counts as success, what to do if a step is missing). The mechanics belong in components; the policy and sequencing belong in a service. Sketch the service method signature and the component calls it would make.

    Key idea

    Services own cross-page flows and policy; components own markup; tests own assertions. One service per domain, dependencies injected (never imported between services), returning domain values. The answer to "why a service layer?" is your single most valuable interview sentence — know it cold.
