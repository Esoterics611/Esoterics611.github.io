    Chapter 22 — Smart Locators & Resilience¶

    Robustness and smart locators are typically the second most heavily weighted area of an automation evaluation, right after architecture. This chapter is about one thing: surviving a hostile, changing, dynamic website without your tests flaking. We'll start with the mindset, then work through each concrete technique with examples, and end with a checklist you can recite when asked "how do you make tests robust?"

    22.1 The resilience mindset¶

    A real commercial site like eBay is, from an automation standpoint, actively hostile in ways a tidy demo app never is:

    • the markup changes between visits (A/B tests, personalization);
    • result order is shuffled per visitor, so "the third item" is meaningless;
    • sponsored listings and ads are injected into the middle of lists;
    • some elements load late or only conditionally (cookie banners, lazy images);
    • the same logical thing appears in multiple markup variants (a price as a single value, or a range, or with a "US $" prefix).

    Resilience means your locators and flows tolerate all of this without breaking. None of the techniques below is complicated; together they're the difference between a suite that runs green for months and one that needs babysitting every morning.

    22.2 Locate by identity, never by position¶

    This is the number-one rule, stated already in Chapter 8 and worth repeating because positional locators are the single most common cause of "worked yesterday, broke today":

    # FRAGILE — breaks the moment an ad is injected or the order shuffles:
page.locator("li.s-item:nth-child(3)")

# RESILIENT — finds the thing by WHAT IT IS:
page.get_by_role("link", name="Nike Air Max")
card.filter(has_text="In stock")

    eBay reorders its results per visitor, so "the third card" doesn't identify anything stable. The XPath in the reference project was written specifically without positional indices for exactly this reason (Chapter 9).

    22.3 Fallback selectors with the CSS comma¶

    When a site exposes the same element two different ways across markup variants, list both and let Playwright try them in order — the comma means "match any of these":

    _SEL_PRICE_CSS = '[data-testid="x-price-primary"], .x-price-primary'
_SEL_LINE_ITEM_CSS = "[data-testid='cart-item'], li.cart-item, [data-listitemid]"

    This one trick absorbs a whole category of "eBay rolled out a new header variant overnight" failures: prefer the stable data-testid, and fall back to the class if it's absent. It costs nothing and buys real resilience on volatile pages.

    22.4 Regex names for fuzzy-but-anchored matching¶

    Accessible names sometimes carry a dynamic part — a count, a suffix. A regular expression lets you match the stable part while ignoring the variable part:

    import re
page.get_by_role("link", name=re.compile(r"^Cart"))          # "Cart", "Cart (3)", "Cart (12)"
page.get_by_text(re.compile(r"^Subtotal"))                    # "Subtotal (3 items) $50.00"
self._SEL_ACCEPT_NAME = re.compile(r"^Accept(?:\s+all)?$", re.I)   # "Accept" OR "Accept all"

    The anchors (^, $) keep the match tight so you don't accidentally match a longer unrelated label, and re.I makes it case-insensitive. This is how the cookie-banner component handles the two common button labels ("Accept" and "Accept all") with a single locator. (Regex itself is covered in Appendix B.)

    22.5 Idempotent, conditional steps for maybe-present elements¶

    Some elements appear only sometimes — a cookie banner, a promo modal. Don't assume one is there; probe for it with a bounded wait, then branch:

    class CookieBannerComponent(BaseComponent):
    _SEL_ACCEPT_NAME = re.compile(r"^Accept(?:\s+all)?$", re.I)

    def is_visible(self) -> bool:
        try:
            self._accept_button().wait_for(state="visible", timeout=2000)
        except PlaywrightTimeoutError:
            return False                     # not here within 2s → there's no banner
        return True

    def accept(self) -> None:
        if self.is_visible():                # no banner present? this is a no-op
            self._accept_button().click()

    accept() is idempotent — safe to call whether or not a banner is present, so you can call it unconditionally in a fixture and not worry. The bounded wait_for(..., timeout=2000) is a legitimate explicit wait (a 2-second "is it here? if not, move on" probe with a branch), not a blind sleep. Dismissing the banner once in a fixture then handles it for the whole suite.

    Interview lens

    "How do you handle elements that only sometimes appear, like cookie banners or modals?" → "A bounded probe plus a branch: wait_for(state='visible', timeout=2s) inside a try/except, and I act only if it's present — so the step is idempotent and safe to call unconditionally. I dismiss the banner once in a fixture, not in every test. The bounded timeout means a missing banner costs two seconds once, never a hang." This shows you distinguish a conditional wait from a sleep.

    22.6 Parse defensively; refuse to guess¶

    Dynamic text is unreliable, and a parser that invents a value spreads bugs downstream. The price parser (Chapter 5) anchors on $ and raises on anything ambiguous, so the caller gets to decide the policy (skip this listing) rather than silently receiving a misleading 0. Resilience here means "fail in a way the caller can handle," not "return something and hope."

    22.7 Skip-and-continue for non-fatal anomalies¶

    A robust collection flow tolerates an individual bad item without aborting the entire run:

    def add_items_to_cart(self, urls: list[str]) -> None:
    for url in urls:
        tab = self.context.new_page()
        try:
            tab.goto(url)
            item = ItemPage(tab)
            if not item.is_buy_it_now():
                self.log.warning("skipping auction-only listing: %s", url)
                continue                      # one bad item is not a failed run
            if item.required_variant_selects():
                self.variant_service.pick_random_variants(item)
            item.add_to_cart()
        finally:
            tab.close()                       # always clean up the tab

    An auction listing (which has no Add-to-Cart button) is logged and skipped, not treated as fatal — and the caller later decides, via the scenario's allow_partial flag, whether a short result set is acceptable. This is policy-driven robustness: the mechanism tolerates the anomaly, and the data (allow_partial, min_results) sets the tolerance.

    Gotcha — robust is not the same as permissive

    "Skip and continue" must always be logged (self.log.warning(...)) — silent skipping hides real problems. And it must be bounded by a policy (allow_partial, min_results) so you don't quietly pass a run that actually collected zero usable items. Tolerating individual anomalies is good; tolerating a completely empty result without noticing is a bug.

    22.8 The robustness checklist¶

    When asked "how do you make tests robust?", walk this list — it's a complete answer:

    1. Locate by identity (role/label/text), never by position.
    2. Auto-wait; never time.sleep; use a bounded wait_for only for genuine probes.
    3. Fallback selectors (data-testid, .class) for volatile markup.
    4. Regex names, anchored tight, for labels with dynamic parts.
    5. Idempotent conditional steps for maybe-present elements.
    6. Defensive parsing that raises on ambiguity.
    7. Skip-and-log non-fatal anomalies, bounded by a data-driven tolerance.
    8. Isolated contexts per test so parallel runs don't interfere.

    Exercise 22.1 — make a brittle locator resilient

    Find (or write) a locator like page.locator("div.card:nth-child(2) .price"). Rewrite it to locate by identity instead — by the card's visible product name (filter(has_text=...)) then the price within it. Then add a comma-fallback for the price selector. Explain which of the two versions survives (a) an injected ad row above the card and (b) a price-class rename.

    Key idea

    Robustness is designing for a site that changes under you: identity over position; fallback selectors for volatile markup; tight, anchored regex names for dynamic labels; idempotent probes for conditional UI; parsers that refuse to guess; and logged skip-and-continue bounded by data-driven tolerances. Memorise the eight-point checklist — it is the robustness answer.
