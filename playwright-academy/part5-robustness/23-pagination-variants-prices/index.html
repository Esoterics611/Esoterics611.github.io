    Chapter 23 — Three Dynamics: Pagination, Variants & Prices¶

    Real e-commerce automation has to handle three recurring dynamic challenges: paginating to collect enough items, selecting product variants, and parsing messy prices. Each is a small, self-contained algorithm, and "how did you handle pagination / variants?" is a direct interview question. We'll work through all three in full, drawing out the reusable design ideas in each.

    23.1 Pagination — a generic, reusable collector¶

    The requirement. Collect up to limit qualifying items. If the current page has fewer than needed, go to the next page and keep collecting. Stop when you have enough, when you run out of pages, or when you hit a safety cap.

    The elegant solution is a generic paginator that knows nothing about eBay, search, or URLs — only "a thing I can advance through pages." That capability is captured by the _Pageable Protocol from Chapter 4:

    def collect_until(component, collect_fn, target_count, max_pages=None, *, env=None):
    if max_pages is None:
        if env is None:
            raise ValueError("collect_until needs max_pages or env")
        max_pages = env.max_pages_to_paginate

    collected = []
    for page_index in range(1, max_pages + 1):
        batch = collect_fn(component)              # collect this page's qualifying items
        collected.extend(batch)
        if len(collected) >= target_count:         # got enough?
            return collected[:target_count]        # trim any overshoot to exactly the target
        if not component.has_next_page():           # no more pages?
            break
        component.go_to_next_page()                 # advance and loop
    return collected                                # may be fewer than target — that's allowed

    The control flow, as a picture:

    flowchart TD
    Start([start, collected=empty]) --> Collect["collect this page → add to collected"]
    Collect --> Enough{"collected >= target?"}
    Enough -- yes --> Trim["return collected, trimmed to target"]
    Enough -- no --> Next{"has next page?"}
    Next -- no --> Return["return what we have"]
    Next -- yes --> Cap{"under max_pages?"}
    Cap -- no --> Return
    Cap -- yes --> Advance["go to next page"] --> Collect

    Design points worth naming in an interview:

    • Bounded by max_pages. Without a cap, a query that never yields limit items would paginate forever. The cap (5 for dev, 3 for ci) comes from the environment profile — a data-driven safety limit, not a magic number.
    • Returns up to the target. collected[:target_count] trims any overshoot, and returning fewer than the target is valid — the caller decides via allow_partial what to do with a short result. The paginator imposes no policy of its own.
    • Generic over the item type and the page. It works for any paginated list and any item type (Chapter 4), so it's reusable far beyond search results — dependency inversion in action.
    • The collector is injected (collect_fn), so what counts as a qualifying item (the price / sponsored / Buy-It-Now rules) stays in the service, not in the paginator.

    Interview lens

    "Walk me through your pagination." → "A generic collect_until that accepts anything satisfying a _Pageable Protocol — has_next_page and go_to_next_page — plus an injected collector function. It accumulates across pages until it has the target count, runs out of pages, or hits a config-driven max_pages safety cap, then trims to the target. Returning fewer is valid; the caller's allow_partial decides if that's fatal. The eBay-specific filtering lives in the injected collector, so the paginator itself is reusable for any list." That one answer demonstrates pagination, generics, and dependency inversion at once.

    A spec nuance worth owning

    The original spec said "paginate until you have 5 or pages run out." The max_pages cap means we might stop before pages truly run out. That's a deliberate safety trade-off — be ready to say "I bounded it to avoid an unbounded walk on a sparse query, and the cap is configuration, so it's trivial to raise." Owning a deliberate trade-off beats pretending it doesn't exist.

    23.2 Variants — random in-stock selection¶

    The requirement. If an item has variant pickers (size, colour), choose random in-stock values before adding it to the cart. The challenge is filtering out the junk options — placeholders like "Select…" and entries that are out of stock:

    class VariantService(BaseService):
    _PLACEHOLDER_PATTERN = re.compile(r"^\s*(?:-+|select|choose|please select|--)", re.I)
    _OUT_OF_STOCK_PATTERN = re.compile(r"(?:out of stock|sold out|unavailable)", re.I)

    def pick_random_variants(self, item: ItemPage) -> None:
        for combo in item.required_variant_selects():
            in_stock = combo.locator("option:not([disabled])")    # 1. skip disabled options
            labels = [label.strip() for label in in_stock.all_text_contents()]
            valid = [
                label for label in labels
                if label
                and not self._PLACEHOLDER_PATTERN.match(label)     # 2. skip "Select…" placeholders
                and not self._OUT_OF_STOCK_PATTERN.search(label)   # 3. skip out-of-stock labels
            ]
            if not valid:
                self.log.warning("no in-stock option; skipping")   # log + continue
                continue
            choice = random.choice(valid)
            combo.select_option(label=choice)
            self.log.info("variant: picked %r", choice)

    The design points:

    • Three layers of filtering, defence in depth: the CSS :not([disabled]) drops disabled options at the DOM level; the placeholder regex drops "Select…"-style prompts; the out-of-stock regex drops unavailable labels. Any one might miss a case; together they're robust.
    • Skip-and-log when a combobox has no valid option, rather than crashing — the caller decides whether the item is still usable (the §22.7 pattern).
    • It's a service, not a component. Choosing a variant at random is a business decision (the policy "pick any in-stock option"); the item page's job is only to expose the variant comboboxes. Putting random.choice in the ItemPage component would be business logic in a component — a real Single Responsibility violation. (This is exactly the kind of dead, duplicated method worth removing in a cleanup pass.)

    Interview lens

    "Why is variant selection in a service and not on the item page object?" → "Choosing which variant is a policy decision — we pick any in-stock one at random — while the item page's job is only to expose the variant comboboxes. Random choice is business logic, so it belongs in a service: the component reports, the service decides." Same SRP refrain as Chapter 20, on a fresh example.

    23.3 Prices — parse defensively (the robustness view)¶

    Price parsing is covered in depth in Chapter 5; here is the robustness framing. The parser must survive every format the site throws at it:

    Input Output Why it's tricky
    "$25.00" 25.00 the baseline
    "US $1,234.56" 1234.56 currency prefix + thousands comma
    "$25.00 to $30.00" 25.00 a range — take the lower bound
    "Subtotal (3 items) $50.00" 50.00 the "3" must NOT win — anchor on $
    "Time left: 3d 4h" ValueError not a price at all — refuse to guess

    The two robustness principles embodied:

    1. Anchor on intent ($), not on position. A "take the first number" parser would return 3 for the subtotal line — a silent, corrupting bug. Anchoring on $ makes the price win.
    2. Raise on ambiguity. Garbage in → ValueError out, so the caller skips the listing. A parser that returned 0 for "Auction ended" would silently pass budget checks it should fail.

    And because the parser is pure (text in, Decimal out, no I/O), all of this is verified by ~22 unit tests in well under a tenth of a second, with no browser (Chapter 16) — the part of the suite that's always green.

    Exercise 23.1 — generalise the paginator

    The collect_until paginator is generic. On paper (or in code), describe how you'd reuse it, unchanged, to collect the first 20 rows of an order-history page that paginates. What two methods must the order-history page expose to satisfy _Pageable, and what would its injected collect_fn return? (Answer: has_next_page() and go_to_next_page(); the collect_fn returns that page's order rows — and nothing in the paginator changes.)

    Key idea

    Pagination: a generic, Protocol-based, bounded collector with the filtering policy injected. Variants: defence-in-depth filtering with a random in-stock choice, living in a service because choosing is policy. Prices: anchor on $, take the lower bound of ranges, raise on garbage, and stay pure so it's exhaustively unit-tested. These three are the concrete robustness that evaluators reward.
