    Chapter 15 — Markers, Parallelism & the pytest-playwright Plugin¶

    This chapter covers the operational layer of pytest: how to tag tests so you can run subsets of them, how to run them in parallel for speed, and the plugin that manages Playwright's lifecycle so you never have to. These are the tools that turn a pile of tests into a suite you can actually operate day to day.

    15.1 Markers: tagging tests¶

    A marker is a label you attach to a test with a decorator. It lets you group and select tests later:

    import pytest

@pytest.mark.smoke
def test_home_loads(page): ...

@pytest.mark.regression
def test_full_e2e(...): ...

    You should register your markers in pyproject.toml so pytest doesn't warn about "unknown markers" (and so there's a documented list of what each means):

    [tool.pytest.ini_options]
markers = [
    "smoke: fast critical-path tests — run before every deploy",
    "regression: the full regression suite — run nightly",
    "slow: long-running tests — run in a dedicated pipeline",
]

    Then you select tests by marker with the -m flag, which accepts a boolean expression:

    uv run pytest -m smoke                 # only tests marked smoke
uv run pytest -m regression            # only regression
uv run pytest -m "not slow"            # everything except slow tests
uv run pytest -m "smoke or regression" # either

    Interview lens

    "How do you organise which tests run when?" → "By marker, not by directory. smoke for the fast critical path on every push, regression nightly, slow in a dedicated pipeline. CI runs -m regression; locally I run -m smoke for quick feedback. Organising by marker means a test's speed and role is a property of the test itself, not of where its file happens to live — and a single test can carry several tags." (This is, incidentally, why a suite organised this way doesn't need separate smoke/ and regression/ folders — selection is by marker.)

    15.2 Parallelism with pytest-xdist¶

    By default pytest runs tests one after another. The pytest-xdist plugin runs them across several worker processes at once, which can cut a multi-minute suite dramatically:

    uv run pytest -m regression -n 4        # spread across 4 worker processes
uv run pytest -n auto                   # one worker per CPU core

    The crucial requirement: because each worker is a separate process with its own browser and its own contexts, your tests must be independent — no shared mutable state, no assumptions about the order tests run in. This is exactly where the function-scoped, isolated context from Chapter 6 and Chapter 13 pays off: because every test already gets its own clean session, your tests parallelise safely with no extra work.

    Gotcha — parallelism exposes hidden coupling

    Running with -n 4 is unforgiving of hidden dependencies between tests. If two tests both write to the same file, share a session, or rely on running in a particular order, parallel execution will surface it as seemingly-random failures. The fix is never "turn off parallelism" — it's "remove the shared state." Process-level isolation (a separate browser context per worker) is precisely what makes safe parallelism possible.

    From TypeScript

    -n auto ≈ Jest's default parallel workers, or Playwright Test's workers setting. Same contract everywhere: tests must be independent. Python parallelises across processes (which also sidesteps the Global Interpreter Lock), so each worker launches its own browser.

    15.3 The pytest-playwright plugin: lifecycle for free¶

    Installing the pytest-playwright plugin gives you a set of fixtures that own Playwright's entire lifecycle, so you never write sync_playwright(), launch(), or close() in a test:

    Fixture Scope What it provides
    playwright session the Playwright runtime
    browser session one launched browser, shared across the run
    context function a fresh, isolated context per test
    page function a fresh page inside that context 
    def test_home(page):          # a fresh page + context, automatically torn down afterwards
    page.goto("https://www.ebay.com")

    It also adds command-line flags for the things you'd otherwise have to wire by hand:

    uv run pytest --headed                 # show the browser window
uv run pytest --browser firefox        # chromium | firefox | webkit
uv run pytest --slowmo 200
uv run pytest --tracing retain-on-failure
uv run pytest --video retain-on-failure
uv run pytest --screenshot only-on-failure

    Interview lens

    "Why use the plugin instead of launching Playwright yourself inside the test?" → "The plugin owns the runtime/browser/context/page lifecycle, gives every test a fresh isolated context, and wires up trace/video/screenshot capture and xdist parallelism for free. Launching Playwright by hand inside a test throws all of that away — no automatic trace on failure, no isolation, no parallel safety. It's literally one of the bugs in the AI-generated-code review in Chapter 26."

    15.4 Overriding the plugin's defaults¶

    The plugin's launch and context settings are themselves fixtures, which you can override in conftest.py to inject your own configuration. The pattern is: request the plugin's fixture by the same name, spread its existing value, and add your overrides:

    @pytest.fixture(scope="session")
def browser_type_launch_args(browser_type_launch_args, env):
    return {**browser_type_launch_args, "headless": env.headless, "slow_mo": env.slow_mo_ms}

@pytest.fixture(scope="session")
def browser_context_args(browser_context_args, env):
    return {
        **browser_context_args,
        "base_url": env.base_url,
        "locale": f"en-{env.region}",
        "viewport": {"width": 1440, "height": 900},
    }

    This is how the reference project drives headless/slow-mo/base-url from its Environment configuration without forking the plugin. The {**existing, "key": value} syntax is a dict merge — it starts from the plugin's defaults and layers your settings on top. (Dict merge is covered in Appendix C; it's the same idea as JS object spread {...existing, key: value}.)

    From TypeScript

    Overriding browser_context_args ≈ extending Playwright Test's use: {} config block — baseURL, locale, viewport, trace. Same knobs, surfaced here as fixtures you compose rather than a static config object.

    15.5 Configure capture once, in addopts¶

    The flags you always want can live in pyproject.toml under addopts, so every run captures diagnostics without you remembering the flags:

    [tool.pytest.ini_options]
addopts = "--tracing=retain-on-failure --video=retain-on-failure --screenshot=only-on-failure"

    The magic value is retain-on-failure: it keeps the trace and video only for tests that fail. So you get rich debugging artifacts exactly where you need them — failures — without filling your disk with recordings of the 99% of tests that pass. Configure it once; it applies to the whole suite.

    Exercise 15.1 — markers and selection

    Take any project with a few tests. Mark two of them @pytest.mark.smoke and register the marker in pyproject.toml. Run pytest -m smoke and confirm only those two run. Then run pytest -m "not smoke" and confirm the rest run. You've just built selectable test suites with no folders.

    Key idea

    Markers tag tests for selection with -m (organise by role, not by folder). pytest-xdist runs tests across parallel processes — safe precisely because each test's context is isolated. The pytest-playwright plugin owns the browser lifecycle and adds trace/video/screenshot capture; override browser_context_args / browser_type_launch_args to inject config without forking it. Put always-on capture in addopts with retain-on-failure.
