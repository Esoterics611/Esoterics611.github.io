    Chapter 12 — pytest Fundamentals¶

    pytest is the test runner the Python world has standardised on. Its philosophy is refreshingly minimal: a test is just a function, and an assertion is just Python's assert keyword. On top of that simple base sits a powerful system called fixtures (the next chapter). This chapter covers the simple base thoroughly, so the fixtures chapter has solid ground to build on.

    12.1 A test is a function whose name starts with test_¶

    That's the entire rule for the simplest case:

    # tests/test_example.py
def test_addition():
    assert 1 + 1 == 2

    You run your tests with the pytest command (here, through uv run so it uses the project's environment):

    uv run pytest                       # find and run every test in the project
uv run pytest tests/test_example.py # run just one file
uv run pytest tests/test_example.py::test_addition   # run one specific test
uv run pytest -k "addition"         # run tests whose name matches "addition"
uv run pytest -v                    # verbose: print one line per test
uv run pytest -x                    # stop at the first failure
uv run pytest -ra                   # print a summary of skips and failures at the end

    -k and -v and -x are the flags you'll reach for daily: filter by name, see each test individually, and fail fast while debugging.

    12.2 How pytest finds tests (discovery by convention)¶

    You never register a test or list it in a manifest. pytest discovers tests by following naming conventions:

    • in files named test_*.py or *_test.py,
    • located within the paths you configure (the reference project sets testpaths = ["tests"] in pyproject.toml),
    • it collects functions named test_*,
    • and methods named test_* inside classes named Test*.

    That convention-over-configuration approach is why you can drop a new test_whatever.py into tests/ and it just runs.

    Gotcha — a non-test class named Test...

    Because pytest collects classes named Test*, a perfectly ordinary class that happens to start with "Test" gets mistaken for a test class. The reference project has a TestDatabase class (a data loader, not tests) and silences this by setting a class attribute: __test__ = False. If you ever name a non-test class Test... and see pytest emit a warning about it, that attribute is the fix.

    12.3 Plain assert — and why pytest's is special¶

    pytest does not give you a matcher library like some frameworks (no expect(x).toBe(y)). You use Python's built-in assert statement. What makes pytest's special is assertion rewriting: pytest inspects your assert and, on failure, prints a rich, introspected breakdown of why it failed — for free:

    def test_list():
    urls = ["a", "b"]
    assert len(urls) == 3

    >       assert len(urls) == 3
E       assert 2 == 3
E        +  where 2 = len(['a', 'b'])

    Notice you didn't ask for any of that detail — pytest shows the operands, the comparison, and even what produced the left-hand value. You can add a custom message after a comma, which is good practice for assertions whose failure isn't self-explanatory:

    assert len(urls) >= scenario.min_results, (
    f"scenario {scenario.id}: expected at least {scenario.min_results}, got {len(urls)}"
)

    From TypeScript

    Jest/Mocha give you a matcher DSL (expect(x).toEqual(y)). pytest instead uses the plain language assert plus compiler-level rewriting for good messages — fewer APIs to learn, and the language itself is the assertion library. (Don't confuse this with Playwright's expect() from Chapter 10, which is a separate thing, used only for page state.)

    12.4 Testing that something raises an exception¶

    Often the correct behaviour is to raise — and you want to assert that it does. Use pytest.raises as a context manager:

    import pytest

def test_parser_rejects_garbage():
    with pytest.raises(ValueError, match="no numeric value"):
        parse_price("Time left: 3d 4h")

    This asserts two things: that the block raises a ValueError, and (via match, a regex) that its message contains "no numeric value". If the block doesn't raise, or raises a different type, the test fails. This is exactly how the price parser's "refuses to guess" behaviour is pinned down (Chapter 16).

    12.5 Setup and teardown — and why fixtures replace them¶

    Tests usually need something set up first — a database connection, a browser page, some data. Older testing frameworks use setUp/tearDown methods that run before and after each test. pytest can do that, but its real mechanism is far more flexible: fixtures — functions that produce the things a test needs, which a test receives simply by naming them as parameters:

    def test_search_returns_results(page):     # "page" is a fixture, supplied by pytest
    page.goto("https://www.ebay.com")
    ...

    You didn't create page. You requested it by putting it in the parameter list, and pytest supplied a ready-made one. That is dependency injection, and it is the single most important pytest concept — important enough to get its own chapter next. For now, just register the shape: a test names what it needs, and pytest provides it.

    12.6 Skipping tests and marking expected failures¶

    Sometimes a test shouldn't run, or is known to fail. Say so explicitly, with a reason:

    @pytest.mark.skip(reason="login is gated by captcha — out of scope")
def test_login(): ...

@pytest.mark.skipif(sys.platform == "win32", reason="POSIX-only behaviour")
def test_unix_thing(): ...

@pytest.mark.xfail(reason="known bug TICKET-123; remove this mark when fixed")
def test_known_bug(): ...
    • skip — never run this test.
    • skipif(condition, ...) — run it only when the condition is false.
    • xfail — "expected to fail." It runs, but a failure is expected and doesn't fail the suite; and crucially, if it unexpectedly passes, pytest flags it ("xpassed") so you remember to remove the mark. This lets you track a known bug without a permanently red build.

    Interview lens

    "How do you handle a test for a feature that's temporarily broken or out of scope?" → "skip with a reason string, so the report records why it didn't run; or xfail for a known bug, so a future fix surfaces as an unexpected pass that prompts me to remove the marker. I never silently comment a test out — that destroys the signal and loses the reason." Emphasising the reason string is what signals discipline here.

    Exercise 12.1 — write three tests

    Create tests/test_math.py with: one passing test; one failing test with a custom assert message (run it and read pytest's introspected output); and one using pytest.raises to confirm 1 / 0 raises ZeroDivisionError. Run with -v, then with -x, and observe the difference.

    Key idea

    A test is a test_* function, discovered by convention. Assertions are plain assert, with rich rewritten failure messages for free. pytest.raises tests error paths. skip/skipif/xfail (always with a reason) preserve the signal for tests that can't or shouldn't pass right now. And dependencies arrive through fixtures — the subject of the next chapter.
