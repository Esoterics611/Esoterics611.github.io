    Chapter 16 — The Test Pyramid & Why Unit Tests¶

    Unit testing is the discipline that experienced end-to-end engineers most often skip, and the gap that most often makes an otherwise strong engineer look junior under questioning. It is also one of the easiest gaps to close. This chapter explains the economics of different test types, why a pure function is the unit-testing sweet spot, and how to write unit tests that pay for themselves many times over.

    16.1 The three layers of tests¶

    Tests come in layers, conventionally drawn as a pyramid:

            ╱╲          End-to-end (E2E / UI) tests
       ╱  ╲         few; slow (seconds); a real browser; high confidence;
      ╱────╲        brittle; expensive to maintain
     ╱      ╲       Integration tests
    ╱        ╲      some; medium speed; several units together (e.g. with a real DB)
   ╱──────────╲     Unit tests
  ╱            ╲    many; fast (milliseconds); one function in isolation; pinpoint failures
 ╱──────────────╲
    • A unit test exercises one function or class in isolation, in memory, with no I/O. It runs in milliseconds.
    • An integration test exercises several units together, possibly with a real dependency like a database or the filesystem. Medium speed.
    • An end-to-end test drives the whole stack through a real browser — the most realistic, but slow and prone to flakiness.

    The "pyramid" is a prescription about proportions: have many fast unit tests at the base, fewer integration tests, and a thin layer of end-to-end tests covering only the most important user journeys. The reasoning is economic, and worth understanding rather than memorising.

    16.2 Why not test everything end-to-end?¶

    End-to-end tests are the most convincing — they exercise the real product — but they are the worst on almost every other axis:

    Property Unit test End-to-end test
    Speed milliseconds seconds to minutes
    Flakiness essentially none network, timing, third-party site changes
    Diagnosing a failure points at the exact line "something in the flow broke"
    Setup cost none a browser, fixtures, a live site
    Confidence per test narrow but precise broad but vague

    Make it concrete. Suppose there's a bug in price parsing. An end-to-end test might catch it — but only if a product listing happens to use the problematic format — and when it does, the failure says "cart total assertion failed," pointing nowhere near the parser, after thirty seconds of running a browser. A unit test for the parser catches the same bug in two milliseconds and says parse_price("US $1,234.56") == 1234.56 failed. Same bug; roughly fifteen-thousand times faster to find and fix, with a message that names the culprit.

    Key idea

    Push correctness checks down the pyramid. Test logic at the unit level, where it's fast and precise; reserve end-to-end tests for proving the journey holds together. The opposite shape — mostly end-to-end tests, few or no unit tests — is the slow, flaky, expensive "ice-cream cone" anti-pattern that experienced UI engineers drift into.

    16.3 What makes code unit-testable: purity¶

    A pure function is one whose output depends only on its inputs, and which has no side effects — no network calls, no DOM access, no reading the clock, no global state. Pure functions are trivially unit-testable: you feed inputs and assert on the output, full stop.

    The reference project's parse_price was deliberately written this way:

    def parse_price(text: str) -> Decimal:      # a string in, a Decimal out — nothing else
    match = _DOLLAR_AMOUNT.search(text)
    if match is None:
        raise ValueError(...)
    return Decimal(match.group(1).replace(",", ""))

    No browser, no page, no I/O. So you can hammer it with edge cases instantly:

    @pytest.mark.parametrize("text, expected", [
    ("$25.00", Decimal("25.00")),
    ("US $1,234.56", Decimal("1234.56")),
    ("$25.00 to $30.00", Decimal("25.00")),           # a range → take the lower bound
    ("Subtotal (3 items) $50.00", Decimal("50.00")),  # the "3" must NOT win
])
def test_parse_price(text, expected):
    assert parse_price(text) == expected

@pytest.mark.parametrize("text", ["", "free shipping", "Time left: 3d 4h"])
def test_parse_price_rejects_garbage(text):
    with pytest.raises(ValueError):
        parse_price(text)

    That's around twenty cases, running in well under a tenth of a second, with no Chromium in sight. It is the part of the suite that is always green — the reliable demonstration you can show even when a live third-party site is having a bad day.

    Interview lens — the design insight, not just the technique

    The reason parse_price can be unit-tested is that it was deliberately extracted from the component into a pure utility. The senior framing is: "I isolate the tricky logic — price parsing, budget arithmetic, pagination decisions — into pure functions, so I can unit-test them exhaustively, and I keep the browser-dependent glue thin." That sentence shows you understand that testability is a design property you build in, not an afterthought.

    16.4 A worked example of the payoff¶

    The trickiest parsing case is "Subtotal (3 items) $50.00". A naive parser ("grab the first number you see") would return 3 — and then every budget comparison downstream would silently use the item count as if it were the price. That bug would:

    • pass most end-to-end runs (3 is less than nearly any budget),
    • occasionally cause inexplicable failures,
    • and never point a finger at the parser.

    The unit test pins it down in isolation:

    def test_dollar_anchor_beats_bare_integers():
    assert parse_price("Subtotal (3 items) $50.00") == Decimal("50.00")
    assert parse_price("Subtotal (99 items) $1.00") == Decimal("1.00")

    If someone later "simplifies" the regex and breaks the $ anchor, this test goes red immediately, naming the exact input. That is the entire value proposition of unit tests: they convert a future silent regression into a loud, located failure.

    16.5 Where each kind of test sits in the reference project¶

    Test Layer Why it lives there
    test_price_parser.py (≈22 cases) Unit a pure function, no browser
    test_smoke.py E2E (thin) "does search even work?" — the critical path
    test_search_under_price.py E2E the full journey, one canonical case
    test_scenario (data-driven) E2E the journey across many data rows

    Notice the shape: exactly one pure-logic module is heavily unit-tested, and the end-to-end layer stays focused on user journeys. Given the domain (browser automation against a live site) it's necessarily browser-heavy, but the principle still holds — the fragile, exact logic is pushed down to fast unit tests.

    Exercise 16.1 — write your first unit tests

    Write a pure function within_budget(prices: list[Decimal], budget: Decimal) -> bool that returns whether the sum of prices is within budget. Unit-test it with: an empty list; a sum exactly equal to the budget; a sum one cent over; and the float-trap case [Decimal("0.1"), Decimal("0.2")] against Decimal("0.3") (which must return True — and would break if you'd used floats). Run it and note that it's instant and needs no browser. You've just practised the most under-used skill in QA automation.

    Key idea

    Many fast unit tests at the base, few slow end-to-end tests at the top. Unit testing is possible because logic is extracted into pure functions; those tests catch regressions in milliseconds and name the exact failing input. Testability is a design choice — isolate logic from I/O and you can test it cheaply, exhaustively, and forever.
