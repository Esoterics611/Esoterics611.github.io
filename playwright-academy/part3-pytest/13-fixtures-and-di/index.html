    Chapter 13 — Fixtures & Dependency Injection¶

    Fixtures are pytest's defining feature and the concept interviewers probe hardest. They're also the thing that makes conftest.py look like magic until it clicks. This chapter takes fixtures from "I copied this and it worked" to "I understand exactly what pytest is doing and why." We build up slowly, with examples at each step.

    13.1 What a fixture is¶

    A fixture is a function that produces something a test needs. You mark it with the @pytest.fixture decorator. A test then requests that thing by listing the fixture's name as one of its parameters:

    import pytest

@pytest.fixture
def db():                          # a fixture named "db" that produces a TestDatabase
    return TestDatabase("db")

def test_scenarios_load(db):       # this test REQUESTS "db" by naming it as a parameter
    assert len(db.scenarios.all()) > 0

    Here is exactly what pytest does when it runs test_scenarios_load:

    1. It looks at the test's parameters and sees one named db.
    2. It searches for a fixture named db — and finds the function above.
    3. It calls that fixture function.
    4. It passes the return value into the test as the db argument.

    So you never write db = TestDatabase("db") inside your test. You declare a need ("I need a db") and pytest fulfils it. That separation — the test says what it needs, the fixture system handles how to build it — is called dependency injection.

    From TypeScript

    This is precisely Angular/NestJS constructor injection, or any DI container resolving providers — except keyed by parameter name rather than by type. If you've written constructor(private db: Database) and let the framework supply the instance, you already understand fixtures. The page fixture from pytest-playwright is a provider you didn't write, resolved the same way.

    13.2 Fixtures can request other fixtures (a dependency graph)¶

    This is where the power appears. A fixture can itself request other fixtures, and pytest resolves the whole chain for you, top to bottom:

    @pytest.fixture
def profile():
    return os.getenv("PROFILE", "dev")        # depends on nothing

@pytest.fixture
def db():
    return TestDatabase("db")                 # depends on nothing

@pytest.fixture
def env(db, profile):                         # depends on db AND profile
    return db.environments.get(profile)

@pytest.fixture
def search_service(page, env):                # depends on `page` (from the plugin) AND env
    return SearchService(page, env)

def test_x(search_service):                   # the test needs only ONE thing
    ...

    When test_x requests search_service, pytest must first build search_service's dependencies (page and env), and to build env it must first build db and profile. It works all of this out automatically and assembles a fully-wired SearchService — and the test simply lists search_service. This is exactly how the reference project's conftest.py constructs its services: each service fixture pulls in the page/context/env it needs, and tests just ask for search_service, cart_service, and so on.

    Pictured, pytest resolves the graph from the test downward, building each dependency in turn:

    flowchart TD
    T["test_x(search_service)"]
    SS["search_service"]
    PG["page<br/>(from pytest-playwright)"]
    EN["env"]
    DB["db"]
    PR["profile"]
    T --> SS
    SS --> PG
    SS --> EN
    EN --> DB
    EN --> PR

    Interview lens

    "How are your page objects and services instantiated in tests?" → "Constructor injection via pytest fixtures. Each service has a fixture that pulls in the page/context/env it needs; fixtures form a dependency graph pytest resolves automatically, so a test just lists search_service as a parameter and receives a fully-wired instance. No new scattered through tests, no globals — and because the wiring is in fixtures, I can swap a real dependency for a fake in one place." That last clause hints you understand testability, which lands well.

    13.3 Scope: how often a fixture is built¶

    By default, a fixture runs once per test (this is called function scope). You can widen the scope so one instance is shared across more tests — trading isolation for speed:

    @pytest.fixture(scope="session")    # built ONCE for the entire test run
def db():
    return TestDatabase("db")

@pytest.fixture(scope="function")   # the default — rebuilt fresh for every test
def search_service(page, env):
    ...
    Scope Built Good for
    function (default) once per test anything stateful or mutable; the page
    class once per test class shared setup for a group of tests
    module once per file expensive read-only setup used across a file
    session once for the whole run immutable config, the loaded database, the browser

    The governing principle: the more state a fixture shares across tests, the more opportunities for one test to corrupt another. Use a wide scope like session only for things that are immutable or genuinely safe to share — configuration, the loaded data, the launched browser. Use the default function scope for anything a test might change. In the reference project, db/env/profile are session-scoped (read-only config) while page/context and the services are function-scoped (fresh and isolated per test).

    Gotcha — shared mutable state via wide scope

    A session-scoped fixture that holds mutable state leaks that state between tests: one test's changes bleed into the next, producing failures that depend on the order tests ran in — among the most miserable bugs to track down. When in doubt, default to function scope; only widen it when you're sure the thing is safe to share.

    13.4 Setup and teardown with yield¶

    Many fixtures need to clean up after the test. A fixture that uses yield instead of return splits naturally into setup (before yield), the value handed to the test (the yielded value), and teardown (after yield) — and the teardown is guaranteed to run, even if the test fails:

    @pytest.fixture
def temp_cart(context):
    cart = create_cart(context)         # ← SETUP runs before the test
    yield cart                          # ← the test runs here, receiving `cart`
    cart.empty()                        # ← TEARDOWN runs after the test, always

def test_with_cart(temp_cart):
    ...                                 # uses temp_cart; when it ends, control returns
                                        # to the fixture and cart.empty() fires

    Trace the flow: pytest runs the fixture up to yield, hands the yielded cart to the test, the test runs, and when it finishes (pass or fail) execution resumes after the yield to do cleanup.

    From TypeScript

    A yield-style fixture is beforeEach and afterEach fused into one function, with the setup and its matching teardown sitting right next to each other so they can't drift apart. Everything before yield is beforeEach; everything after is afterEach.

    13.5 conftest.py: shared fixtures with no imports¶

    Where do you put fixtures that many test files need? In a specially-named file: conftest.py. Fixtures defined there are automatically available to every test in that directory and all subdirectories — you never import them. It is pytest's convention for "shared test infrastructure."

    tests/
├── conftest.py        # fixtures here are visible to EVERY test below — no imports needed
├── test_smoke.py      # can use db, env, page, search_service, ... just by naming them
└── unit/
    └── test_x.py      # also sees tests/conftest.py's fixtures

    This is why the reference project's tests can request search_service with no visible import — it's defined in tests/conftest.py. conftest.py is also where you put plugin-configuration hooks and overrides (the next two sections, and Chapter 15).

    13.6 autouse: fixtures that run without being requested¶

    Occasionally you want some setup to apply to every test automatically, without each test listing it. Set autouse=True:

    @pytest.fixture(autouse=True)
def _set_region_cookies(request, env):
    if not _uses_browser(request):     # skip for unit tests that have no browser
        yield
        return
    context = request.getfixturevalue("context")
    context.add_cookies([...])         # seed cookies before EVERY browser-based test
    yield

    autouse=True means "apply to every test in scope, requested or not." Use it sparingly, for genuinely cross-cutting setup like seeding cookies, configuring logging, or writing a report file. Notice the reference project's version guards itself: it checks whether the test actually uses a browser (via request.fixturenames) and does nothing for unit tests, so the fast no-browser tests don't get saddled with browser setup. That guard is a thoughtful detail worth being able to point at.

    Gotcha — unguarded autouse fixtures

    An autouse fixture runs for every test in its directory tree, including ones that don't need it. An unguarded autouse fixture that, say, launches a browser would force your fast unit tests to spin up Chromium for no reason. Always ask "does every test in scope truly need this?" — and if not, guard it (as above) or move it to a narrower location.

    13.7 The request object¶

    request is a built-in fixture that gives a fixture (or test) metadata about the test currently running:

    @pytest.fixture
def screenshots(page, request):
    return ScreenshotManager(page, test_id=request.node.nodeid)   # name files after the test

# Commonly used members:
request.fixturenames                 # the names of all fixtures this test uses
request.getfixturevalue("context")   # fetch a fixture by name, at runtime
request.node.nodeid                  # e.g. "tests/test_search.py::test_full[param]"

    request.getfixturevalue("context") lazily resolves a fixture by name — which is exactly how the autouse cookie fixture in §13.6 pulls in context only when a browser test actually needs it, rather than declaring it as a parameter (which would force it on every test).

    Exercise 13.1 — build a dependency graph

    Write three fixtures: raw_config (returns a dict), setting (depends on raw_config, returns one key from it), and a test that requests only setting. Confirm it works — you've built a two-level dependency graph and let pytest resolve it. Then add a fourth fixture using yield that prints "setup" before and "teardown" after; request it in the test and watch the order of the printed lines.

    Key idea

    Fixtures are dependency injection by parameter name; they compose into a graph pytest resolves automatically. Scope trades isolation for speed (default function; reserve session for immutable or shared things). yield fuses setup with guaranteed teardown. conftest.py shares fixtures with no imports. autouse applies cross-cutting setup (always guard it). Together these are the entire backbone of a real conftest.py.
